# K-LEGACY · Anti-Legacy Critic · Round 1 findings

### K-LEGACY-1 · major · wrong-boundary
- Target: C-SPATIAL, C-PHYS, C-ANIM, C-AUDIO, C-NET, C-GAME, C-ECS; consumers render-architect, world-architect, replication, physics-architect, audio-architect; PHY.ARCH.world; 00-design-principles §6 row 3
- Finding: §6 says the object model is hybrid, "not ECS for everything". The contract graph says the opposite. C-SPATIAL (layer 2) `requires` C-ECS. So do C-PHYS, C-ANIM, C-AUDIO, C-NET and C-GAME. render-architect, world-architect and replication also consume C-ECS as a required contract. So `ecs-runtime` is the universal world representation that every runtime subsystem is built against. It is the "one world container everyone reaches into" pattern with new vocabulary. It also contradicts §3's replaceability claim: "C-PHYS can be served by an integrated middleware". Jolt, PhysX, Havok and Box2D own their body storage and islands, and cannot sit behind a contract whose build-level dependency is the engine's ECS. Transforms needed by non-ECS consumers (editor gizmos, world-space UI, audio emitters on non-entity objects, tools) are forced through ECS as well. The indie-2d configuration must carry archetype/sparse-set ECS scheduling to use a transform.
- Evidence: Unity DOTS keeps GameObjects alongside Entities. Physics packages integrate through baking/system adapters, not by making the solver's contract depend on Entities. UE Mass is an optional plugin, not the substrate of Chaos or audio. Frostbite and Decima keep physics and audio behind their own data ownership, with bulk-sync adapters. Dependency inversion here means the physics/audio *contract* exposes handle-addressed bulk SoA streams, and the ECS *binding* is an adapter.
- Proposed change: In contracts.json, change C-SPATIAL.requires to [C-MATH, C-ID]. Change C-PHYS, C-ANIM and C-AUDIO.requires to replace C-ECS with C-ID (handles) plus C-SPATIAL. Keep C-ECS only in C-NET, and make it optional there. Add adapter capabilities that make the ECS binding explicit and replaceable: CORE.ECS.subsystem-bindings "ECS ↔ subsystem bulk-sync adapters (physics, animation, audio, render)" owned by ecs-runtime, with contributors physics-architect, animation-architect and audio-architect. In skills.json, mark C-ECS optional (`C-ECS?`) for render-architect, audio-architect and world-architect. Add a fitness function (architecture-governance) that forbids new `requires: C-ECS` edges on layer ≥3 contracts without an ADR.

### K-LEGACY-2 · major · obsolete-assumption
- Target: C-FRAME, frame-orchestration (CORE.FRAME.phases), 00-design-principles §3 "Cycles", 02 "Runtime coupling cycles"
- Finding: §3 makes C-FRAME's "phase list with sync points" the *only* way runtime data may flow between subsystems. A single engine-wide ordered phase list with barriers is the sequential `Update()` loop / UE TickGroup model. It is parallel inside each phase and serialized between phases. Nothing states that phases are the exception and data dependencies are the rule. Nothing covers multi-rate domains either. Audio runs on a device clock, network on net ticks, physics on substeps, the server tick differs from the client tick, and async compute and streaming span frames. None of these fit one per-frame phase list. The declared mechanism also has no data contract. rigid-body-dynamics owns kinematic/animated bodies (PHY.DYN.kinematic) but consumes no C-ANIM. The anim→physics flow that §3 cites as its example therefore has no declared contract, which is why 02 lists only one runtime cycle. audio-architect, ui-architect and gameplay-architect do not consume C-FRAME at all, so their scheduling placement is undeclared.
- Evidence: Destiny's task-graph engine (Tatarchuk/Genova, GDC 2015) and Naughty Dog's fiber-based frame (Gyrling, GDC 2015) schedule by data dependency and overlap frames. Bevy's and Unity's schedulers derive order from declared access, not from global stages. A global stage list recreates the "frame as a sequence of global barriers" that the §6 row 1 stance claims to remove.
- Proposed change: Narrow C-FRAME to "time domains, cadences (multi-rate), pipelining depth and the minimal set of named global sync points". Add a new layer-2 contract C-FLOW "Cross-subsystem data channels" (versioned snapshots, double/triple-buffered hand-off, mailboxes, multi-rate resampling; producer/consumer declared per channel), owned by frame-orchestration via a new capability CORE.FRAME.channels. Require every runtime `lead` to consume C-FRAME and declare its channels. Add C-ANIM (optional) to rigid-body-dynamics.consumes, or declare an anim→physics channel. Rewrite §3 "Cycles" so that phase barriers need ADR justification and dataflow edges are the default.

### K-LEGACY-3 · major · omission
- Target: gameplay-architect, scripting-runtime, C-GAME, C-SCRIPT, GAM.FW.*, GAM.SCR.*
- Finding: No capability owns the *gameplay execution model*, meaning how game logic and scripts run on a many-core machine. gameplay-architect consumes neither C-FRAME nor C-TASK. frame-orchestration disowns "system ordering inside a phase" to ecs-runtime, which covers only ECS systems. Non-ECS gameplay objects, abilities (GAM.SYS.abilities), AI decisions, camera and scripts therefore have no scheduling owner. The silent default an implementation agent will reach for is the legacy one: a serial "game thread" running per-object virtual `Tick()` plus one global script VM. scripting-runtime has capabilities for GC policy and AOT/JIT, but none for VM concurrency: per-worker VMs or isolates, parallel-safe bindings, deferred mutation through command buffers. C-SCRIPT also `requires` C-GAME, so scripting is structurally bound to the gameplay framework (UnrealScript heritage) and unusable for tools, UI logic or mods outside it.
- Evidence: UE's per-actor tick and single game thread are its most-cited scaling limit, and Mass/StateTree were added to escape it. Unity DOTS moved logic to scheduled systems. Luau parallel actors (Roblox, 2021+) and Wasm isolates show that VM-level parallelism is production-proven. Per-object tick is on the brief's explicit hunt list.
- Proposed change: Add GAM.FW.execution "Gameplay execution model: gameplay logic as scheduled systems/jobs with declared access; no per-object tick by default (opt-in, budgeted, significance-gated); serial exceptions enumerated", owned by gameplay-architect with contributors frame-orchestration and ecs-runtime. Add C-TASK and C-FRAME to gameplay-architect.consumes. Add GAM.SCR.concurrency "Script VM concurrency: per-worker VMs/isolates, thread-safe binding rules, deferred world mutation", owned by scripting-runtime. Change C-SCRIPT.requires to [C-REFL] and make C-GAME an optional consumer of scripting-runtime.

### K-LEGACY-4 · major · obsolete-assumption
- Target: C-RSCENE ("render proxies, world→render sync"), RND.ARCH.scene-sync, RND.ARCH.threading, render-architect.consumes C-ECS
- Finding: The render-scene contract bakes in UE's `FPrimitiveSceneProxy` model: a per-object mirror copied from game-side objects to a render-side object graph. RND.ARCH.threading ("render threading model") leaves the door open to a dedicated render thread, which is the game-thread/render-thread dichotomy. No stance or capability rules either one in or out. render-architect also consumes C-ECS directly, so two sync paths now co-exist: proxies and direct ECS reads, with no declared extraction semantics. GPU-driven rendering (§6 row 4) wants the opposite. Change-tracked simulation data is written as batched deltas straight into the GPU scene (RND.GEO.gpu-scene), and the "render side" is a set of tasks, not a thread.
- Evidence: Unity Entities Graphics uploads changed chunk data directly to a persistent GPU buffer. Frostbite and Destiny render with jobs, not a fixed render thread. Even UE5 has moved toward GPUScene deltas and parallel RHI command recording. Bevy's extract phase is an explicit, bounded snapshot rather than an open-ended proxy graph.
- Proposed change: Add RND.ARCH.extraction "Simulation→render extraction: change-tracked, parallel, versioned snapshot/delta upload into GPU scene; no per-object proxy mirror by default", owned by render-architect with contributors gpu-driven-pipeline and frame-orchestration, carried on C-FLOW (see K-LEGACY-2). Reword the C-RSCENE summary from "Render proxies" to "Render-scene data streams and GPU-scene deltas". Reword RND.ARCH.threading to "Parallel command recording; render work as tasks, no dedicated render/RHI thread unless an API mandates affinity (ADR)". Add §6 stance: "No fixed game/render/RHI threads."

### K-LEGACY-5 · major · omission
- Target: platform-architect (PLAT.PAL.*), job-system-task-graph, ui-architect, audio-architect, platform-mobile-portable
- Finding: No capability owns thread-affinity constraints: APIs that must run on a specific OS thread. Examples are the Win32 message pump on the window-creating thread, AppKit/UIKit on the main thread, Android's UI and Choreographer thread, OS-created audio device callback threads, and some console system-UI and suspend callbacks. Without an owner, agents default to "main thread does windowing, input, UI and scripting". That is how single-thread-first engines are built, and it is on the brief's hunt list ("main-thread-only APIs (UI, scripting, platform callbacks)").
- Evidence: SDL3 and Filament both isolate main-thread-bound calls behind a message queue so the engine loop is not the OS main thread. Wicked Engine and id Tech 7 run the frame entirely on job workers. Input and window events are marshalled from a thin OS thread.
- Proposed change: Add PLAT.PAL.thread-affinity "Thread-affinity registry & isolation of OS-thread-bound APIs (main/UI thread, audio callbacks, system dialogs) behind asynchronous queues; engine loop never assumes it runs on the OS main thread", owned by platform-architect with contributors job-system-task-graph, platform-mobile-portable and platform-console. Add CORE.JOBS.pinned "Pinned-thread lanes for affinity-bound work" to job-system-task-graph. Require ui-architect and input-system to declare that they have no main-thread dependency beyond PAL queues.

### K-LEGACY-6 · major · omission
- Target: content-pipeline-architect (CNT.COOK.*), hot-reload-iteration, editor-architect (ED.ARCH.pie, ED.ARCH.remote)
- Finding: The pipeline is "deterministic, incremental, per-platform cook" with a DDC, but no capability owns *play before a full cook*. That covers cook-on-demand/cook-on-the-fly, streaming cooked data from a cook server to a device, and loading editor-domain/uncooked data in development builds. Hot reload covers changing things after launch, not launching without the cook. The default an agent will build is the legacy one: cook-then-stage-then-run, which the brief explicitly flags ("blocking cook-before-play").
- Evidence: UE5 Zen server with cook-on-the-fly and the editor domain. Frostbite/Decima streaming data from a pipeline server to devkits. Guerrilla's "Decima tools" talk (GDC 2019) on live content streaming. In each case, iteration time is dominated by avoiding full cooks.
- Proposed change: Add CNT.COOK.on-demand "On-demand (lazy) cooking & cook-server streaming to running targets; play without full cook; editor-domain loading in development builds", owned by content-pipeline-architect with contributors hot-reload-iteration, resource-streaming-architect and editor-architect. Add a C-COOK summary clause: "processors must be invocable per-asset on demand." Add a K-TOOLS check: "first-play latency after a clean sync measured."

### K-LEGACY-7 · major · scale-down
- Target: 00-design-principles §6 row 4, gpu-driven-pipeline profiles [mobile3d, std3d], RND.GEO.fallback, RND.GEO.visbuffer
- Finding: The stance "GPU-driven rendering with a CPU-driven fallback path" is new dogma for mobile. The justification, that the fallback exists because "low-tier and older mobile GPUs lack indirect or mesh-shader features", is technically incomplete. On tile-based mobile GPUs, CPU-side culling plus instanced/batched submission is often the *preferred* path even when indirect draws are supported. The reasons are: indirect draws defeat some drivers' binning optimizations; GPU culling adds compute passes and bandwidth that TBDR cannot hide in tile memory; mesh shaders are largely absent; and visibility-buffer shading is bandwidth-hostile on TBDR. Making the CPU path a "fallback" inside the GPU-culling expert's territory makes mobile a second-class path, owned by an agent whose expertise and critic checks ("no draw-call-centric assumptions") push the other way. The stance also does not say that 2D (C-DRAW2D batched draw lists) is legitimately CPU-batched.
- Evidence: Arm Mali and Qualcomm Adreno best-practice guides (indirect-draw and compute-to-graphics costs on TBDR). The mobile renderers of UE5 and Unity URP use CPU culling and instancing by default, and Nanite-class paths are desktop/console only. The Frostbite and Activision visibility-buffer talks target desktop/console bandwidth.
- Proposed change: Rewrite §6 row 4 as "Submission strategy (GPU-driven vs CPU-culled batched) chosen per hardware tier by render-architect ADR; GPU-driven is default for desktop/console tiers." Rename RND.GEO.fallback to RND.GEO.cpu-submission "CPU-culled batched/instanced submission path as a first-class tier path with its own budgets and tests", and move it to render-architect or give it an explicit mobile-tier owner with platform-mobile-portable as a contributor. Add an explicit "2D uses batched draw lists by design" line to §6. Add to RND.GEO.visbuffer a required TBDR suitability ADR.

### K-LEGACY-8 · major · obsolete-assumption
- Target: 00-design-principles §6 row 5 ("Bindless is the default binding model"), rhi-core (RND.RHI.bindless, RND.RHI.backends incl. WebGPU), PLAT.PAL.web
- Finding: Bindless is a declared universal default, and no capability owns a non-bindless binding tier. WebGPU does not ship bindless: it has fixed bind groups and implicit synchronization, so render-graph barrier generation does not apply. A significant share of Android Vulkan devices still have unusable descriptor-indexing limits. So indie-2d on web or mobile-3d on low-end Android either cannot run or silently get a binding path that no one owns, and that path will be improvised as DX11-style slot binding.
- Evidence: WebGPU spec (bind groups; bindless is a proposal only). Android Vulkan hardware database coverage of `descriptorIndexing`/`runtimeDescriptorArray` and per-stage limits. Vulkan Roadmap 2022/2024 profiles. Bevy/wgpu run bindless as an optional feature tier.
- Proposed change: Add RND.RHI.binding-tiers "Binding-model tiers: bindless (default on capable tiers) and bind-group/descriptor-set tier for WebGPU and low-end mobile; shader-side abstraction shared with shader-system", owned by rhi-core with contributor shader-system. Add RND.RHI.implicit-sync "Backends with implicit synchronization (WebGPU): render-graph barrier output mapped or elided", owned by rhi-core with contributor render-graph-scheduling. Qualify §6 row 5 with "on capable tiers".

### K-LEGACY-9 · major · omission
- Target: ARCH.STRUCT.replaceability, C-RHI, C-PHYS, C-PLUGIN, RND.ARCH.feature-contract, 00-design-principles §3 "Replaceability"
- Finding: "Replaceable subsystems via contracts" is a core principle, but no capability decides how a contract is bound. The choices are compile-time, link-time, per-batch interface, or per-call virtual interface. The naive implementation of "C-RHI can be swapped" and "C-PHYS served by middleware" is an abstract-base-class interface with a virtual call per command, draw, body or query. That is legacy UE3/UE4 `FDynamicRHI` virtual-per-command dispatch and hot-path virtual dispatch, both on the hunt list. Phase 1 explicitly defers contract APIs (§9), so without a binding policy every contract owner will choose its own.
- Evidence: The UE RHI moved to command lists with batched, non-virtual recording to remove per-command virtual overhead. The Sokol/bgfx/The Forge backends select at compile time or through function tables per batch. In data-oriented design (Acton, CppCon 2014) the boundary is the batch, not the object.
- Proposed change: Add ARCH.STRUCT.binding "Contract binding policy: implementation selected at compile/link/module-load time; interfaces are batch-granular (spans, command buffers); no per-item virtual dispatch across a contract boundary on hot paths", owned by engine-architect with contributors cpu-performance and architecture-governance. Add a matching fitness function to ARCH.GOV.fitness.

### K-LEGACY-10 · major · obsolete-assumption
- Target: GAM.FW.rules "Game rules, players & possession", C-GAME summary ("rules, players"), C-GAME.requires [C-ECS, C-PHYS, C-ANIM, C-WORLD]
- Finding: "Possession" is UE's GameMode/PlayerController/Pawn model, imported by name with no justification. It encodes a specific inheritance-shaped control model: controllers possess pawns. That model does not fit RTS, card, puzzle, simulation, MMO, or 2D games, and there is no ADR or alternative listed. C-GAME also *requires* C-PHYS, C-ANIM and C-WORLD, so the gameplay framework is a monolith. A turn-based 2D game must build against a physics world, the animation pose contract and world-partition cells to get "game rules".
- Evidence: Bevy, Unity DOTS, Godot and most proprietary engines (Decima, id Tech) do not have a universal possession concept. Control binding is data (an input-consumer component or a player→entity association). The brief lists "actor/pawn/controller/possession gameplay model imported by habit" as a target pattern.
- Proposed change: Rename GAM.FW.rules to "Game rules & session state" and add GAM.FW.control "Player/agent ↔ controlled-entity association as data (control model chosen per game by ADR; possession is one option)". Change C-GAME.requires to [C-ID, C-FRAME] and make C-ECS, C-PHYS, C-ANIM and C-WORLD optional consumers of gameplay-architect, with persistence-save's C-WORLD also optional.

### K-LEGACY-11 · minor · obsolete-assumption
- Target: CORE.OBJ.events (entity-object-model), GAM.SYS.messages (gameplay-systems-toolkit), C-RES "residency callbacks"
- Finding: No capability or stance fixes the delivery semantics of events and callbacks. Immediate synchronous observer dispatch, where the caller runs the listener on its own thread in the middle of an update, is the legacy pattern that makes parallel scheduling unsafe and ordering implicit. C-RES "residency callbacks" invite the same thing from IO completion threads into arbitrary subsystems.
- Evidence: Frostbite, Destiny and ECS schedulers all use deferred, batched event queues consumed in a declared place. Immediate callbacks across subsystems are a known source of data races and re-entrancy bugs.
- Proposed change: Extend CORE.OBJ.events to "Events & messaging: deferred, batched delivery at declared consumption points by default; immediate dispatch only within one owner (ADR)". Change the C-RES summary from "residency callbacks" to "residency notifications (queued, consumed by owner)".

### K-LEGACY-12 · minor · obsolete-assumption
- Target: C-CFG, CORE.LIFE.config ("typed cvars, change notification")
- Finding: Cvars are process-global mutable state that any thread can read at any time: the Quake console-variable model. §6 row 8 forbids hidden globals, but the config contract does not say how cvar reads interact with parallel tasks. The options are snapshotting per frame or phase, or immutable views. Nor does it say where change notification is delivered.
- Evidence: A mid-frame cvar change read by two parallel jobs produces inconsistent state, and TSan catches this in practice. Engines that parallelize heavily latch config into per-frame immutable snapshots (e.g., UE's render-thread cvar shadow copies exist precisely because the global model broke).
- Proposed change: Add CORE.LIFE.config-snapshots "Config/cvar reads via versioned immutable snapshots latched at declared sync points; change notification queued", owned by core-runtime-architect with contributor frame-orchestration, and reflect it in the C-CFG summary.

### K-LEGACY-13 · minor · obsolete-assumption
- Target: CORE.REFL.dynamic, C-REFL ("dynamic invocation"), CORE.TYPES.strings ("interned names"), C-UI data binding, GAM.SYS.tags
- Finding: No stance limits stringly-typed reflection. Dynamic invocation by name, interned-name lookup (the FName pattern) and reflection-driven UI data binding are listed as established defaults, with no rule that runtime hot paths use static, compile-time reflection and resolved IDs. Name-based lookup would then be restricted to tools, scripting and serialization boundaries. The brief flags "stringly-typed reflection".
- Evidence: C++26 static reflection (P2996), which the artifact already cites in CORE.REFL.generation, and codegen-based typed accessors make runtime string lookup unnecessary outside tool boundaries. UMG property-path bindings are a known UE performance problem, and Epic introduced ViewModel/FieldNotify to replace them.
- Proposed change: Add CORE.REFL.static-default "Static/compile-time reflection and resolved type/property IDs on runtime paths; string lookup only at tool, script and serialization boundaries", owned by reflection-metadata. Make UI.FW binding use resolved IDs (contributor ui-architect).

### K-LEGACY-14 · minor · obsolete-assumption
- Target: GAM.SCR.gc, CORE.OBJ.references, GAM.SYS.spawning ("spawning and pooling")
- Finding: The framework owns a script GC *policy*, but no stance forbids engine objects being GC-managed or tracing-reachable (the UObject model). entity-object-model owns references and lifetime but does not state that engine lifetime is explicit and handle-based, with script-side references as weak handles. "Pooling" as a default gameplay capability is a GC-era workaround that becomes redundant with chunked, generational-handle allocation.
- Evidence: UE's GC hitches are listed by the artifact itself under PRF.LOAD.hitches ("GC pauses"), and incremental/parallel UObject GC is years of remediation. Unity DOTS and Bevy have no engine-object GC.
- Proposed change: Extend CORE.OBJ.references to "... engine-object lifetime is explicit (owner + generational handles); no tracing GC over engine objects; script-held references are weak handles". Reword GAM.SYS.spawning to "Spawning (batched, deferred structural changes); pooling only where measured".

### K-LEGACY-15 · minor · obsolete-assumption
- Target: RES.IO.mmap (async-io-storage, maturity E)
- Finding: Memory-mapped IO is listed as an established IO capability with no constraint. Page-fault-driven reads are synchronous, unprioritized IO hidden inside ordinary loads. On hot threads they reintroduce the synchronous-IO hitch that §6 row 7 claims to remove, and they bypass the deadline/priority scheduler.
- Evidence: Crotty, Leis and Pavlo, "Are You Sure You Want to Use MMAP in Your DBMS?" (CIDR 2022). DirectStorage and io_uring designs explicitly avoid page-fault IO for streaming.
- Proposed change: Reword RES.IO.mmap to "Memory-mapped IO restricted to prefetched/locked or tool-side use; never on latency-critical workers without explicit prefetch". Add a K-SYSTEMS check that no streaming path depends on demand paging.

### K-LEGACY-16 · minor · other
- Target: ARCH.GOV.anti-legacy, critics.json K-LEGACY (checks), docs/05 K-LEGACY mandate
- Finding: The flagged-pattern catalogue that K-LEGACY checks against, "each flagged pattern either absent or justified by an ADR", exists only as a prose sentence in docs/05, not as data. That list also omits several patterns from the brief: game/render-thread dichotomy, main-thread-only APIs, per-object tick, GC-managed engine objects, stringly-typed reflection, level-as-a-file loading, editor-in-runtime monoliths and blocking cook-before-play. Phase-2 SKILL.md authors and the G2/S* stages therefore have no enumerable checklist, and K-LEGACY is absent from S4, where frame-tied or synchronous behavior would show up in captures.
- Evidence: See K-LEGACY-3/4/5/6/13/14. The patterns the list omits are exactly those this review found silently present.
- Proposed change: Add data/legacy-patterns.json (id, pattern, detection hint, default stance, owner of the justification), owned by architecture-governance via ARCH.GOV.anti-legacy. Make critics.json K-LEGACY.checks reference it, and add stage S4 to K-LEGACY.
