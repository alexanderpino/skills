# K-PERF · Performance Critic · Round 1 findings

### K-PERF-1 · blocker · wrong-boundary
- Target: performance-architect, cpu-performance, gpu-performance, loading-streaming-performance; PRF.CPU.cache, PRF.CPU.contention, PRF.LOAD.load-time, PRF.LOAD.hitches, PRF.GPU.overlap
- Finding: The non-responsibilities of the performance subtree contradict each other, so nobody clearly owns the code change that fixes a performance problem. `performance-architect` says "Optimizing a subsystem's code (its owner does, with review)" and points that line at `cpu-performance`. `cpu-performance` says "Owning subsystem code" belongs to `engine-architect`, which owns no subsystem code. At the same time the PRF.* capabilities use optimization verbs: "Load-time optimization", "Hitch & stutter elimination", "Cache & memory-access optimization". Those describe edits to code in `async-io-storage`, `rhi-core`, `ecs-runtime` and so on. The three experts provide no contract and have no defined output. Under principle 1.4 (independent validation), a critic has no artifact of theirs to judge. The result is either two agents editing the same files, or findings that no agent is bound to act on.
- Evidence: Production perf teams (the Frostbite and Unreal Engine "strike team" models) work in one of two ways. Either they file owned tickets against the subsystem owner, or they are given temporary code ownership through an explicit handoff. Both need a protocol. The ownership-ledger design (ARCH.ORG.ownership-ledger) cannot hold two owners for one file set.
- Proposed change: (a) Fix the non-responsibility pointers. `performance-architect` → "Optimizing subsystem code → the owning skill (via C-PERF finding)". `cpu-performance` → "Owning subsystem code → the owning skill of that territory". (b) Rename the PRF.CPU/GPU/LOAD capabilities to analysis verbs, e.g. "Load-time analysis & root-cause attribution". (c) Add a process contract `C-PERF` (layer P, owner `performance-architect`). It covers the finding format (hypothesis, capture, attribution, expected gain), how a finding is routed as a C-ORCH change request to the owning skill, and time-boxed territory loans recorded in the ledger. (d) Give each expert territory it owns outright, so it can be validated independently. `cpu-performance`: PGO/LTO build profiles and the flag policy, moving PRF.CPU.compiler to sole ownership. `gpu-performance`: automated GPU capture and per-pass cost baselines (new PRF.GPU.baselines). `loading-streaming-performance`: load/hitch trace analyzers and the hitch gate (new PRF.LOAD.hitch-gate).

### K-PERF-2 · major · missing-contract
- Target: frame-orchestration (CORE.FRAME.phases), ecs-runtime (CORE.ECS.scheduling), C-FRAME, C-ECS
- Finding: Two schedulers are defined with no shared dependency model. `ecs-runtime` owns access-conflict analysis, but only for ECS systems inside a phase. `frame-orchestration` owns "phases, sync points & phase barriers". Much frame work is not an ECS system: physics stepping (often middleware), render extraction/sync, audio parameter push, replication gather, streaming activation, animation evaluation pipelines. That work cannot state which data it reads and writes, so the only safe ordering is a phase barrier. The frame then degenerates into a fixed sequence of fork/join phases, the "tick groups" pattern. That is the legacy central loop with parallel-for inside it, and it adds hidden global sync points. The K-PERF check "no hidden global sync points" has no capability behind it.
- Evidence: Frostbite's FrameGraph applies declared-access scheduling to GPU work, and Destiny's and Naughty Dog's fiber job graphs apply it to CPU work. Unity DOTS job dependencies come from declared component access. In each case, overlap across subsystems comes from declared read/write sets, not from coarse phases. Engines that rely on phases (UE tick groups) report the game-thread critical path as their dominant limit.
- Proposed change: Add CORE.FRAME.access, "Frame-wide data-access declarations (read/write sets over component types, singleton resources, world regions and subsystem-owned data) for all frame work, ECS and non-ECS; barriers derived, not hand-placed". Owner: `frame-orchestration`; contributors: `ecs-runtime`, `physics-architect`, `render-architect`. Extend the C-FRAME summary to "phase list AND access declarations". `ecs-runtime` then exports its system access sets into this model. Add CORE.FRAME.critical-path, "Frame critical-path analysis and phase-overlap reporting". Owner: `frame-orchestration`; contributor: `performance-architect`.

### K-PERF-3 · major · missing-contract
- Target: gpu-driven-pipeline (RND.GEO.gpu-scene, RND.GEO.instancing), render-architect (RND.ARCH.scene-sync), C-RSCENE; consumers vegetation-foliage, terrain, procedural-generation, crowd-simulation, destruction-fracture, ray-tracing-infrastructure (RND.RT.instances)
- Finding: The persistent GPU scene is the structure that makes instance counts scale. Its owner, `gpu-driven-pipeline`, provides no contract. Every bulk instance producer (foliage with millions of instances, runtime PCG, HLOD, crowds, debris) can only reach the renderer through C-RSCENE, whose summary is "Render proxies, world→render sync". That wording implies a per-object proxy that is created, updated and synced every frame. This is the UE4 `FPrimitiveSceneProxy` model, whose CPU cost grows with object count, not with change count. The TLAS instance feed (RND.RT.instances) uses the same instance data, but no shared contract ties the two together.
- Evidence: UE5 moved to GPUScene with delta uploads and the Instanced Static Mesh / "Nanite instance" batch APIs because the per-proxy path did not scale. Ubisoft's GPU-driven pipeline (Haar & Aaltonen, SIGGRAPH 2015) and Wihlidal's Frostbite GPU-driven rendering (GDC 2016) both use persistent, batch-updated instance buffers. Per-frame CPU work there scales with O(changed instances).
- Proposed change: Add contract `C-GPUSCENE` (layer 3, owner `gpu-driven-pipeline`, requires C-RG, C-GPUMEM). It covers persistent instance/primitive handles, batched add/remove/update with delta upload, and the instance data layout shared with the TLAS builder. `vegetation-foliage`, `terrain`, `procedural-generation`, `crowd-simulation`, `destruction-fracture` and `ray-tracing-infrastructure` consume it. Restate C-RSCENE as a feature/view contract, not per-object proxies. Add a stated asymptotic requirement on RND.ARCH.scene-sync: CPU cost O(changes), not O(objects). For configurations without `gpu-driven-pipeline`, the CPU fallback (RND.GEO.fallback) serves the same contract.

### K-PERF-4 · major · missing-contract
- Target: spatial-transforms (WLD.SPACE.transforms), C-SPATIAL; consumers physics-architect, render-architect, audio-architect, replication (NET.REP.interest), navigation-pathfinding, ai-behavior-perception
- Finding: At least seven subsystems keep their own spatial copy of entity transforms: the physics broadphase, GPU scene, audio emitters, replication interest grid, spatial index, AI perception and nav obstacles. No contract publishes which transforms changed. C-SPATIAL offers representation, hierarchy and queries. ECS change detection (CORE.ECS.change) covers only ECS data and is per-query version filtering, not a changed-entity stream that non-ECS middleware can consume. Without a change stream, each consumer rescans all N entities per frame (O(N × consumers)) or builds its own dirty tracking. Neither of those appears in the map.
- Evidence: Scalable engines publish a "moved this frame" set once and fan it out. Examples are UE5's `FPrimitiveSceneInfo` dirty lists and the Mass processors' change filters, and Jolt's body-interface batch updates for broadphase moves. Bevy's change ticks likewise feed `Changed<Transform>`.
- Proposed change: Add WLD.SPACE.change-sets, "Per-phase transform change sets (moved / attached / teleported) published once and consumed by all spatial replicas; teleport vs continuous distinction". Owner: `spatial-transforms`; contributors: `ecs-runtime`, `physics-architect`. Add "change sets" to the C-SPATIAL summary. Add a crosscutting obligation under "scalability": every spatial replica must declare O(changed) update cost.

### K-PERF-5 · major · omission
- Target: world-architect (WLD.PART.grid, WLD.PART.sources), resource-streaming-architect (C-RES "residency callbacks"), C-WORLD, C-PHYS, C-NAV
- Finding: When a streaming cell finishes loading, its content must be activated. That means instantiating ECS entities (structural changes), inserting bodies into the broadphase, registering GPU-scene instances, linking nav tiles, registering replicated objects and running runtime PCG. Nothing owns doing that in a budgeted, time-sliced way with bulk registration. The only listed hook is C-RES "residency callbacks", which suggests synchronous callbacks from completion threads into arbitrary subsystems. That creates either data races or global locks. Activation spikes are the dominant open-world hitch source, and PRF.LOAD.hitches can only review them, not own them.
- Evidence: UE5 World Partition added time-sliced "AddToWorld"/level streaming budgets (`s.LevelStreamingComponentsRegistrationGranularity`, the incremental registration budget) after activation hitches. Insomniac's and Guerrilla's (Decima) streaming talks describe relocatable, pre-baked cell blobs that are patched in place in batches. Jolt and PhysX both provide batch add APIs, because single inserts into the broadphase are pathological.
- Proposed change: Add WLD.PART.activation, "Budgeted, time-sliced cell activation/deactivation pipeline with per-frame activation budgets and bulk registration protocol". Owner: `world-architect`; contributors: `ecs-runtime`, `physics-architect`, `gpu-driven-pipeline`, `navigation-pathfinding`. Extend C-WORLD with "activation batches". Require C-PHYS, C-GPUSCENE (K-PERF-3), C-NAV and C-NET to expose batch add/remove with cost O(batch). Replace "residency callbacks" in C-RES with "completion events drained at a declared C-FRAME phase".

### K-PERF-6 · major · wrong-boundary
- Target: resource-streaming-architect (RES.MGMT.streaming), texture-streaming-vt (RND.TEX.mip-streaming, RND.TEX.feedback), virtualized-geometry-lod (RND.LOD.streaming), direct-lighting-shadows (RND.LIGHT.vsm physical pages), audio-dsp-mixing (AUD.DSP.streaming), gpu-memory-resources (RND.MEM.budget), memory-allocators (CORE.MEM.budget-enforcement, CORE.MEM.uma)
- Finding: At least five streaming pools each own their own residency policy: texture/VT mips, cluster pages, VSM pages, audio, and world cells, plus animation and ML models. Budgets for the same physical memory are split three ways: GPU memory (`gpu-memory-resources`), CPU enforcement (`memory-allocators`) and streaming (`resource-streaming-architect`). On UMA consoles and portables all of this is one pool with one IO queue. No capability arbitrates memory or IO bandwidth across pools, or rebalances them when pressure moves (for example, a camera cut or fast traversal). The GPU-feedback-driven streamers (sampler feedback, cluster page requests, VSM page marking) produce requests on the GPU. C-RES has no notion of batched GPU-originated requests, and their readback latency interacts with RND.GRAPH.readback.
- Evidence: UE5 has separate pools for Nanite streaming, VT, the texture streamer and VSM, each tuned independently. Tuning these on consoles is well known to be painful, and "texture pool over budget" cascades are a common shipping issue. Microsoft's DirectStorage and Sampler Feedback Streaming guidance assumes one IO scheduler with priorities across clients.
- Proposed change: Add RES.MGMT.arbitration, "Cross-pool memory and IO-bandwidth arbitration (texture, geometry pages, shadow pages, audio, animation, world cells, ML models) with pressure-driven rebalancing; single physical budget on UMA". Owner: `resource-streaming-architect`; contributors: `gpu-memory-resources`, `memory-allocators`, `performance-architect`. Add RES.MGMT.gpu-requests, "Batched GPU-originated streaming requests (feedback buffers) and their latency contract". Owner: `resource-streaming-architect`; contributor: `render-graph-scheduling`. In C-RES, add "pool registration and pressure signals". Make the texture, geometry, VSM and audio streamers clients of the arbiter rather than independent pools.

### K-PERF-7 · major · omission
- Target: performance-architect (PRF.METH.*), K-PERF check "asymptotics stated for world-scale data"
- Finding: No capability owns an analytical performance or capacity model. The map has no per-phase cost model (cost per entity, instance, light, replicated object, cell, navmesh tile or voice, times counts, per tier), and nothing states asymptotic behavior along each world-scale dimension. Budgets (PRF.METH.budgets) are therefore numbers with no derivation. Scale limits for configurations like `aaa-open-world-online` can only be found empirically, after content exists. That is too late to change an O(N²) interest-management design or a per-proxy render sync. The critic check about asymptotics has no owner to hold accountable.
- Evidence: Budget derivation from cost models is standard practice in console launch planning, e.g. Naughty Dog's and Guerrilla's per-frame "ms per thing" spreadsheets and Insomniac's perf budgets. Server capacity planning (players per core, bytes per player per second) is the basis of fleet cost in every live-service title. Roofline-style GPU models (Williams et al. 2009) are established for bandwidth-bound passes.
- Proposed change: Add PRF.METH.model, "Analytical performance and capacity model: per-phase unit costs × declared counts per hardware tier and configuration; derived budgets; predicted scale limits; model-vs-measurement reconciliation". Owner: `performance-architect`; contributors: `perf-benchmarking`, `network-architect`, `world-architect`. Add PRF.METH.asymptotics, "Declared asymptotic cost per world-scale dimension for every runtime skill". Owner: `performance-architect`. Add the corresponding obligation to the crosscutting "scalability" row: "declare unit costs and asymptotic class per scale dimension".

### K-PERF-8 · major · omission
- Target: reconstruction-upscaling (RND.RECON.dynres), world-architect (WLD.PART.sim-lod), platform-mobile-portable (PLAT.MOB.thermal), gpu-performance (PRF.GPU.power), cpu-performance (PRF.CPU.hybrid), vfx-particles (RND.VFX.budgets), animation-architect (ANM.ARCH.lod), performance-architect (PRF.METH.scalability)
- Finding: Runtime scalability actuators are spread across eight owners, and there is no closed-loop controller. Dynamic resolution, the significance/simulation LOD, VFX budgets, animation update rate, thermal adaptation and frame pacing would each react to frame time or power on their own. Independent controllers oscillate or fight each other, e.g. dynres dropping while VFX LOD also drops, then both overshoot. PRF.METH.scalability is a static framework of device profiles. Power and thermal ownership is split three ways (PLAT.MOB.thermal, PRF.GPU.power, PRF.CPU.hybrid), and "runtime power governor" is owned by none of them. Handhelds (PLAT.DESK.handheld) and mobile depend on this mechanism most.
- Evidence: Android's Adaptive Performance / ADPF (thermal headroom, performance hint sessions), Apple's thermal-state API and Unity's Adaptive Performance package all provide one governor that drives many knobs. UE combines Dynamic Resolution with the Significance Manager, but they are separate loops, which licensees coordinate by hand.
- Proposed change: Add PRF.METH.governor, "Runtime performance governor: consumes frame-time, GPU-time, thermal/power headroom and memory-pressure signals; drives registered scalability actuators with priorities and hysteresis". Owner: `performance-architect` (already runtime=true); contributors: `frame-orchestration`, `platform-mobile-portable`. Extend C-BUDGET with "actuator registration and control signals". RND.RECON.dynres, WLD.PART.sim-lod, RND.VFX.budgets and ANM.ARCH.lod then become registered actuators.

### K-PERF-9 · major · omission

### K-PERF-10 · major · missing-contract
- Target: perf-benchmarking (PRF.BENCH.workloads, PRF.BENCH.micro), crosscutting "performance" obligation ("the benchmark that proves them")
- Finding: Every skill must "declare … the benchmark that proves" its budgets, but `perf-benchmarking` provides no contract. That leaves no defined way to register a micro or workload benchmark, declare its metrics, tie it to a C-BUDGET line, or make runs reproducible. Realistic workloads at world scale are also unowned. That includes synthetic stress worlds (10⁶ instances, 10⁴ agents, 10³ lights, 100+ replicated players with bots), and they need content before production content exists. `perf-benchmarking` consumes none of the contracts needed to build them (C-WORLD, C-GAME, C-RSCENE, C-DET). Replay-driven runs are the only way to get low-variance gameplay benchmarks, and nothing connects them to XC.DET.replay.
- Evidence: id Tech's and Frostbite's automated perf runs rely on deterministic camera paths and recorded play. Unity's Performance Testing Extension and Google Benchmark give the micro-level registration model. Without a registration contract, 96 expert agents will produce 96 incompatible harnesses.
- Proposed change: Add contract `C-BENCH` (layer P, owner `perf-benchmarking`). It covers benchmark registration, metric schema, the C-BUDGET line reference, warm-up and variance rules, and the required hardware tier. Add PRF.BENCH.scale-content, "Procedural synthetic stress worlds per configuration and scale dimension". Owner: `perf-benchmarking`; contributors: `procedural-generation`, `functional-automation-soak`. Add PRF.BENCH.replay, "Replay- and flythrough-driven deterministic benchmark runs". Owner: `perf-benchmarking`; contributor: `determinism-replay`. `perf-benchmarking` then consumes C-WORLD?, C-GAME?, C-DET?.

### K-PERF-11 · major · omission
- Target: PRF domain; memory-allocators (CORE.MEM.tracking); functional-automation-soak (QA.FUNC.soak); crosscutting "memory usage" (owner memory-allocators)
- Finding: The performance subtree has CPU, GPU and loading experts but no memory-performance expert. `memory-allocators` owns mechanisms (tagging, enforcement) and `performance-architect` owns the numbers. Nobody owns memory analysis: whole-process footprint across CPU, GPU and UMA; snapshot capture and diffing; per-asset, per-cell and per-feature content attribution; peak analysis during transitions such as level travel, cutscene preload and cell churn; and fragmentation-over-time reports. The crosscutting "memory usage" obligation is reviewed by the allocator implementer, who then judges their own mechanism. Memory is the most common console ship blocker, and a reviewer-only CPU expert does not cover it.
- Evidence: UE Memory Insights and LLM, the PlayStation Razor memory analyzer, PIX memory captures and Xbox's title memory budget reviews exist because memory footprint is analyzed as its own discipline. Many AAA studios have dedicated "memory strike teams" before cert.
- Proposed change: Add expert skill `memory-performance` (parent `performance-architect`, runtime=false, profiles all). New capabilities: PRF.MEM.footprint (whole-process CPU+GPU+UMA footprint analysis per tier), PRF.MEM.snapshots (snapshot capture and diff tooling), PRF.MEM.attribution (content-level memory attribution per asset, cell and feature), and PRF.MEM.peaks (transition peak analysis). Move the crosscutting "memory usage" review owner to `memory-performance`, keeping `memory-allocators` as mechanism owner. Alternatively, if a new skill is rejected, assign these capabilities to `loading-streaming-performance` renamed "Memory, Loading & Hitch Performance".

### K-PERF-12 · major · omission
- Target: job-system-task-graph (CORE.JOBS.hetero, CORE.JOBS.blocking), physics-architect (PHY.ARCH.build-integrate), audio-architect (AUD.ARCH.middleware), ml-inference-runtime, async-io-storage, network-transport, observability-telemetry
- Finding: The map assumes all CPU work runs through the job system. Yet it explicitly allows integrated middleware (physics, Wwise/FMOD-class audio, ML runtimes) and has its own always-on threads: audio mixer, IO completion, network, telemetry upload, shader compile workers and the GPU submission thread. No capability owns the process-wide thread inventory and core-affinity/QoS policy, or requires job-system adapters for middleware thread pools. On fixed-core consoles (6.5–7 usable cores) and hybrid P/E desktops, oversubscription and priority inversion between middleware pools and the job system are standard causes of frame spikes.
- Evidence: Console TRCs and platform guidance require explicit core affinity. Jolt, PhysX and Havok expose job-system interfaces precisely so engines can avoid a second thread pool. Wwise exposes `AkJobMgr` for the same reason. Intel's Thread Director guidance for hybrid cores says QoS classes must be set process-wide.
- Proposed change: Add CORE.JOBS.thread-budget, "Process-wide thread inventory, core-affinity and QoS policy per platform; mandatory job-system adapters for middleware and runtime thread pools; oversubscription detection". Owner: `job-system-task-graph`; contributors: `platform-architect`, `cpu-performance`. Add "dedicated threads declared in the thread inventory" to C-TASK, and add an obligation to the crosscutting "concurrency" row.

### K-PERF-13 · major · scale-down
- Target: crowd-simulation (profiles ["openworld"]); GAM.AI.mass, GAM.AI.flowfields; seed-map "large-scale simulation" → GAM.AI.mass
- Finding: The brief's "large-scale simulation" maps to GAM.AI.mass and WLD.PART.sim-lod. `crowd-simulation` is tagged only `openworld`, so `indie-2d`, `standard-3d` and `online-3d` configurations cannot include mass-agent simulation or flow fields. RTS, colony-sim, factory, tower-defense and horde games are large-scale simulations without an open world, often 2D and often deterministic-lockstep. Those configurations therefore scale up with no owned bulk-simulation path. They fall back to per-entity AI (`ai-behavior-perception`), which is the O(N)-heavyweight path.
- Evidence: Examples are Factorio (2D, deterministic lockstep, 10⁵+ entities), They Are Billions (2D, 10⁴ units), Total War (non-open-world), and Unity DOTS's primary showcases (RTS/crowds, not open world).
- Proposed change: Either add a `largesim` add-on profile, tag `crowd-simulation` with ["openworld", "largesim"] and add configurations such as `indie-2d-largesim` = [min2d, largesim, online?], or change `crowd-simulation` profiles to ["min2d", "mobile3d", "std3d", "server"] and make it opt-in per configuration. Also add a 2D/grid variant note to GAM.AI.flowfields, and have check.py prove a large-simulation configuration closed.

### K-PERF-14 · major · obsolete-assumption
- Target: shader-system (RND.SHADER.pso-lists, RND.SHADER.permutations), rhi-core (RND.RHI.pso), material-system, loading-streaming-performance (PRF.LOAD.hitches)
- Finding: PSO coverage is owned only as "PSO / permutation list gathering from play traces" plus async creation. Trace-gathered PSO caches are the approach that repeatedly failed in PC shipping: coverage gaps become first-encounter stutter. The current best practice is load-time PSO precaching driven by the material × vertex-layout × pass combinations of assets as they are loaded. That spans `material-system` (which combinations exist), `gpu-driven-pipeline` (vertex formats and passes), C-RES (the load hook) and `rhi-core` (creation). No one owns this end to end. No capability owns a permutation-count budget either, which drives both cook time and runtime PSO count.
- Evidence: Epic introduced PSO Precaching in UE 5.1–5.3 because bundled trace caches ("PSO caching" from playtests) did not remove stutter in shipped titles. See the Epic "Game engines and shader stuttering" blog (2025) and Digital Foundry coverage. Visibility-buffer and uber-material approaches (id Tech 7, Decima) avoid the problem by keeping PSO counts small by design.
- Proposed change: Add RND.SHADER.precache, "Load-time PSO precaching derived from loaded asset/material/pass combinations; no dependence on trace coverage". Owner: `shader-system`; contributors: `material-system`, `rhi-core`, `resource-streaming-architect`. Add RND.SHADER.permutation-budget, "Permutation and PSO-count budgets per configuration with cook-time enforcement". Owner: `shader-system`; contributor: `performance-architect`. Demote RND.SHADER.pso-lists to a coverage-validation capability.

### K-PERF-15 · minor · omission
- Target: engine-architect (ARCH.REQ.hardware-tiers), performance-architect (PRF.METH.budgets), C-BUDGET
- Finding: The hardware tiers are "portable, mobile, console, PC min/rec/high". They include no server tier (vCPU per instance, memory per instance, cost per player-hour), yet NET.SRV.density and QA.FUNC.load need one. They also include no refresh-rate class (XR at 90/120 Hz, competitive at 240 Hz), which changes every per-phase budget. Budgets are also keyed per tier only, not per configuration: `indie-2d` and `aaa-open-world-online` on the same console need different budget splits.
- Evidence: Dedicated-server budgets are stated in cores and cost per CCU in every live-service postmortem. XR frame-time budgets (11.1 ms / 8.3 ms, including a compositor reserve) are platform requirements.
- Proposed change: Extend ARCH.REQ.hardware-tiers with "server instance classes" and "refresh-rate classes". Change PRF.METH.budgets to "Budgets per hardware tier × configuration × refresh class". Add `dedicated-server` as a contributor to ARCH.REQ.hardware-tiers.

### K-PERF-16 · minor · wrong-boundary
- Target: animation-architect (ANM.ARCH.sync), physics-architect (PHY.ARCH.stepping), rigid-body-dynamics (PHY.DYN.kinematic), C-ANIM, C-PHYS
- Finding: The animation→physics→animation ordering is a sequence of pre-physics pose, kinematic targets, step, ragdoll/foot-IK read-back, then skinning. It usually forms the longest serial chain on the simulation critical path. ANM.ARCH.sync is owned by `animation-architect` alone with no contributors. No physics-side skill consumes C-ANIM, so kinematic targets have no contract path; only the principle document asserts that the flow goes "through C-FRAME". The number and placement of these hand-off points directly sets frame latency and parallel slack, and two leads can each set it independently.
- Evidence: UE's "tick prerequisites" between SkeletalMeshComponent and physics are a well-known source of serial game-thread chains. Decima and id Tech describe pipelining animation one frame ahead to break the chain, which is a policy decision needing both owners.
- Proposed change: Add `physics-architect` and `frame-orchestration` as contributors to ANM.ARCH.sync. Add C-ANIM? to the consumes list of `rigid-body-dynamics` (kinematic targets). Require the animation/physics hand-off phases to be declared in C-FRAME, with a stated latency (same-frame vs one-frame-delayed) per configuration.

### K-PERF-18 · minor · omission
- Target: observability-telemetry (OBS.LOG.tracing), rhi-core (RND.RHI.queries), cpu-performance, gpu-performance
- Finding: Only trace zones and timestamp/pipeline-statistics queries are owned. In-engine sampling of hardware performance counters is not: CPU PMU counters for top-down / cache-miss attribution, and GPU streaming performance counters (occupancy, bandwidth, cache hit rate) per render-graph pass.
