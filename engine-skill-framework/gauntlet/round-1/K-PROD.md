# K-PROD · Production Critic · Round 1

### K-PROD-1 · blocker · omission
- Target: ARCH.ORG.integration, ARCH.ORG.decomposition, program-orchestration, C-ORCH, XC.DX.samples
- Finding: There is no bootstrap path and no milestone plan. "Integration sequencing & milestone vertical slices" is one capability line with no content behind it. Nothing names the walking skeleton: the smallest end-to-end build that boots on one platform, runs the task graph, opens a window, presents through the RHI, reads input, draws a 2D sprite, loads one cooked asset from a package, and passes CI. Nothing says which skills take part in it, which contracts must exist first (as stubs or fakes), or what the exit criteria are. The data has only one ordering signal, contract layer 0→5. Read literally, that ordering gives a bottom-up waterfall. Upper-layer agents (render features, gameplay, editor) would wait for complete lower layers, or would build against contracts nobody has drafted yet. Configurations are proven closed. Milestones are not modeled at all.
- Evidence: Every engine bring-up that has gone well was vertical-first: a thin end-to-end slice, then widening (Cockburn's "walking skeleton"; the id and Frostbite practice of keeping the game running from day one; Unreal's sample-driven validation with Lyra and City Sample). If 124 agents start without a shared integration target, you get integration hell at the first merge. You also get consumers coding against the wrong reading of a contract, because C-ECS, C-RSCENE and others are only one-line summaries.
- Proposed change: Add `ARCH.ORG.bootstrap` ("Walking-skeleton definition and bring-up order", owner program-orchestration, contributors engine-architect, platform-architect, ci-cd-automation). Add `ARCH.ORG.milestones` ("Milestone ladder with per-milestone skill set, contract maturity level and exit criteria", owner program-orchestration). Add `data/milestones.json`, with each milestone listing its participating skills, the contracts required at stub, draft or frozen level, and the sample or scenario that proves it. Tie the milestones one-to-one to the XC.DX.samples ladder and to the named configurations (M0 skeleton → M1 indie-2d → M2 standard-3d → M3 open-world → M4 online → M5 aaa). Extend check.py so each milestone is proven closed, the same way configurations are. Add `ARCH.ORG.contract-stubs` ("Contract-first fakes/mocks so consumers start before providers finish", owner test-architect as part of QA.STRAT.contracts).

### K-PROD-2 · blocker · missing-contract
- Target: C-ORCH, ARCH.ORG.ownership-ledger, skills.json schema, contributors field in capabilities.json
- Finding: Territory is defined only as capabilities, and agents edit files and modules, not capabilities. No skill declares the code modules, directories or namespaces it may write. There is no rule for inherently shared files: root build scripts, module registration, shared shader include headers across 18 render experts, common component definitions, the reflection codegen output, and the project config. "Contributors" appear on many capabilities (for example CNT.COOK.variants ← performance-architect, WLD.ENV.buoyancy ← character-vehicle-physics), but nothing says whether a contributor may write the owner's code or only files change requests. The "ownership ledger & territory locks" therefore has no schema to lock against. check.py proves the capabilities are disjoint, but that does not prove that write sets are disjoint.
- Evidence: Real multi-team engines enforce module ownership mechanically (CODEOWNERS or Perforce protections, Unreal's module/plugin boundaries, Frostbite's per-team module ownership). Conflicting writes between parallel agents most often happen in shared registration and build files, not inside feature code.
- Proposed change: Add a `modules` field (module or namespace path globs) to every skill in skills.json, and have check.py verify the globs are disjoint. Extend the C-ORCH summary to cover the ledger schema, a shared-file protocol (named integration files have a single owner, program-orchestration or build-system-toolchains, and change only through a CR), and contributor semantics ("contributor = may submit CR and review; never writes owner module"). Add `ARCH.ORG.write-sets` ("Module/file write-set definition & shared-file protocol", owner program-orchestration).

### K-PROD-3 · major · omission
- Target: missing skill/capabilities; api-lifecycle-migration, build-release-architect, engine-architect
- Finding: The engine-as-product concerns have no owner. Missing: intake and triage of bugs and feature requests from game teams; the engine roadmap and prioritization across competing game-team requirements (ARCH.REQ.game-requirements captures requirements but does not prioritize or schedule them); release notes and changelogs; distribution of the engine itself (installer or launcher, prebuilt editor binaries, SDK and headers, source access tiers). BLD.REL.packaging covers game packaging only. Also missing: a corpus of licensee or reference projects used to validate each engine upgrade before release, the security-fix backport process into LTS branches (XC.EXT.lts sets policy but nobody runs backports), and the licensing and terms model for game teams.
- Evidence: Unreal, Unity and every internal engine group (Frostbite and Snowdrop both serve many titles) run an engine-product function: a roadmap, a customer-facing issue tracker, release notes, "upgrade to 5.x" guides, LTS hotfix streams, and a compatibility test farm of customer projects. Without it, engine agents optimize for internal elegance, and shipped games get stranded on old versions.
- Proposed change: Add an orchestrator-tier skill `engine-product-management` (parent engine-architect, profiles all, runtime false) that owns new capabilities `ARCH.PROD.roadmap`, `ARCH.PROD.intake` (game-team bug and feature intake and triage SLAs), `ARCH.PROD.release-notes`, `ARCH.PROD.customer-corpus` (upgrade validation against reference and licensee projects, contributor api-lifecycle-migration and functional-automation-soak) and `ARCH.PROD.licensing-model`. Add `BLD.REL.engine-distribution` ("Engine SDK/editor binary distribution & installers", owner packaging-release-patching). Add `BLD.CI.backports` ("LTS backport/hotfix streams", owner build-release-architect). Give it a process contract `C-PROD` (roadmap priorities consumed by program-orchestration's decomposition).

### K-PROD-4 · major · wrong-owner
- Target: XC.DX.samples, developer-experience-docs
- Finding: The sample-project ladder (2D → open-world online) is described as doubling as the engine's integration tests. It is owned by a technical-writing and DX skill. The top rungs of that ladder, an open-world online sample and an AAA sample, are full game productions. They are the engine's real proof of shippability, and they need game-development expertise across content, design and online operation. They also have to drive milestone exit criteria (K-PROD-1). A documentation agent cannot own them, and owning them puts the de facto integration vehicle outside both program-orchestration and test-architect.
- Evidence: Engines are validated by dogfood titles built by dedicated game teams, not by their docs team: Fortnite for UE5, Battlefield for Frostbite, The Division for Snowdrop, Unity's Megacity and Spaceship demos from dedicated demo teams. Samples written for teaching and reference games written for validation have different goals.
- Proposed change: Split XC.DX.samples. `XC.DX.samples` stays with developer-experience-docs as small, teaching-oriented samples. Add a new expert skill `reference-games` (parent program-orchestration or test-architect, profiles all) owning `QA.REF.ladder` ("Reference game ladder per configuration used as milestone and release gate"), `QA.REF.content` ("Representative production-scale content sets") and `QA.REF.playtest` ("Internal playtest and dogfood loop"), with contributors from each domain lead. PRF.BENCH.workloads should consume these rather than build separate scenes.

### K-PROD-5 · major · omission
- Target: gameplay-systems-toolkit, gameplay-architect, world-editor-viewport, audio-content-runtime, ED.*
- Finding: Designers, writers and level designers have no authoring path for their core daily artifacts. Missing: (a) gameplay data definitions such as data tables, curve tables, data assets or definitions and spreadsheet round-trip, the primary surface for balancing; (b) narrative, dialogue and quest authoring (branching dialogue, quest and objective state, Ink/Yarn/articy-class integration); AUD.CONTENT.dialogue is VO playback only; (c) greybox or blockout geometry modeling in-editor (CSG and ProBuilder-class) for pre-production level design; (d) 2D authoring: sprite slicing and atlasing, tile palettes, auto-tiling rules, a 2D level editor. RND.2D.tilemaps is runtime-only. The indie-2d configuration instead pulls in world-editor-viewport, whose territory is 3D gizmos and partitioned worlds. The crosscutting "tooling" obligation asks each skill to "declare authoring path", but these artifacts belong to no runtime skill, so nobody declares them.
- Evidence: UE DataTables/DataAssets and Unity ScriptableObjects are what designers use most. Unity's 2D Tilemap/Sprite Editor and Godot's TileSet editor are table stakes for 2D. UE Modeling Mode and ProBuilder exist because greyboxing sits on the pre-production critical path. Quest and dialogue systems are rebuilt ad hoc by every RPG team when the engine lacks them.
- Proposed change: Add `GAM.SYS.data-tables` ("Designer data definitions, curve tables, spreadsheet import/export, live-tunable", owner gameplay-systems-toolkit). Add `GAM.SYS.narrative` ("Dialogue, quest & objective framework with narrative-tool interchange", owner gameplay-systems-toolkit, contributors audio-content-runtime, localization-i18n). Add `ED.WORLD.blockout` ("Greybox/blockout modeling", owner world-editor-viewport). Add `ED.2D.authoring` ("Sprite slicing/atlas, tile palettes, auto-tiling, 2D level editing", owner a new expert `editor-2d-tools`, or render-2d-vector as format owner with world-editor-viewport hosting). Make the 2D editing path part of the indie-2d configuration in place of the 3D-centric viewport where possible.

### K-PROD-6 · major · omission
- Target: PLAT.SVC.remote-config, OBS.LOG.telemetry, BLD.REL.*, platform-online-services, observability-telemetry
- Finding: Live operations are covered only as fragments: remote config, telemetry, patching and rollback. Missing: (a) live events and time-gated or scheduled content activation (seasons, limited-time modes) without a client patch; (b) A/B experiment assignment and exposure logging; (c) a gameplay analytics event schema and taxonomy, as distinct from engine performance telemetry, with privacy classification; (d) server-driven data hotfixes to balance data (ties to K-PROD-5 data tables); (e) staged or canary rollout and kill switches as release capabilities; (f) player bug and feedback reporting from inside the game (state, log and screenshot capture to a ticketing boundary); (g) incident response hooks for live services (server-side forced-update and maintenance-mode messaging). OBS.LOG.telemetry lumps development tracing and live player analytics under one low-level instrumentation owner, but those are different data, retention, consent and expertise.
- Evidence: Fortnite, Destiny, Genshin-class and mobile F2P titles run on engine-side support for scheduled content, experiments, analytics taxonomies and data-only hotfixes. Unity (Remote Config, Analytics, Game Overrides), PlayFab and GameAnalytics show where the engine-side integration boundary sits. The mission explicitly calls for "future AAA online" titles.
- Proposed change: Add an area `LIVE` (or extend PLAT.SVC) with `LIVE.events` ("Scheduled/time-gated content activation", owner platform-online-services, contributor package-formats-vfs), `LIVE.experiments` ("A/B assignment & exposure logging", owner platform-online-services), `LIVE.analytics` ("Gameplay analytics event schema, taxonomy & privacy classes", owner observability-telemetry, contributor security-engineering), `LIVE.data-hotfix` ("Server-delivered data overrides for tunables", owner gameplay-systems-toolkit, consumes C-SVC and C-CFG), `LIVE.feedback` ("In-game bug/feedback capture boundary", owner crash-diagnostics), and `BLD.REL.staged-rollout` ("Canary/staged rollout & kill switches", owner packaging-release-patching). Give these capabilities to the `online` add-on profile.

### K-PROD-7 · major · omission
- Target: build-release-architect, ci-cd-automation, collaboration-version-control, BLD.CI.branching
- Finding: The late lifecycle phases have no owner: alpha, beta, content lock, certification submission, launch and day-one patch, post-launch hotfix streams, and sunset or end-of-service. Specifically missing: (a) archival of shipped builds and the ability to rebuild them years later, including a pinned toolchain, pinned console SDK versions, and a snapshot of cooked data, DDC and symbols (XC.SEC.supply-chain covers reproducibility for security, not multi-year rebuild); (b) end-of-service handling: offline-mode or server-sunset patches and graceful degradation when online services are removed, which is now a legal and consumer-protection expectation in several regions; (c) content lock and branch-stabilization policies for a title's release branch as distinct from the engine's release branch.
- Evidence: Studios routinely need to rebuild a title for a re-release, a cert-driven patch or a remaster years later, and failures there are well known (lost toolchains, expired SDKs). The "Stop Killing Games" pressure in the EU and The Crew shutdown show end-of-service is a real requirement. Console first parties require patchability for the whole support window.
- Proposed change: Add `BLD.REL.archival` ("Shipped-build archival & long-term rebuildability", owner build-release-architect, contributors build-system-toolchains, platform-console, crash-diagnostics). Add `BLD.REL.end-of-service` ("End-of-service/offline-mode transition", owner packaging-release-patching, contributors platform-online-services, network-architect). Add `BLD.CI.title-branching` ("Title release-branch stabilization, content lock & hotfix streams", owner build-release-architect). Add a release-readiness capability `QA.STRAT.release-criteria` ("Ship/launch gate: crash-free rate, perf gates, cert prechecks, known-issue list", owner test-architect) and reference it from critic stage S4.

### K-PROD-8 · major · scale-down
- Target: skills.json configurations/profiles, program-orchestration, architecture-governance, docs/00 §5
- Finding: Scale-down is modeled only as runtime skill inclusion, and even that is blurred. indie-2d contains 87 of 124 skills, including research-evidence, architecture-governance, four performance experts, certification-compliance and collaboration-version-control, and the principles document admits this. There is no organizational scale-down. Nothing defines which skills one agent can host together when running a small effort, and nothing defines a lightweight governance tier. Every emerging technique needs an ADR with evidence, every change goes through the CR protocol, and every critic stage runs. The result is that the framework cannot be staffed economically for an indie-scale engine build, or during bootstrap when only a few agents are active.
- Evidence: Small engines (Godot, Bevy, Defold) succeed with a handful of maintainers who each span many domains, and with lightweight RFC processes. Process weight has to scale with team size just as runtime weight scales with configuration.
- Proposed change: Add `ARCH.ORG.staffing` ("Agent staffing tiers: which skills may be co-hosted by one agent per org scale", owner program-orchestration). Add a `host_group` field to skills.json for solo, small and large tiers, for example "core-runtime-* co-hosted" or "all perf experts co-hosted by performance-architect". Add `ARCH.GOV.process-tiers` ("Governance weight per org tier: which ADR/CR/critic stages are mandatory", owner architecture-governance). Report runtime-skill membership separately from process-skill membership in the configuration matrix so runtime scale-down becomes measurable.

### K-PROD-9 · major · scale-down
- Target: CNT.COOK.distributed, CNT.COOK.ddc, ED.COLLAB.multiuser, ED.COLLAB.locking, BLD.CI.farm, BLD.SYS.caching, capabilities.json schema
- Finding: Profiles are tagged per skill, never per capability. Including collaboration-version-control, content-pipeline-architect or ci-cd-automation in indie-2d therefore pulls in, with no stated alternative, AAA-scale production infrastructure: distributed cooking, a shared DDC server, Perforce-class locking, multi-user concurrent editing, a build farm and a device farm. ### K-PROD-10 · major · omission
- Target: content-creator workflows; ci-cd-automation, collaboration-version-control, editor-architect
- Finding: Content creators are not first-class in how builds are distributed and how they sync. Missing: distribution of precompiled editor and tool binaries to non-engineers, so artists and designers never compile, synced to a known-good changelist (UnrealGameSync class). Also missing: build distribution to QA, playtesters and devkits (TestFlight-, Play-internal- and devkit-push class), and a per-discipline workflow owner. No capability or critic check covers the animator loop (DCC → import → retarget → preview in context), the sound designer loop (middleware ↔ in-game audition), or the lighting-artist loop (bake times, preview fidelity). XC.ITER.metrics measures edit-to-see latency but no one owns discipline workflows end to end.
- Evidence: At AAA scale, content staff far outnumber engineers. UGS, Horde and Unity Accelerator exist because content staff stuck on broken or compiling builds is the largest productivity sink in production. GDC production postmortems repeatedly name iteration and sync time as the top content-team pain.
- Proposed change: Add `BLD.CI.binary-distribution` ("Precompiled editor/tool binaries synced to known-good content changelists", owner ci-cd-automation, contributor collaboration-version-control). Add `BLD.CI.build-distribution` ("Internal build distribution to QA/playtest/devkits", owner ci-cd-automation, contributor platform-console). Add `ED.ARCH.discipline-workflows` ("Per-discipline end-to-end workflow specs and iteration targets for artists, animators, designers, sound, lighting, writers, QA", owner editor-architect, contributor hot-reload-iteration). Add a K-TOOLS or K-PROD check that each discipline workflow has a measured iteration target.

### K-PROD-11 · major · omission
- Target: platform-console, security-engineering, collaboration-version-control, program-orchestration
- Finding: No capability covers confidentiality of platform code under NDA. Console SDK headers, platform-specific engine code and cert documents may be accessed only by NDA-covered parties, and are normally kept in separate access-controlled repos or modules. The ownership ledger and the agent organization do not model access classes. Any agent could therefore read or write console code, or leak NDA content into public docs, samples or the mod SDK.
- Evidence: Unreal puts console platforms in separately gated platform extensions. Godot and other open engines keep console ports in third-party private forks for exactly this reason. First-party developer agreements require access control over SDK material.
- Proposed change: Add `PLAT.CON.nda-segregation` ("NDA-confidential platform code & docs segregation, access classes", owner platform-console, contributors build-system-toolchains, collaboration-version-control, security-engineering). Add an `access_class` attribute to skills and modules in C-ORCH or the ledger (public, internal, NDA-platform-X), and add a fitness function in ARCH.GOV.fitness that blocks NDA symbols from reaching public API surfaces, docs and the mod SDK.

### K-PROD-12 · major · omission
- Target: QA.CERT.licenses, ED.AI.provenance, content-pipeline-architect (CNT.ID)
- Finding: IP and license tracking covers only third-party code (QA.CERT.licenses and SBOM) and AI-generated content (ED.AI.provenance). Nothing tracks the rights of ordinary content: marketplace or outsourced assets, fonts (embedding and redistribution terms), licensed music (including streamer-safe flags), voice-actor performance rights (which increasingly restrict ML reuse), and photogrammetry and scan rights. Rights are not carried as asset metadata through cook, so a shipping build cannot produce a content-rights manifest, and streamer mode cannot mute licensed tracks.
- Evidence: Titles have been pulled from sale or patched when music licenses expired (for example the Alan Wake delisting and many racing games). SAG-AFTRA's 2024–2025 interactive-media agreement adds AI-reuse consent terms for performances. Font licensing violations are a common audit finding.
- Proposed change: Add `CNT.ID.rights` ("Asset rights/license/provenance metadata propagated through cook to a shipping content-rights manifest", owner content-pipeline-architect, contributors certification-compliance, ai-assisted-authoring). Reframe ED.AI.provenance as a consumer of CNT.ID.rights. Add `AUD.CONTENT.licensed-music` flags (streamer-safe) under audio-content-runtime, consuming the same metadata.

### K-PROD-13 · major · other
- Target: engine-architect, program-orchestration, render-architect, ARCH.STRUCT.arbitration
- Finding: The coordination topology will not hold at 124 agents. engine-architect has 28 direct children and is the only arbiter of every cross-domain dispute. program-orchestration has no children and alone decomposes and schedules work for 124 skills. render-architect has 18 direct experts with no intermediate grouping, which is the largest integration surface in the engine (all share C-RG, C-RSCENE and C-SHADER). There is no delegated arbitration and no escalation SLA, so either the root becomes a serial bottleneck or disputes get resolved informally, which defeats the ledger.
- Evidence: Large engine organizations use a two-level structure: engine-wide technical director → area leads (runtime foundations, rendering, simulation, content/tools, online, platform/release) → teams. Rendering in UE5, Frostbite and Decima is usually split into sub-leads for GPU infrastructure (RHI, graph, memory, shaders), scene and lighting, and features. Span-of-control limits apply even more strongly to LLM agents, whose context must hold every contract they arbitrate.
- Proposed change: Add a `workstream` field to skills.json (foundation, rendering-infra, rendering-features, simulation, content-tools, online-platform, process). Name a workstream integrator for each (the existing lead). Restrict ARCH.STRUCT.arbitration at engine-architect to cross-workstream disputes, and add `ARCH.ORG.escalation` ("Escalation tiers & decision SLAs", owner program-orchestration). Consider splitting render-architect's subtree with a `render-infrastructure` sub-lead over rhi-core, gpu-memory-resources, render-graph-scheduling and shader-system.

### K-PROD-14 · major · omission
- Target: C-ORCH, ARCH.STRUCT.build-buy, AUD.ARCH.middleware, PHY.ARCH.build-integrate, PLAT.CON.devkit
- Finding: The framework assumes agents can carry out every decision. It has no human decision points for actions agents legally or practically cannot take: signing middleware and platform licenses and NDAs, purchasing (Wwise/FMOD-, Havok- or Bink-class licenses, devkits, cloud build capacity), first-party developer-program enrollment and cert submission, rating-board submissions, and legal sign-off on privacy or license findings. Build/buy decisions sit with engine-architect with no approver or budget owner.
- Evidence: Every one of these is a contractual act with a counterparty (Sony, Microsoft, Nintendo, Audiokinetic, ESRB/PEGI/IARC). An autonomous framework that does not name its human gates will either stall silently or plan work on SDKs it has no access to.
- Proposed change: Add `ARCH.ORG.human-gates` ("Register of decisions requiring human authorization: contracts, spend, NDA access, submissions, legal sign-off; with blocking semantics in the task graph", owner program-orchestration, contributors engine-architect, certification-compliance). Extend C-ORCH to cover "human-gate tasks". Mark ARCH.STRUCT.build-buy, PLAT.CON.devkit, BLD.REL.submission, QA.CERT.ratings and QA.CERT.privacy as gated.

### K-PROD-15 · minor · omission
- Target: program-orchestration, ARCH.EVID.spike, ARCH.GOV.adr
- Finding: There is no program risk register. ADR revisit conditions cover technical reversibility of individual decisions. Nothing tracks schedule and dependency risk: a middleware vendor or platform SDK changing, first-party requirement updates, a critical-path skill blocked, or an emerging technique adopted without a fallback milestone. Spikes are not tied to front-loading the highest risks in the milestone ladder.
- Evidence: Standard production practice (risk-driven spiral scheduling, "find the fun and the risk first" in pre-production) front-loads risky technical bets such as a virtualized geometry or netcode model into early prototypes.
- Proposed change: Add `ARCH.ORG.risk` ("Program risk register, risk-driven milestone ordering, spike scheduling", owner program-orchestration, contributor research-evidence). Require every emerging-maturity ADR to register a risk with its fallback milestone.

### K-PROD-16 · minor · missing-contract
- Target: PLAT.SVC.remote-config, CORE.LIFE.config, C-CFG, C-SVC, platform-online-services
- Finding: Remote configuration and feature flags (platform-online-services) and layered config and cvars (core-runtime-architect) are two independent owners with no contract edge. platform-online-services does not consume C-CFG, and C-CFG's summary does not include a remote source layer or precedence. The live-tuning path, meaning which of shipped defaults, device profile, remote override and user settings wins and when changes apply mid-session, has no owner.
- Evidence: Mis-layered remote overrides are a classic live-ops incident class (flags applied mid-match or overriding user accessibility settings).
- Proposed change: Add a "remote/live source layer & precedence rules" clause to C-CFG, add `C-CFG` to platform-online-services.consumes, and record PLAT.SVC.remote-config as a contributor to CORE.LIFE.config.

### K-PROD-17 · minor · wrong-owner
- Target: gameplay-architect.non_responsibilities, platform-online-services.non_responsibilities
- Finding: Out-of-scope territory is pointed at engine-architect: "Game-specific code (the game team)" and "Backend implementation (outside engine scope)". This makes the chief architect the nominal owner of game code and backend code, so agents that treat non-responsibility targets as a routing table will send game-team and backend work to the root architect. The game team, the actual customer of the engine, is not represented as an external party with an interface.
- Evidence: Non-responsibilities exist, per the principles doc, to route work correctly between overlapping agents. A root-architect sink breaks that routing.
- Proposed change: Introduce an explicit `external:game-team` and `external:backend` pseudo-owner that check.py accepts only in non_responsibilities. Route game-team interaction through engine-product-management (K-PROD-3).
