# K-TOOLS round 4 findings

### K-TOOLS-1 · major · dependency-error
- Target: C-EDHOST, C-EDVIEW, ED.UI.asset-editor-host, ED.WORLD.preview-scenes; skills material-system, animation-runtime, animation-graphs, facial-animation, character-rendering, vfx-particles, cloth-deformables, motion-synthesis, cinematics-sequencer, ik-procedural-animation, virtualized-geometry-lod, vehicle-physics, character-physics, fluid-simulation
- Finding: Preview-world creation is exposed through C-EDVIEW (ED.WORLD.preview-scenes, world-editor-viewport), while C-EDHOST's summary says asset editors embed preview worlds "from C-EDVIEW". But C-EDHOST requires only C-EDCMD, editor-ui-framework does not consume C-EDVIEW (and cannot: world-editor-viewport consumes C-EDHOST, so it would be a cycle), and the ~14 skills above own asset editors with 3D preview and hold tool_consumes of only C-EDCMD/C-EDHOST(/C-COOK/C-GRAPH). check.py only demands C-EDVIEW for world tools, so nothing catches it. Asset editors have no legal way to create a preview world, orbit camera, picking or gizmos.
- Evidence: skills.json tool_consumes; contracts.json C-EDHOST/C-EDVIEW summaries. Precedent: Unreal's FAdvancedPreviewScene / SEditorViewport and Unity's PreviewRenderUtility are a layer below both the level editor and the asset-editor toolkit.
- Proposed change: split a small L5 contract C-EDPREVIEW (preview world lifetime, orbit/turntable viewport widget, picking, basic gizmos), owned by world-editor-viewport, requiring only C-EDCMD; C-EDHOST embeds panels supplied by it (world-editor-viewport stops consuming C-EDHOST for that path, or C-EDHOST consumes C-EDPREVIEW), and add it to tool_consumes of every skill with a previewing asset editor. Add a check: any skill owning a *.TOOL capability whose name contains preview/viewport/editor of a spatial asset must reach C-EDPREVIEW/C-EDVIEW.

### K-TOOLS-2 · major · missing-contract
- Target: asset-import-interchange, CNT.IMP.* (fbx, gltf, usd, textures, audio, materialx, reimport, rules, dcc-plugins, livelink, caches, scans), C-COOK, C-ASSET
- Finding: No contract mentions import. asset-import-interchange provides nothing and consumes only C-ASSET and C-COOK, and every CNT.IMP.* capability has empty contributors. Yet one FBX/glTF/USD file must yield domain assets owned by other skills: skeletal mesh, skeleton and clips (animation-runtime), materials (material-system), collision/physics assets (physics-tools), cluster/LOD settings (virtualized-geometry-lod), audio import settings, sockets, morph targets. Nothing defines importer registration, the import-settings schema (reflected, per asset type, stored for reimport), the domain asset factory hook, reimport merge that preserves user overrides, headless batch import, or the versioned interchange schema that external DCC plugins (CNT.IMP.dcc-plugins, out-of-tree code) target. The "format owner owns the builder" pattern is silently inverted: one agent owns import for every domain format.
- Evidence: Unreal (UFactory/reimport handlers), Unity (ScriptedImporter with per-asset importer settings and dependency registration), Godot (EditorImportPlugin), Bevy asset loaders/processors all expose a registered importer contract; domain teams own their importers.
- Proposed change: add contract C-IMPORT (L5, owner asset-import-interchange, requires C-ASSET, C-SER, C-COOK, oracle author distinct from the owner, fuzz target on the interchange schema): importer/exporter registration by domain skills, import-settings schema and reimport-preserve rules, domain asset-factory hook, batch/headless entry, interchange schema version. Domain skills that own imported asset types (animation-runtime, material-system, audio-content-runtime, virtualized-geometry-lod, physics-tools, ui/localization) become contributors of the relevant CNT.IMP.* capabilities and implement importers through it. Also route import UI through C-EDHOST and undo through C-EDCMD (asset-import-interchange tool_consumes currently has neither).

### K-TOOLS-3 · major · dependency-error
- Target: milestones M0-M3 (contracts_draft/contracts_frozen), C-EDCMD, C-EDHOST, C-EDVIEW, C-GRAPH, C-VCS; skills in M0/M1 owning *.TOOL capabilities
- Finding: The tool contracts are drafted at M2 and frozen at M3, but the skills that own the tool halves of domains arrive earlier: material-system, post-color-hdr, render-2d-vector (tilemap/sprite editor), texture-streaming-vt, input-system in M0; animation-graphs, animation-runtime, cinematics-sequencer, ui-architect (UI designer), gameplay-data, ai-behavior-perception, scripting-runtime, localization-i18n, world-data-model (prefabs) in M1. Their tool_consumes name C-EDCMD/C-EDHOST/C-GRAPH before any of them exists. The milestone closure proof only covers configurations claimed by then (M0/M1 claim only client targets), so the tool halves of ~40 skills are built with no frozen host, and the M1 "indie-2d and minimal reference games" are authored with no editor at all. Domain asset formats (undo granularity, diffable/mergeable text layout, reflected property metadata, override models) are then fixed before the editability contract that constrains them; this contradicts "tooling as thorough as runtime" and the design rule that instrumentation exists before features.
- Evidence: milestones.json M0-M3 lists; skills.json tool_consumes. Precedent: Unreal's transaction and property-editor systems were retrofitted onto UObject serialization and still constrain formats; Godot and Unity designed the inspector/undo model together with the first serialized formats.
- Proposed change: draft C-EDCMD, C-EDHOST, C-GRAPH and C-VCS at M0 (walking skeleton includes a reflection-driven inspector, command journal and a headless commandlet over C-CMD) and freeze C-EDCMD/C-EDHOST at M1 before domain tools start; move minimal editor-architect/editor-ui-framework into M1 with an 'indie-2d-tools-min' configuration claimed at M1; add a check: a skill that owns *.TOOL capabilities may not be scheduled before its tool_consumes contracts are drafted, and a contract frozen after its first tool consumer is scheduled is an error.

### K-TOOLS-4 · minor · overlap
- Target: RND.GI.bake-pipeline, WLD.PART.hlod, PHY.TOOL.fluids (cache baking), AUD.TOOL.acoustics (propagation baking), GAM.AI.navmesh vs CNT.COOK.world-build, CNT.COOK.distributed, CNT.COOK.architecture
- Finding: "Incremental/distributed lighting bake orchestration" (global-illumination) and "HLOD generation orchestration" (world-architect) restate the region-invalidation, distributed-bake and staleness graph that CNT.COOK.world-build owns; fluid, acoustics and navmesh bakes have no stated hookup. Each domain will invent its own scheduler, cache keys and staleness UI, and world-build cannot prove incremental equals clean for bakes it does not control.
- Evidence: framework's own pattern "format owner vs pipeline host" (docs/00 section 4); Unreal World Partition builders and Unity's incremental Progressive Lightmapper both had separate bake queues that later had to be unified under one build graph.
- Proposed change: reword RND.GI.bake-pipeline, WLD.PART.hlod to "bake/builder implementations as C-COOK world-scope processors (algorithm, sampling, seam handling); orchestration, invalidation, distribution and staleness are CNT.COOK.world-build"; list the same rule on the fluid, acoustics and navmesh bake capabilities and make those owners contributors of CNT.COOK.world-build.

### K-TOOLS-5 · minor · scale-down
- Target: configurations minimal-tools, indie-2d-tools, fighting-2d-rollback-tools; skills world-editor-viewport, graph-editor-framework, collaboration-version-control, ci-cd-automation, editor-*
- Finding: There is no tools configuration without the editor. minimal-tools (card/narrative games with no world) still contains world-editor-viewport, graph-editor-framework, collaboration-version-control and ci-cd-automation because all are profile 'all', and there is no code-first/CLI-only tool configuration (cook + build + validate via commandlets, hand-edited text assets), which is how small Bevy/Godot-headless/custom-engine teams work. Tool scale-down is only proved as "closed", not as "editor optional".
- Evidence: minimal-tools membership = 10 tool skills incl. all editor skills; ED.ARCH.headless exists but no configuration proves it stands alone.
- Proposed change: add configuration minimal-cli-tools (target tools, no editor-architect/editor-ui-framework/world-editor-viewport/graph-editor-framework/collaboration-version-control) closed over C-COOK/C-BUILD/C-PKG/C-AUTOMATION, claimed at M1; retag world-editor-viewport to exclude 'minimal', and require ED.ARCH.headless to be the only editor dependency of import/cook tool paths.

### K-TOOLS-6 · minor · scale-down
- Target: CNT.COOK.shared-cache (profiles lite3d, std3d), ED.COLLAB.multiuser/session-server (team-mid, team-large), CNT.COOK.distributed (team-large)
- Finding: Team-size features are gated on the wrong axis in one place: the team/cloud derived-data cache is tagged with base profiles lite3d/std3d instead of team-mid/team-large. A 30-person 2D studio (min2d + team-mid) gets no shared DDC while a solo 3D developer is assigned "team/cloud DDC deployment & health". The same base-profile mix means the 2D and minimal ladders have no path from 3 to 100 people for cook caching.
- Evidence: capabilities.json profile tags; docs/00 section 5 states team scale is a separate add-on axis.
- Proposed change: retag CNT.COOK.shared-cache to ['team-mid','team-large'] and add a local-only DDC capability (all profiles) so CNT.COOK.ddc covers solo use; add a check that no capability with a team-size name (team, shared, fleet, multi-user, distributed) carries only base-profile tags.

### K-TOOLS-7 · minor · omission
- Target: direct-lighting-shadows, RND.TOOL.lighting, RND.TOOL.* (none for direct lights); AUTHORING_WORKSTREAMS in check.py
- Finding: The rendering workstream is exempt from the authoring-path check, and direct lighting has no authoring capability: RND.TOOL.lighting covers probes, captures, scenarios and density visualization only. Light placement and units, IES/cookie profiles, light functions, shadow-budget and light-complexity overlays, lighting-only/unlit viewmodes and per-light bake mode have no owner (RND.ARCH.debug-modes is a runtime buffer view, not authoring).
- Evidence: every mainstream editor ships light-authoring with complexity viewmodes (Unreal light complexity/shader complexity view modes, Unity light explorer).
- Proposed change: add RND.TOOL.direct-lights (owner direct-lighting-shadows, contributors world-editor-viewport, global-illumination) and add 'rendering' to AUTHORING_WORKSTREAMS so any render skill that authors user-visible content needs a TOOL capability or an 'authoring' note.

### K-TOOLS-8 · minor · omission
- Target: persistence-save (authoring note), platform-web (authoring note), ED.DEBUG.inspector, GAM.SAVE.*
- Finding: persistence-save's exemption says "save inspection via visual-debugging-tools", but no capability there (ED.DEBUG.inspector is a runtime entity inspector) covers save-file inspect, edit, diff, migration dry-run or corruption/cloud-conflict repro. platform-web's exemption says web preview is "the standard editor play mode", yet editor PIE runs native and cannot expose WASM, WebGPU-limit, memory-cap or threading (COOP/COEP) failures; only on-device/browser deploy via C-TARGETPLAT does.
- Evidence: authoring notes in skills.json vs capability list; QA.FUNC.compat-corpus tests migrations but offers no designer/QA tool.
- Proposed change: add GAM.TOOL.save-inspector (owner persistence-save: inspect/edit/diff/upgrade-dry-run, built on C-SAVE and CORE.SER.evolution) and change platform-web's note to name C-TARGETPLAT deploy-to-browser plus a web tier in RND.TOOL.scalability-preview.

### K-TOOLS-9 · minor · omission
- Target: editor-ui-framework, editor-architect, CORE.LIFE.config, C-CFG, untrusted input config-layers
- Finding: No capability owns the editor-side surfaces of configuration: the schema-driven project-settings editor (layered per-platform/per-build config from C-CFG, with validation and diff), editor preferences, layout/workspace persistence, keybinding and command-palette/search-everywhere. ED.UI.toolkit covers docking/panels only. The C-CFG layers are untrusted input (config-layers) but their authoring UI is unowned, so every domain will invent its own settings panel.
- Evidence: capability search finds no project-settings, shortcut, keybinding, command-palette or workspace capability in ED.*; Unreal Project Settings/Editor Preferences, Unity Project Settings/Preferences/Shortcut Manager, Godot Project Settings/Editor Settings are core, shared editor services.
- Proposed change: add ED.UI.settings-editor (reflection-driven over C-CFG, per-platform layers, diff/validate) and ED.UI.workspace (layouts, keybindings, command palette, preferences persistence) to editor-ui-framework; domain tools register commands and settings through C-EDHOST.

### K-TOOLS-10 · minor · omission
- Target: untrusted-inputs.json; GAM.DATA.spreadsheets, ED.UI.tabular, UI.TOOL.localization, GAM.TOOL.dialogue, ED.COLLAB.codev, ED.COLLAB.production-tracking, AUD.CONTENT.authoring
- Finding: Tool-side parsers of vendor- or partner-supplied files are not registered: spreadsheet/CSV/XLSX round-trip (zip bombs, XXE, formula injection on export), localization exchange (XLIFF/PO/TMS drops), screenplay/narrative-tool import, audio-middleware bank/project imports, vendor delivery packages (ED.COLLAB.codev), and production-tracker webhooks. imported-dcc-files covers DCC geometry only; assets covers cooked/serialized data. check.py's registry proof therefore cannot force fuzz targets or limits for them.
- Evidence: untrusted-inputs.json ids; the entries above name external file/format sources in capabilities.
- Proposed change: add inputs tabular-imports (owner editor-ui-framework or gameplay-data), localization-exchange (localization-i18n), narrative-imports (narrative-dialogue), vendor-deliveries (collaboration-version-control, validated at CNT.VAL.submit-gate), tracker-webhooks (collaboration-version-control), each with parser owner, fuzz target and size/depth limits.

### K-TOOLS-11 · minor · wrong-boundary
- Target: world-editor-viewport (ED.WORLD.blockout, ED.WORLD.mesh-paint, ED.WORLD.partitioned, ED.WORLD.2d-mode, ED.WORLD.color-management), ED.COLLAB.binaries, ED.COLLAB.partial-sync, BLD.CI.binary-distribution
- Finding: (a) One skill (12 capabilities) declares three literatures, "3D manipulation UX", "large-world editing" and "mesh editing/geometry processing", and provides C-EDVIEW on which ~25 domain tools depend, so an agent doing half-edge modeling and paint tools owns the viewport contract's change queue. (b) Large binary storage strategy (ED.COLLAB.binaries) sits in ci-cd-automation while the VCS choice (B15), locking and sparse workspaces sit in collaboration-version-control; the depot layout cannot be decided apart from binary storage, and binary-distribution/shared-cache also touch it.
- Evidence: skills.json expertise fields and non_responsibilities; docs/00 section 1 split rule (different literatures, different change rates).
- Proposed change: move ED.WORLD.blockout and ED.WORLD.mesh-paint into a mesh-editing expert (or asset-cook-processors with CNT.COOK.geometry-ops, which already contributes) consuming C-EDVIEW, leaving world-editor-viewport with viewport, gizmos, placement, partitioned editing and preview scenes; move ED.COLLAB.binaries ownership to collaboration-version-control with ci-cd-automation as contributor.
