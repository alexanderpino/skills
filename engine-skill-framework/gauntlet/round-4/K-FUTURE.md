# K-FUTURE (Future-Technology Critic), round 4

### K-FUTURE-1 · major · missing-contract
- Target: C-GPUTIER, profile `hwrt` (skills.json profiles.addons.hwrt), RND.GI.rt-required, RND.RHI.caps
- Finding: C-GPUTIER expresses hardware capability as a linear ladder of named tiers ("rt", "rt+tensor") and lets a render feature declare "the minimum tier it needs". RT, tensor/matrix, mesh-shader, work-graph and binding capabilities are orthogonal and ship in different combinations. Metal 4 and mobile GPUs offer tensor ops without an "rt" baseline. RDNA-class desktop parts have matrix units and RT without a vendor-neutral tensor API. Current-generation consoles have RT but no tensor units (the profile text calls "RT+tensor" the "console baseline", which is only true of a mid-cycle or next-generation SKU). A single minimum tier cannot say "needs tensor, not RT" or "needs RT, tensor optional".
- Evidence: DXR 1.x with cooperative vectors (SM 6.9), Vulkan cooperative matrix/vector, Metal 4 tensor ops. Each is a separate capability bit with different availability per vendor.
- Proposed change: reword C-GPUTIER so features declare a required capability set (feature bits with API-neutral semantics, versioned limits) and tiers are named bundles for configurations and QA matrices only. Reword the `hwrt` profile to "RT required, tensor required only where a feature declares it" and remove "console baseline". Add a contract sentence that no contract text names a concrete API limit (for example a SM version) as a tier definition; API mappings live in `RND.RHI.caps` data.

### K-FUTURE-2 · major · maturity-error
- Target: data/radar.json (all entries), scripts/check.py radar rules, ARCH.GOV.radar
- Finding: radar evidence and triggers are time-relative prose with no as-of date, source citation or review stamp ("preview", "beta", "no shipped titles", "2025", "Two shipped titles"). Maturity labels are claimed to be "honest against production evidence", but nothing lets a critic or check.py detect a stale label. Several will flip within months: cooperative vectors and SM 6.9 are marked "preview" and work-graph "no shipped titles". Nothing forces re-evaluation before the milestone-exit review, and a label that is correct today silently becomes wrong. The radar is also the mechanism that unlocks profile retagging, so staleness has downstream cost.
- Evidence: Radar entries such as RND.SHADER.autodiff ("SM 6.9 cooperative vectors (preview)") and RND.GEO.mesh-nodes ("no shipped titles") have no dates. Promotion and demotion are only checked at milestone exit.
- Proposed change: add required fields `reviewed` (ISO date), `evidence_refs` (list of dated, typed sources per the T1–T6 tiers in docs/06) and `max_age_days` per class (for example X/S 180, M 365). Make check.py fail an entry whose review is older than its max age relative to the milestone date. Add `promotion_signal` as a testable predicate (named shipped-title count, API status) rather than free prose.

### K-FUTURE-3 · major · omission
- Target: PLAT.PAL.cloud-streaming, PLAT.PAL.cloud-hybrid, skills.json target/platform axes, radar
- Finding: streaming-first delivery is modelled only from the perspective of a build that is being streamed (session detection, touch overlay, UI scale). The engine-as-cloud-render-host case has no owner or radar entry. That case means a headless-with-GPU target that renders without a display, captures presented frames, hardware-encodes them at low latency (AV1/HEVC), runs a WebRTC or QUIC video and input back-channel, and packs several instances or tenants on one GPU or partition. `headless-client` exists as a bot target without rendering, `PLAT.SVC.capture` is clip export, and `RND.GPU.hetero-offload` only mentions encode on a second adapter. Interactive pixel streaming is already used for enterprise, digital-twin and cloud-play products, and it is where server-side rendering meets the existing `C-PRESENT` interposer model.
- Evidence: Unreal Pixel Streaming, NVIDIA CloudXR and GeForce NOW-style hosts, Omniverse streaming. Low-latency encode is an established path (NVENC/AMF/VideoToolbox SDKs).
- Proposed change: add a capability `PLAT.PAL.cloud-render-host` (owner platform-architect, M, contributors frame-orchestration, gpu-platform-architect, network-transport, input-system) plus a radar entry (M, evidence Pixel Streaming and CloudXR, trigger "second engine ships multi-tenant host", fallback "client build streamed by a third-party host"). Add a `cloud-render-host` value to the platform axis or a target flag, and a radar note that interposed presenters in `C-PRESENT` include an encoder sink.

### K-FUTURE-4 · minor · maturity-error
- Target: RND.GEO.splats (M), CNT.IMP.splats (X), RND.GEO.splat-relight (X), radar entries for splats
- Finding: the three splat entries repeat identical evidence but carry different classes. Rendering static splats is M and its import is X, so a required content path exists in a lower class than its consumer. The M label for rendering rests on research citations (Kerbl 2023, 3DGRT) and an unstandardized glTF extension. It does not rest on shipped-game evidence. The radar's own X entries (neural texture compression, work graphs) require shipped titles for promotion, so M for splats applies a weaker bar.
- Evidence: the only radar evidence is research papers and a format draft; the fallback is "photogrammetry meshes".
- Proposed change: retag RND.GEO.splats to X (profile `experimental`) or split it into capture-viewer (M) and gameplay-renderer (X). Set CNT.IMP.splats and RND.GEO.splats to the same class with a single radar entry, or write in the radar why they differ.

### K-FUTURE-5 · minor · maturity-error
- Target: NET.ARCH.meshing (M), PLAT.PAL.cloud-hybrid (X), profile `persistent-world`
- Finding: seamless server meshing is labelled M on the evidence of one live deployment with sparse technical publication (docs/06 A5 says so). Split client/cloud compute is labelled X on the evidence of one shipped title (Crackdown 3). The bars are inconsistent. If one live title is enough for M, cloud-hybrid is at least M. If technical postmortems are required, meshing is X. Because meshing is bundled into the `persistent-world` profile, a shipping configuration inherits an unproven capability.
- Evidence: radar `NET.ARCH.meshing` revisit "Two shipped-title technical postmortems", which is the promotion bar for the label the entry already holds.
- Proposed change: move NET.ARCH.meshing to X and put it in `experimental`, keeping zoning (NET.SRV.zoning) as the required capability of `persistent-world`. Or state one written rule in radar `_doc` mapping evidence to class (M requires a published postmortem or two independent shipped uses) and apply it to both entries.

### K-FUTURE-6 · minor · obsolete-assumption
- Target: L73, RND.RECON.upscalers, RND.RECON.ml-denoise, profile `hwrt`
- Finding: L73 states that upscaling and frame generation are "an optional presentation layer". That is right for frame generation. Upscaling is not optional on the tiers this framework itself defines: real-time path tracing and console 4K targets are budgeted at internal resolution with reconstruction as part of the pipeline. The `hwrt` profile drops the raster fallback while ray reconstruction (M, fallback "spatiotemporal denoiser") is the only denoiser-quality path within budget. As written, a `hwrt` budget could pass without any upscaler, or an ADR could be forced to hide a mandatory dependency behind "optional".
- Evidence: shipped path-traced titles and console performance modes are designed around internal resolution plus temporal upscaling.
- Proposed change: split L73. Frame generation stays optional and is never counted toward latency or simulation budgets. Upscaling is a declared budget input per tier ("internal-resolution budget at base rate R with reconstruction mode Q"), required where the tier declares it. Add that field to C-BUDGET tier records and make `hwrt` tiers state whether reconstruction is mandatory.

### K-FUTURE-7 · minor · scale-down
- Target: non-goal "GLES / WebGL backends", configuration `indie-2d-*` on web, RND.RHI.webgpu
- Finding: the smallest 2D and card games claim the web platform, yet the web target requires WebGPU-capable browsers only and the WebGL non-goal has no fallback. A 2D sprite renderer needs none of WebGPU. The revisit trigger ("more than 10% of a shipping web audience without WebGPU") can only fire after a title has shipped with no fallback. Older iOS and Android WebViews, and embedded browsers, will lack WebGPU for years.
- Evidence: Safari, Firefox and Chrome WebGPU rollout dates are 2023–2025 with an uneven Linux and Android WebView tail; portal and embedded browsers lag.
- Proposed change: keep WebGL out for `std3d`, but allow a reduced-tier registered backend slot behind C-RHI (or a separate `render-2d-vector` Canvas2D/WebGL2 path) for `minimal` and `min2d` web builds. Alternatively change the trigger to a pre-ship measurement from `PLAT.WEB.audience-share` and set a blocking gate at the web-release milestone.

### K-FUTURE-8 · minor · omission
- Target: ML.RT.*, PLAT.WEB.*, radar
- Finding: browser ML (WebNN, WebGPU-compute inference, WASM SIMD) has no entry. The `ml` profile is limited to `pc`, `console` and `xr-standalone`; the web platform variant cannot use on-device models, so browser-delivered ML NPCs and speech would go cloud-only. Also missing are volumetric or spatial video and light-field or holographic display output as radar S or X entries, which the XR row otherwise covers as "scene, anchors, depth".
- Evidence: WebNN Candidate Recommendation (W3C); ONNX Runtime Web with WebGPU; Apple Spatial Video capture and playback.
- Proposed change: add `ML.RT.web-backends` (M, platform-web, contributed by ml-inference-runtime) with fallback "remote inference via C-LIVE". Add radar S entries "volumetric/spatial video playback" and "light-field/holographic displays" with owners in RND and PLAT.XR.

### K-FUTURE-9 · minor · other
- Target: A11 (docs/06), B29, CORE.LIFE.language, CORE.LIFE.interop, radar memory-safe entries
- Finding: docs/06 A11 limits memory-safe languages to "parsers of untrusted data", while B29 and CORE.LIFE.language admit a mixed-language engine. The radar trigger for memory-safe components is "console toolchain support" alone. Both ignore that this framework's implementers are autonomous agents. Borrow checking and bounds-checking make undefined-behavior classes machine-detectable, so choosing the language is also a verification decision, and this is not recorded as a criterion. The fallback ("hardened C++ plus fuzzing") is presented as equivalent.
- Evidence: Android memory-safety data (Google 2024) attribute the drop in memory-safety vulnerabilities to new code in memory-safe languages; C++ hardening modes (libc++ hardened, bounds-safe subsets) are not equivalent to language-enforced safety.
- Proposed change: reconcile A11 with B29 (the ADR may cover more than parsers); add `agent_verifiability` and `UB-class exposure` as decision criteria for CORE.LIFE.language; add a radar trigger "agent-authored defect data shows memory-safety escapes above threshold in C++ modules".
