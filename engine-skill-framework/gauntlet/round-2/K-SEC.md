# K-SEC · Security Critic · Round 2 findings

Scope reviewed: data/*.json, docs/00, 06, 07, 08, gauntlet/PROTOCOL.md, scripts/check.py (gate is green: 0 errors, 0 warnings).

### K-SEC-1 · major · missing-contract
- Target: C-TRUST, crosscutting "untrusted input", skills.json `untrusted_inputs` / `fuzz_targets`, scripts/check.py, serialization-schema, network-transport, replication, package-formats-vfs, shader-system, modding-ugc, text-fonts, online-services-liveops, ai-behavior-perception
- Finding: The untrusted-input registry is an uncontrolled free-text tag list that no one checks. `check.py` has no rule for `untrusted_inputs` or `fuzz_targets` (grep finds neither in check.py or model.py), even though crosscutting.json says every untrusted input must be registered "with a validating owner and a fuzz target". The 17 tags match the fuzz list only because they were typed in by hand. No entity defines the vocabulary. Several inputs also have more than one "validating owner" with no split of duties: `packets` is on serialization-schema, network-transport and replication. `assets` is on serialization-schema and package-formats-vfs. `saves` is on serialization-schema and persistence-save. `ugc-graphs` is on modding-ugc and shader-system. `chat-text` and `generated-content` are each on two skills. Meanwhile dedicated-server and prediction-rollback both take attacker-controlled client input commands (NET.PRED.input-commands, NET.SRV.auth) and register nothing. Nothing records trust level, sandbox, resource limits or which configurations an input reaches. So "who validates what, in which layer" stays undecided, which is how parse-then-trust bugs get in. In Dark Souls III (CVE-2022-24125/24126), P2P packet parsing led to RCE and PvP servers were taken offline for months.
- Evidence: C-TRUST's summary ("Untrusted inputs list, validation obligations, sandbox rules") names a list that does not exist as data. PROTOCOL.md says structural changes must be "expressed in data, so the next gate checks it", and this rule is not.
- Proposed change: Add `data/untrusted-inputs.json` with one entry per input class: {id, sources, trust tier (hostile-remote / hostile-local / semi-trusted-signed / trusted-first-party), configurations reached, validating_owner (exactly one), parser_owners[], fuzz_harness_owner, resource limits (size, depth, time, memory), sandbox}. In check.py: every skill's `untrusted_inputs` must be a registry id; every registry id must be in robustness-fuzzing `fuzz_targets` and be registered by its validating owner; every validating owner must be a runtime or tool skill in a configuration the input reaches. Add a `--selftest` mutation for each rule. Register `packets` (semantic input commands) on prediction-rollback and dedicated-server.

### K-SEC-2 · major · omission
- Target: untrusted-input vocabulary; audio-dsp-mixing (AUD.DSP.codecs, AUD.DSP.voip), network-transport (NET.TRANS.voice), ml-inference-runtime (ML.RT.packaging), online-services-liveops / platform-services / async-io-storage (RES.IO.remote, PLAT.PAL.process HTTP client), observability-telemetry (OBS.LOG.logging), collaboration-version-control (ED.COLLAB.multiuser), content-pipeline-architect (shared derived-data cache), asset-import-interchange (CNT.IMP.livelink, CNT.IMP.procedural, CNT.IMP.usd)
- Finding: Several attacker-reachable parsers and sinks are neither registered nor fuzzed. (a) Voice-chat codec streams from other players: Opus is decoded by audio-dsp-mixing, and neither skill registers anything. (b) Player-supplied images: avatars, emblems, sprays, UGC thumbnails and photo-mode shares. There is no runtime image-decode owner and no tag. (c) ML model files in DLC, mods or remote delivery (ML.RT.packaging). (d) Backend and CDN responses other than remote config: store catalogs, news/MOTD rich text, matchmaking tickets, leaderboard payloads, RES.IO.remote content. (e) Player-controlled strings that reach the logging, telemetry and crash-annotation substrate: format-string and lookup injection in log sinks. (f) Tools side: multi-user editing session traffic, shared derived-data/cache entries (cache poisoning spreads to every workstation and to CI), DCC live-link sockets, and HDA/USD evaluation, which runs code or resolves arbitrary asset paths and plugins.
- Evidence: libwebp CVE-2023-4863 and libvpx CVE-2023-5217 were image/video decoders exploited in the wild. Log4Shell (CVE-2021-44228) was first exploited at scale by typing a string into Minecraft chat, where the logging substrate was the sink. Autodesk FBX SDK CVE-2020-7080..7085 show DCC SDK parsers are exploitable. ONNX/TFLite model-parser CVEs are recurrent. USD composition can load plugins and resolve external paths.
- Proposed change: Add registry ids `voice-streams` (validating owner audio-dsp-mixing, contributor network-transport), `user-images` (owner: the skill that decodes runtime images, e.g. texture-streaming-vt or a named decode capability; add one if none exists), `ml-models` (ml-inference-runtime), `service-responses` (online-services-liveops, with platform-services and async-io-storage as parser owners), `logged-untrusted-strings` (observability-telemetry: log/trace/crash sinks must treat arguments as data, with no interpolation or lookups), `collab-session`, `shared-ddc` (content-pipeline-architect; entries content-addressed and verified), `dcc-live-link` and `procedural-asset-eval` (asset-import-interchange; sandboxed out-of-process import per XC.SEC.dev-trust). Add all of them to robustness-fuzzing `fuzz_targets`.

### K-SEC-3 · major · omission
- Target: CORE.LIFE.config, C-CFG, platform-desktop, platform-mobile (PLAT.MOB.links), platform-console, XC.SEC.vuln-response
- Finding: Launch arguments, environment variables, OS intents / URL-scheme handlers and the layered config and cvar system are not treated as a trust boundary. CORE.LIFE.config merges "command line, per-platform/device and remote layers with precedence". C-CFG has no trust class per layer and no per-cvar restriction on which layers may set it. In particular, nothing stops remote config or a command-line argument from setting load paths, plugin or module lists, debug ports or script-eval cvars. Only `invites-deep-links` is registered, and only on platform-services.
- Evidence: Unity CVE-2025-59489 (disclosed October 2025). On Android, intent extras reached engine command-line handling and let an attacker load arbitrary native libraries in any Unity game. The same class of issue existed on Windows/macOS through URL handlers. It affected games back to Unity 2017, and Unity had to ship a binary patcher for games that had already shipped. The incident is also a direct precedent for XC.SEC.vuln-response needing a path to titles built and shipped by licensees.
- Proposed change: Add untrusted input `launch-args` (validating owner core-runtime-architect, contributors platform-mobile, platform-desktop and platform-console). Extend C-CFG with a per-layer trust tier and a per-cvar "settable-from" allow-list, so shipping builds reject code-loading or path-type cvars from command-line, intent and remote layers. Add capability CORE.LIFE.config-trust (owner core-runtime-architect, contributor security-engineering). Add a fuzz target for it.

### K-SEC-4 · major · missing-contract
- Target: CORE.TYPES.crypto / C-TYPES (containers-core-types), RES.PKG.crypto, GAM.SAVE.integrity, XC.EXT.plugin-trust, PLAT.SVC.remote-config, BLD.REL.cdn / C-PKG, modding-ugc
- Finding: At least six skills each verify a signature (packages, patches/CDN manifests, saves, plugins, mods, remote config). Yet the only shared runtime crypto is "vetted cryptographic primitives wrapper, CSPRNG" inside containers-core-types. Nobody owns the signed-artifact envelope, trust-root store, key rotation and revocation, crypto agility, or anti-rollback (a monotonic version floor that blocks downgrade to a vulnerable signed build or content). Each consumer would build its own verification path, and a key compromise could not be revoked consistently. Separately, a containers expert is the wrong owner for security-critical crypto integration, and security-engineering is a process skill, so it cannot own the code.
- Evidence: The Microsoft Storm-0558 signing-key misuse in 2023 and the NVIDIA code-signing certificate leak in 2022 both needed coordinated revocation. Downgrade and rollback attacks are the standard gap that TUF and Uptane address. Console and mobile titles must keep verifying content for 10 or more years, which requires crypto agility (PQC migration of signatures is on NIST's 2030–2035 deprecation track).
- Proposed change: Add capability XC.SEC.signed-artifacts ("signature envelope, trust roots, key rotation/revocation, version floors/anti-rollback, algorithm agility"). Its owner should be a runtime skill, either moving CORE.TYPES.crypto into a new runtime expert `security-runtime` (parent security-engineering, targets all) or giving it to package-formats-vfs. Expose it through a new contract C-SIGN (layer 1–2) consumed by package-formats-vfs, persistence-save, plugin-system, modding-ugc, online-services-liveops and packaging-release-patching. Add a radar entry for PQC signatures (class M).

### K-SEC-5 · major · omission
- Target: XC.SEC.secrets, BLD.REL.packaging, RES.PKG.crypto, ARCH.ORG.human-gates, XC.SEC.incident
- Finding: No capability owns signing-key custody. That covers key hierarchy, HSM or cloud-KMS use, signing as a gated service rather than a key file, who may request a signature, rotation, and compromise response. XC.SEC.secrets ("Secrets management", contributor ci-cd) is generic. Release signing sits under packaging-release-patching with no custody model. ARCH.ORG.human-gates lists contracts, spend, NDA access, submissions and legal, but not production signing, security-exception or risk acceptance, CI permission or secret-scope changes, new third-party dependencies, vulnerability disclosure publication, or telemetry/data-collection scope changes. In an engine built by autonomous agents, an agent able to trigger a production signature can ship anything. XC.SEC.incident is scoped to "online titles", so a compromise of the engine's own build farm or keys has no runbook owner.
- Evidence: The NVIDIA 2022 and MSI 2023 (Intel Boot Guard) key leaks, and the SolarWinds 2020 build-system compromise. SLSA L3 requires that signing keys are not accessible to build steps.
- Proposed change: Add XC.SEC.key-custody (owner security-engineering, contributors packaging-release-patching, ci-cd-automation, package-formats-vfs, persistence-save): "key hierarchy, HSM/KMS, signing-as-a-service with human approval for production keys, rotation, revocation, compromise drill". Extend ARCH.ORG.human-gates with the gates listed above. Widen XC.SEC.incident to "engine infrastructure and online titles", with ci-cd-automation and build-release-architect as contributors.

### K-SEC-6 · major · dependency-error
- Target: milestones.json (M0–M5), C-TRUST, plugin-system (M1), modding-ugc (M5), anti-cheat-integrity (M4)
- Finding: Security appears in no milestone. C-TRUST is never drafted or frozen, although C-SER, whose rules include "untrusted-input rules", is frozen at M1. No exit criterion requires a threat model, fuzzing or hardening. M1 declares the indie-2d game "shippable" and brings in saves, fonts, scripting, deep links (platform-services) and plugin-system (binary plugins in client and server targets). Its exit criterion has no threat-model, fuzz-coverage or hardened-build condition. M4 "Online" has no network fuzzing, DoS or pen-test condition. M5 "mods" has no sandbox-escape testing. "Process skills are active from M0" is not a gate. Security retrofitted after contracts freeze is the classic, expensive failure mode.
- Proposed change: Put C-TRUST in M0 `contracts_draft` and M1 `contracts_frozen`. Add to exit criteria: M0, a sanitizer and fuzz lane on the package/serialization parser. M1, the threat model for the configuration, fuzz harnesses for every registry input reaching indie-2d-client with coverage floors, the hardened shipping build matrix (XC.SEC.hardening), and a shipping dev-surface audit. M4, packet/handshake fuzzing, DoS test (NET.TRANS.dos), server-authority review, and an external pen test as a human gate. M5, mod/script/shader sandbox-escape and GPU-DoS tests. Have check.py require every registry input reaching a milestone's configuration to have a fuzz target by that milestone.

### K-SEC-7 · major · maturity-error
- Target: XC.SEC.agent-boundary (E), ARCH.ORG.provenance, research-evidence, engine-product-management (ARCH.PROD.intake), program-orchestration (ARCH.ORG.triage), crash-diagnostics (OBS.CRASH.feedback), ARCH.ORG.critic-gates
- Finding: (a) XC.SEC.agent-boundary, which includes the "prompt-injection threat model", is labeled Established. No demonstrated robust defense against prompt injection exists: OWASP ranks it LLM01, and vendors describe it as unsolved. The E label keeps it off the radar, because check.py only tracks non-E capabilities. (b) The agents that build this engine read attacker-influenceable text all the time: web sources (research-evidence), game-team bug reports (intake), external vulnerability reports, player feedback and crash annotations (triage), and third-party source and docs. None of these is registered as an untrusted input to an agent, and there is no red-team corpus analogous to fuzz targets. (c) Nothing requires a mandatory independent security review, or a two-agent rule, for changes to security-critical code: parsers of registry inputs, crypto, auth, sandboxes, build scripts and CI config. QA.AGENT.* guards test integrity, not deliberately or injected malicious changes.
- Evidence: In the xz-utils backdoor (CVE-2024-3094, 2024), a trusted contributor inserted a backdoor through build scripts and test fixtures, which is exactly what a prompt-injected agent could do. Coding-agent prompt injection has been exploited: CVE-2025-53773 (Copilot changed its own settings to auto-approve and gained RCE) and CVE-2025-54135 in Cursor.
- Proposed change: Set XC.SEC.agent-boundary to M and add a radar entry with a promotion trigger. Add `untrusted_inputs` to process skills: `web-sources` (research-evidence), `external-reports` (engine-product-management, program-orchestration), `vuln-reports` (security-engineering), `third-party-source` (build-system-toolchains). Add capability XC.SEC.agent-redteam (owner security-engineering): a prompt-injection corpus run against each agent role. Add ARCH.ORG.sensitive-paths (owner program-orchestration, contributor security-engineering): a K-SEC S3 gate plus a second agent's approval on registry-parser, crypto, auth, sandbox, build and CI write sets.

### K-SEC-8 · major · omission
- Target: ai-assisted-authoring, ED.ARCH.agent-api, ED.ARCH.extension, C-EDCMD
- Finding: Editor copilots (ED.AI.generative) and the agent/automation control protocol for "editor and runtime" (ED.ARCH.agent-api, MCP class) let an LLM issue editor commands, tool scripts (Python class) and runtime controls, while reading project content that may be hostile (asset metadata, imported files, marketplace packages, collaborator commits). ai-assisted-authoring registers no untrusted input. No capability defines permission scoping for copilot and agent-API actions, confirmation for destructive or code-executing commands, or whether the agent API is compiled out of shipping runtimes. XC.SEC.genai covers runtime gameplay LLMs, not tool-side ones.
- Evidence: CVE-2025-53773 and CVE-2025-54135 (above) were both caused by instructions hidden in workspace content. The MCP ecosystem has also had tool-poisoning disclosures in 2025. XC.SEC.dev-trust ("workspace trust") shows the framework already accepts that opening a project is a trust event, but the AI path bypasses it.
- Proposed change: Register `generated-content` and `project-content-to-llm` on ai-assisted-authoring. Add ED.ARCH.agent-api-security (owner editor-architect, contributor security-engineering): "capability-scoped tokens, per-command permission classes, human confirmation for code-exec/destructive/network actions, workspace-trust gating, shipping-build exclusion". Add both to the XC.SEC.genai contributors.

### K-SEC-9 · major · omission
- Target: modding-ugc (XC.EXT.ugc, XC.EXT.mod-loading), plugin-system (C-PLUGIN consumed by modding-ugc), XC.SEC.sandbox
- Finding: modding-ugc consumes C-PLUGIN, so mods can be native binary plugins in client and server. Nothing covers distribution integrity or response: mod package signing and author identity, integrity of mod updates (account takeover), scanning, an explicit native-code-mod policy (opt-in and warnings versus sandboxed-only), and a kill switch or revocation for malicious mods already installed. The sandbox capability (XC.SEC.sandbox) is policy only and assumes the code runs sandboxed.
- Evidence: The fractureiser malware (June 2023) spread through Minecraft mods on CurseForge and Bukkit after author accounts were compromised. In the "Downfall" Slay the Spire mod incident (December 2024), a hijacked Steam Workshop update pushed an infostealer to installed users. Both came in through the update channel, not the sandbox.
- Proposed change: Add XC.EXT.ugc-integrity (owner modding-ugc, contributors security-engineering, online-services-liveops, platform-services): "mod/UGC package signing via C-SIGN, author identity and 2FA requirement at the distribution boundary, update pinning/review, remote revocation/kill switch, native-code mod policy". Record an ADR obligation that mods in the `ugc` profile are sandboxed-by-default, with native mods allowed only behind an explicit player opt-in.

### K-SEC-10 · major · omission
- Target: legacy-patterns.json, K-LEGACY, architecture-governance (ARCH.GOV.anti-legacy)
- Finding: The anti-legacy catalogue has 27 patterns and none is about security. K-LEGACY checks only against this catalogue, so legacy security stances will never be flagged. Missing patterns: client-authoritative game state or economy; content encryption treated as protection (pak keys ship in every client and are routinely extracted); long-lived backend secrets or API keys embedded in clients; client-side receipt validation; unsandboxed in-process native mods; hand-written C/C++ parsers for hostile input without a hardened or memory-safe path; dev consoles, ports and live-coding reachable in shipping; unkeyed hashing of attacker-controlled keys; "collect everything" telemetry without data minimization; kernel-mode anti-cheat as the default posture.
- Evidence: Embedded title secret keys and cloud credentials in shipped game clients are a recurring disclosure class. iOS in-app purchase "LocalhostHook"/iAP Cracker (2012) defeated client-side receipt checks. After the July 2024 CrowdStrike outage, Microsoft's Windows Resiliency Initiative is moving security vendors out of the kernel.
- Proposed change: Add these as legacy-patterns entries, each naming security-engineering as the justification owner and the capability that provides the modern alternative (NET.ARCH.authority, XC.SEC.signed-artifacts, PLAT.COMM.receipts server-side, XC.SEC.sandbox, XC.SEC.memory-safety, XC.SEC.testing, OBS.LOG.analytics privacy classes).

### K-SEC-11 · major · omission
- Target: anti-cheat-integrity, platform-services, platform-mobile, platform-desktop, radar.json
- Finding: The framework has no client or device attestation capability. On mobile this is established practice (Play Integrity API, App Attest/DeviceCheck), and elsewhere platform-signed auth tokens, TPM/VBS-backed checks and console attestation play the same role. Server-side trust decisions such as ranked eligibility, economy and anti-bot need it. The radar also has no entry for anti-cheat architecture shifts: platform pressure against kernel drivers, user-mode and attestation-based anti-cheat, anti-cheat on Proton/ARM, and ML-based behavioral detection from server telemetry.
- Evidence: Google made Play Integrity the SafetyNet replacement (SafetyNet shut down in 2025). Apple App Attest is established. The Windows Resiliency Initiative after CrowdStrike affects kernel anti-cheat. PLAT.DESK.os-security already mentions "anti-cheat on Proton", which shows the platform matrix is being hit by this.
- Proposed change: Add XC.SEC.attestation (owner anti-cheat-integrity, contributors platform-mobile, platform-desktop, platform-console, platform-services; E on mobile, M on PC): "device/app attestation tokens, server verification, graceful degradation". Add a radar entry "User-mode & attestation-based anti-cheat; kernel-driver deprecation pressure" (M) with a revisit trigger tied to Windows kernel-access policy changes.

### K-SEC-12 · major · missing-contract
- Target: NET.REP.interest (replication), NET.PRED.lockstep, NET.ARCH.model / NET.ARCH.authority, anti-cheat-integrity, rts-3d-massim-client configuration
- Finding: Server authority alone does not stop information cheats (wallhacks, maphacks, ESP). Stopping them requires that the server not send hidden state at all. NET.REP.interest is framed as performance relevancy (owner replication, contributor world-architect), with no anti-cheat contributor and no "security relevancy" mode such as visibility- or fog-based culling. Lockstep (NET.PRED.lockstep, used by the rts-3d-massim configuration) and P2P/listen-server topologies (NET.ARCH.model, NET.SRV.listen) inherently send full state to, or place authority in, untrusted peers. The framework does not record this trade-off or who decides it.
- Evidence: Riot's Valorant "Fog of War" and CS2 server-side occlusion culling show that information hiding is part of netcode, not a middleware add-on. Maphacks are endemic to lockstep RTS. The Dark Souls III P2P RCE also shows the P2P trust exposure.
- Proposed change: Add anti-cheat-integrity as a contributor to NET.REP.interest. Add capability XC.SEC.info-hiding (owner anti-cheat-integrity, contributors replication, prediction-rollback): "server-side visibility/fog culling, delayed reveal, per-netcode-model information-leak and host-trust assessment". Make it an obligation of the "network authority & replication" crosscutting concern: declare what hidden state reaches clients.

### K-SEC-13 · major · omission
- Target: CORE.TYPES.hashing / CORE.TYPES.containers (containers-core-types), C-TRUST validation obligations, dedicated-server, replication (NET.REP.rpc), anti-cheat-integrity
- Finding: Denial of service by resource exhaustion is covered only at the transport (NET.TRANS.dos) and in scripts (GAM.SCR.sandbox). There is no obligation for algorithmic-complexity limits: keyed or randomized hashing for attacker-controlled keys (CORE.TYPES.hashing specifies only "stable content hashing with versioned algorithm/seed"), and per-input size, depth, element-count and time quotas, including decompression ratio limits. Nobody owns application-level server budgets either: per-connection memory, RPC and command rate limits, and quotas on expensive server work triggered by clients (pathfinding, spawns, physics queries). "Rate limiting" appears only in the anti-cheat skill's purpose text. Fuzzing finds crashes, not quadratic blow-ups.
- Evidence: HashDoS (CVE-2011-4885 and related, 2011) hit every major language runtime. Decompression bombs. Server hitches caused by crafted RPC floods are a recurring online-game outage class.
- Proposed change: Add CORE.TYPES.hash-dos ("keyed hashing (SipHash-class) mandated for containers keyed by untrusted data", owner containers-core-types, contributor security-engineering). Add NET.SRV.budgets ("per-connection memory/CPU/RPC quotas and client-triggered-work limits", owner dedicated-server, contributors replication, anti-cheat-integrity). Add "resource limits" as a required field of every untrusted-input registry entry (K-SEC-1).

### K-SEC-14 · minor · omission
- Target: C-IPC ("dev-only port security"), PLAT.PAL.devlink, OBS.LOG.remote, ED.ARCH.remote, ED.DEBUG.console, XC.ITER.live-coding, ED.ARCH.agent-api, XC.SEC.testing, BLD.SYS.configs
- Finding: Dev-only remote and code-loading surfaces (devlink, remote diagnostics, remote live editing, console and cheat commands, live coding, automation API, script debugger over DAP) are spread over six owners. The only shipping safeguard is an after-the-fact "shipping-build hardening audit" (XC.SEC.testing). No build-time mechanism ensures that shipping configurations contain none of them, such as a declared dev-surface manifest checked by a fitness function. Where they must exist in shipping, such as a server remote console, nothing requires authentication.
- Proposed change: Add BLD.SYS.dev-surface-exclusion (owner build-system-toolchains, contributors security-engineering, architecture-governance): every skill declares its dev surfaces in data, and the shipping configuration is verified by fitness function and binary scan to contain none. Any surface allowed in shipping must be authenticated through C-IPC.

### K-SEC-15 · minor · omission
- Target: xr-runtime (PLAT.XR.gaze-input, PLAT.XR.scene, PLAT.XR.anchors, PLAT.XR.passthrough), INP.DEV.eye-tracking, PLAT.SVC.voice-text, NET.REP.replays / C-REPLAY, XC.SEC.data-rights
- Finding: Personal-data classes that need special handling have no privacy contributor or data-class obligation. Gaze and eye-tracking data is biometric-grade under GDPR Art. 9 and restricted by platforms (visionOS does not give apps gaze data). Room meshes and anchors map the interior of a player's home and become shared data through shared anchors. Passthrough camera frames count too. So do voice recordings or transcripts kept for moderation, and replays or killcams that embed player IDs, names and chat when shared publicly.
- Proposed change: Add security-engineering as a contributor to PLAT.XR.gaze-input, PLAT.XR.scene, PLAT.XR.anchors, PLAT.XR.passthrough, INP.DEV.eye-tracking, PLAT.SVC.voice-text and XC.DET.replay-format. Extend XC.SEC.data-rights to "data inventory with sensitivity classes (biometric, spatial, voice, minors), per-class retention and on-device-only defaults".

### K-SEC-16 · minor · wrong-boundary
- Target: PLAT.COMM.receipts (platform-services, runtime client), PLAT.COMM.currency, NET.SRV.transactions
- Finding: Receipt and entitlement validation is owned by a runtime client skill as a "validation boundary". The text does not say that validation happens server-side or at the store, with grants issued only through the idempotent server transaction path, and not in the client. Without that, an implementing agent may validate in the client, which is the known-broken pattern.
- Proposed change: Rename to "Server-side receipt/entitlement verification boundary (client only forwards receipts; grants via NET.SRV.transactions)". Add dedicated-server as a contributor.

### K-SEC-17 · minor · wrong-boundary
- Target: security-engineering (18 capabilities), XC.SEC.privacy, XC.SEC.data-rights, OBS.LOG.consent, QA.CERT.privacy, XC.SEC.vuln-response
- Finding: security-engineering is one process agent owning threat modeling, memory safety, hardening, crypto policy, supply chain, secrets, privacy engineering, data-subject rights, vulnerability response (PSIRT), incident response, agent boundary, genAI threats and pen testing. It also reviews all 143 skills. Privacy/data protection is a separate discipline, and its policy is currently split three ways (XC.SEC.privacy, OBS.LOG.consent, QA.CERT.privacy) with no single privacy owner. XC.SEC.vuln-response also lacks the licensee-notification channel (engine-product-management) and the expedited security-patch certification path (certification-compliance, platform-console). The Unity 2025 incident needed both.
- Proposed change: Add expert skill `privacy-data-protection` (parent security-engineering, process) owning XC.SEC.privacy, XC.SEC.data-rights and the policy half of OBS.LOG.consent, with privacy review obligations. Add engine-product-management and certification-compliance as contributors to XC.SEC.vuln-response.
