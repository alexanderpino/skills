# K-PERF · Performance Critic · G1 round 2

Scope: performance architecture that the structure bakes in, and the performance organization. `check.py` is green (0 errors, 0 warnings). None of the findings below can be detected by it.

### K-PERF-1 · blocker · omission
- Target: RES.MGMT.* (missing `RES.MGMT.arbitration`), resource-streaming-architect, RND.MEM.residency, C-RES, CORE.MEM.uma, milestone M3
- Finding: Nothing owns cross-pool memory arbitration. `docs/00` §4 says "residency policy belongs to the cross-pool arbiter in `resource-streaming-architect`". §6 makes "cross-pool arbitration under one physical budget" a default stance. `RND.MEM.residency` reads "policy in RES.MGMT.arbitration", gap A14 assigns the arbiter spike to resource-streaming-architect, and the M3 exit criterion is "within the arbitration budget". But no capability `RES.MGMT.arbitration` exists. The purpose of resource-streaming-architect names only "the streaming manager (budgets, eviction, prediction)". C-RES provides "pool registration, pressure signals and shrink-by-deadline requests", but nothing makes the decision that consumes those signals. So the texture/VT pool (texture-streaming-vt), cluster pages (virtualized-geometry-lod), BLAS/TLAS (ray-tracing-infrastructure), audio streaming (audio-dsp-mixing), physics/nav cells, animation data and shadow pages each get a local budget with no owner of the global trade-off. The reference to the arbiter points at nothing, so no gate catches it.
- Evidence: On UMA consoles and on integrated/mobile GPUs, CPU heaps and every GPU pool share one physical memory (PS5, Xbox Series, Apple silicon, Switch-class). Independent pools with separate budgets either over-reserve, wasting the most constrained resource, or oscillate and starve each other under pressure. The framework's own §6 row names this ("independent streaming pools that compete") as the legacy pattern it replaces. Pool-local streamers with fixed pool sizes were a documented source of pop-in and OOM on memory-constrained platforms. That is why unified priority spaces were adopted (for example, feedback-driven unified residency in virtual-geometry/VT systems, and Frostbite/Decima-era streaming talks that describe global priority). Without an owner, the phase-2 SKILL.md of every pool owner will each invent its own budget policy.
- Proposed change: Add `RES.MGMT.arbitration`: "Cross-pool memory arbiter: one priority/utility space across CPU and GPU pools under a single physical budget per tier (UMA and discrete), pool registration, pressure → shrink-by-deadline, anti-oscillation hysteresis, OOM-avoidance ordering". Owner resource-streaming-architect. Contributors: memory-allocators, gpu-memory-resources, texture-streaming-vt, virtualized-geometry-lod, ray-tracing-infrastructure, audio-dsp-mixing, performance-architect. Add "cross-pool arbitration" to the resource-streaming-architect purpose. Add a C-RES obligation that every pool registers with the arbiter and must not size itself. Add a seed-map entry "cross-pool arbitration" → `RES.MGMT.arbitration`. Extend check.py so that every capability id quoted inside a capability name must exist.

### K-PERF-2 · major · obsolete-assumption
- Target: CORE.FRAME.pipelining, CORE.FRAME.phases, frame-orchestration, render-architect (purpose "render threading"), RND.GPU.recording, L03
- Finding: The capability that owns frame pipelining reads "Frame pipelining with a **dedicated game thread and a dedicated render thread**". `CORE.FRAME.phases` reads "Tick phases, sync points & **phase barriers**". Both contradict the §6 defaults ("No fixed game, render or RHI threads"; "A global barrier needs an ADR"), legacy pattern L03, C-FLOW ("global barriers need an ADR") and `RND.GPU.recording` (no dedicated render thread unless an API mandates it). Three skills now claim the render-threading model with incompatible stances: frame-orchestration (dedicated threads), gpu-platform-architect (tasks) and render-architect (purpose lists "render threading").
- Evidence: A fixed game/render thread pair caps frame parallelism at two critical-path lanes and forces a per-frame proxy hand-off copy. This is the UE3/UE4 GameThread/RenderThread/RHIThread structure that later engines moved away from: Destiny's job-based renderer (Tatarchuk/Genova, GDC 2015), Naughty Dog's fiber-based frame (Gyrling, GDC 2015) and Frostbite's frame graph (O'Donnell, GDC 2017). Phase barriers idle every worker at each phase edge. Because the frame-orchestration SKILL.md is generated from its capabilities, the frame owner would inherit the legacy model, and the task-based recording owner would inherit the opposite one.
- Proposed change: Rename `CORE.FRAME.pipelining` to "Frame pipelining as overlapping task-graph frames (simulation N+1 ‖ render extract N ‖ GPU N−1) with declared frames-in-flight depth; no fixed game/render threads (dedicated threads only by ADR via CORE.JOBS.thread-model)". Rename `CORE.FRAME.phases` to "Tick phases & the minimal set of named global sync points (each justified by ADR); ordering otherwise derived from C-FRAME access declarations". Remove "render threading" from the render-architect purpose and add a non-responsibility "Render threading / command-recording model → gpu-platform-architect".

### K-PERF-3 · major · overlap
- Target: RND.ARCH.instance-data (render-architect), RND.GEO.gpu-scene / C-INSTANCES (geometry-pipeline)
- Finding: Two owners define the same hot data. render-architect owns `RND.ARCH.instance-data` "GPU instance data layout & delta upload". geometry-pipeline owns `RND.GEO.gpu-scene` "GPU scene & instance data management" and provides C-INSTANCES, "batched add/remove/update with delta upload …, instance data layout shared with the ray-tracing instance builder". The layout, the delta-upload scheme and its bandwidth cost therefore have two owners. That breaks §1's merge rule ("merge units that share hot data without a stable interface").
- Evidence: The instance buffer is the most bandwidth-sensitive structure in a GPU-driven renderer. It is read by culling, visibility-buffer resolve, shadows, motion vectors and TLAS build. Its layout (SoA vs AoS, quantization, cache-line packing) and its update scheme (scatter-upload of dirty ranges vs full rewrite) set the O(changes) property that C-RSCENE promises. In GPU-scene designs (UE5 GPUScene, "GPU-Driven Rendering Pipelines", Haar/Aaltonen SIGGRAPH 2015) one owner holds layout and upload together. With split ownership, two agents edit one buffer format.
- Proposed change: Delete `RND.ARCH.instance-data`. Move its text into `RND.GEO.gpu-scene` (owner geometry-pipeline, contributors render-architect and ray-tracing-infrastructure). render-architect keeps only `RND.ARCH.scene-sync` (the extraction side of C-RSCENE).

### K-PERF-4 · major · maturity-error
- Target: RND.GRAPH.work-graphs, RND.RHI.gpu-work, radar entry "Work graphs & mesh nodes"
- Finding: `RND.GRAPH.work-graphs` is labelled **E** (established), while radar.json classifies the same capability as **X** ("no shipped titles"). Gap A6 and §7 say work graphs are reached only as an optional part of C-RG. The E label lets an established capability depend on work graphs, and check.py cannot flag the inconsistency because it only checks that non-E capabilities appear on the radar. `RND.RHI.gpu-work` (E) also bundles "work-graph programs" together with established indirect/ExecuteIndirect/DGC primitives, so the whole capability passes as established.
- Evidence: D3D12 Work Graphs 1.0 shipped in 2024 and mesh nodes are still in preview. There is no cross-vendor Vulkan equivalent beyond a provisional AMDX extension, no Metal or WebGPU equivalent, and no public console exposure. Performance varies by vendor and driver (the framework's own A6). The radar row is correct and the capability label is wrong.
- Proposed change: Set `RND.GRAPH.work-graphs` to X (or M at most, matching the radar). Split `RND.RHI.gpu-work` into `RND.RHI.gpu-work` (E: indirect, device-generated commands, backing memory) and `RND.RHI.work-graph-programs` (X, radar-listed, fallback indirect). Add a check.py rule that a capability's maturity must equal its radar class.

### K-PERF-5 · major · dependency-error
- Target: runtime-scalability, C-SCALE (L1), CORE.SCALE.governor, C-PRESENT, C-RES, RND.RHI.queries
- Finding: The closed-loop governor sits in a skill whose only runtime inputs are C-CFG, C-PAL, C-INSTR and C-TASK, and C-SCALE is L1. The governor's control signals are GPU frame time (RHI timestamp queries, L2), present/pacing feedback (C-PRESENT, L2), streaming-pool pressure (C-RES, L2) and GPU memory budget reports (C-GPUMEM, L2). None of them can reach it under the no-upward-links rule except through C-INSTR, and C-INSTR is "zero cost when compiled out". In a shipping build the governor therefore has no frame-time or GPU-time input: the loop either doesn't close or quietly depends on development instrumentation.
- Evidence: Shipping dynamic resolution and governors need GPU timing and present feedback in release builds. Examples are console DRS driven by GPU timestamp queries, Android ADPF/Swappy pacing feedback, and Apple Game Mode / MetalFX dynamic resolution. The signal path must be a product feature, not a profiler feature. The layer placement also stops the governor from reading the C-RES pressure signals that K-PERF-1's arbiter emits.
- Proposed change: Keep the knob/actuator registry and budget query in C-SCALE (L1, universal). Move the governor into a separate runtime-scalability module that provides a new L2 contract `C-GOVERN` (or attribute it as `C-PRESENT@C-GOVERN`, `C-RES@C-GOVERN`, `C-GPUMEM?@C-GOVERN`, `C-FRAME@C-GOVERN`). Add an obligation to C-PRESENT and C-RHI to deliver shipping-grade GPU-frame-time and present-feedback signals that do not depend on C-INSTR. Add a governor fitness test to the M2 exit (see K-PERF-10).

### K-PERF-6 · major · omission
- Target: RND.MEM.upload, RES.MGMT.pipeline, RES.IO.gpu-decompress, RND.GRAPH.async, RND.RT.as, C-IO (L2) vs C-RG (L3)
- Finding: Per-frame GPU transfer and bandwidth has no arbiter. Several producers compete every frame for copy queues, the PCIe/UMA bandwidth and the async-compute slots: streaming uploads (RES.MGMT.pipeline), GPU decompression (RES.IO.gpu-decompress), instance/scene deltas (C-INSTANCES), VT page uploads, BLAS builds and refits (RND.RT.as, ANM.DEF.rt), particle/skinning compute, and ML passes. `RND.MEM.upload` owns only the staging rings, and `RES.MGMT.pipeline` owns a "staging-memory budget", which is capacity, not bandwidth. GPU decompression belongs to async-io-storage at L2, which cannot consume C-RG (L3), so its GPU work cannot be scheduled against the render graph's queues at all.
- Evidence: GPU-decompression and streaming-upload contention with frame work is a documented hitch source on PC. Examples are the DirectStorage GPU decompression guidance on queue priority and scheduling (Microsoft DirectStorage 1.1+ docs) and stutter reports on PC ports of PS5 titles that stream heavily. On discrete GPUs PCIe upload competes with readback and residency paging. On UMA, copy traffic competes with rasterization for the same DRAM bandwidth. Render-graph owners (Frostbite frame graph, the UE5 RDG async-compute scheduler) treat copy and async work as graph-scheduled, not as side channels.
- Proposed change: Add `RND.GRAPH.transfer-budget`: "Per-frame transfer & async-queue bandwidth arbitration: registered producers (streaming upload, GPU decompression, scene deltas, AS builds, VT pages) with priority, deadline and byte budgets per tier; copy/async queue placement". Owner render-graph-scheduling, contributors gpu-memory-resources, async-io-storage, resource-streaming-architect, ray-tracing-infrastructure. Invert the dependency for GPU decompression: C-IO declares GPU-decompress jobs as external work items that a C-RG node owned by render-graph-scheduling executes (dependency inversion like C-PRESENT). Add "transfer bytes per frame" as a C-BUDGET line.

### K-PERF-7 · major · wrong-boundary
- Target: perf-benchmarking, memory-performance, gpu-performance, loading-streaming-performance (all kind=process, targets []), PRF.BENCH.micro/stats/replay, PRF.MEM.snapshots, PRF.GPU.baselines, PRF.LOAD.hitch-gate, C-BENCH
- Finding: Performance measurement code exists in no build. Every performance expert is kind=process with no targets, but several of their capabilities are code that must run inside the measured process on every target, including server, mobile and console. Examples: the benchmark runner and warm-up/variance control (PRF.BENCH.micro/stats), replay- and flythrough-driven runs (PRF.BENCH.replay), in-process memory snapshot capture (PRF.MEM.snapshots), automated GPU capture and per-pass baselines (PRF.GPU.baselines), and hitch trace capture (PRF.LOAD.hitch-gate). Configuration closure therefore cannot prove that a benchmark can run in `online-3d-server` or `lite-3d-mobile-client`. The write-set convention gives these process skills neither `src/` nor `tools/`. memory-performance consumes no contracts at all, so it has no declared access to C-MEM tagging, C-RES pool reports or C-GPUMEM budget reports that attribution requires.
- Evidence: Production perf infrastructure has an in-engine half, such as UE's automated perf tests plus CSV profiler and memreport, or Unity's Performance Testing Extension plus Memory Profiler capture. It also has an offline half (analyzers, dashboards, statistics). The in-engine half is subject to the same layering, platform and build-target rules as any other runtime module. Under the §8 rule ("two agents must never own one file set") it needs one owner and one declared target set. Otherwise it ends up in observability-telemetry by accident, or in each subsystem.
- Proposed change: Either give perf-benchmarking a runtime module (kind stays process for the organization, plus a declared dev-only runtime module with targets client/headless-client/server/tools on all platforms, consuming C-INSTR, C-FRAME, C-REPLAY?, C-MEM, C-RES, C-GPUMEM?) that hosts the benchmark runner, capture triggers and snapshot hooks for all perf experts, or assign these in-process hooks explicitly to observability-telemetry through C-INSTR and C-BENCH. Give memory-performance `consumes: [C-MEM, C-RES, C-GPUMEM?, C-INSTR]`. Extend configuration closure so that every configuration contains a C-BENCH runner.

### K-PERF-8 · major · omission
- Target: NET.REP.state, NET.REP.interest, NET.REP.priority, C-REP, C-SIGNIF, replication
- Finding: Replication is the largest world-state replica at online scale, yet it has no O(changes) or per-connection cost obligation. The crosscutting "scalability" obligation says "spatial replicas update in O(changes)", and C-RSCENE, C-INSTANCES and C-SPATIAL all state change-driven cost. C-REP ("replicated state declaration, relevancy hooks, RPCs…") and NET.REP.* say nothing about change tracking (push/dirty model vs per-connection shadow-state comparison), about sharing serialized deltas across connections, or about the cost of interest management as entities × connections grow. C-SIGNIF is "computed … from views/players (all players on a server)", which is O(entities × players) unless spatially bucketed, and nothing requires the bucketing.
- Evidence: Per-connection property comparison against shadow state was the dominant server CPU cost in UE's legacy replication. Epic introduced the push model and then Iris (UE 5.1+) with dirty tracking, shared quantized state and filter/prioritization passes that are batch-parallel over connections. Grid- and cell-based relevancy is standard at MMO/BR scale (Fortnite replication graph, GDC 2019). These choices set server density (NET.SRV.density) and therefore cost per player.
- Proposed change: Add `NET.REP.change-tracking`: "Change-driven replication: dirty tracking at the write site, per-object serialized deltas shared across connections, batch-parallel filtering/prioritization; cost O(changes + relevant-set per connection)". Owner replication. Add to C-REP: "producers mark dirty state; no per-connection full-state comparison". Add to C-SIGNIF: "significance/relevancy computed over a spatial bucketing (C-SPATIAL index) with declared cost per player". Require `PRF.METH.asymptotics` to cover the dimensions "replicated entities" and "connections".

### K-PERF-9 · major · omission
- Target: performance-architect subtree, NET.DBG.profiler, NET.SRV.density, QA.FUNC.load, PRF.METH.model
- Finding: No independent performance analyst covers online performance: bandwidth per player, server tick cost and instance density, cost per concurrent user, and analysis of load-test results. The perf workstream covers CPU, GPU, loading/hitches, memory and benchmarking. The network bandwidth profiler belongs to replication (the implementer). Server density belongs to dedicated-server (the implementer). Load testing belongs to functional-automation-soak (QA, which executes tests and does not analyze performance). This breaks the framework's rule that "performance experts analyze and route findings" and that implementers must not grade themselves (QA.AGENT.*). For online configurations, which cost money per server-hour, no one outside the implementing skill runs the hypothesis → analysis → C-PERF finding step.
- Evidence: Bandwidth and server CPU per player are first-order budgets in online titles. Examples are the Fortnite/UE replication-graph work on 100-player servers (GDC 2019), Overwatch netcode (Ford, GDC 2017) and Halo/Destiny bandwidth budgets. Production studios keep server performance/capacity engineers who are separate from netcode feature owners.
- Proposed change: Add an expert `online-performance` (kind process, parent performance-architect, workstream performance) owning `PRF.NET.bandwidth` (per-connection/entity/property bandwidth analysis against NET.ARCH.budgets), `PRF.NET.server-density` (tick cost, instances per host, cost per CCU against ARCH.REQ.hardware-tiers server classes) and `PRF.NET.load-analysis` (load-test analysis and capacity-model reconciliation with PRF.METH.model). Contributors: replication, dedicated-server, functional-automation-soak. Keep NET.DBG.profiler with replication as the instrument. If a new skill is unwanted, assign these three capabilities to cpu-performance and state the expertise in its purpose.

### K-PERF-10 · major · omission
- Target: milestones.json (M0–M5 exits), C-BUDGET, C-BENCH, PRF.METH.gates
- Finding: The milestone ladder has no performance exit criteria, although §6 says "Instrumentation, tests, budgets and determinism levels exist before features". The M0 exit covers boot, window, sprite, CI and determinism/sanitizer smoke lanes, but has no frame-time trace, no C-BUDGET baseline and no benchmark lane. M1 and M2 exits contain no budget. M2's "GPU-driven and CPU-submission paths" carry no tier budget, and the hitch/PSO gate is absent even though gap A10 asks for one. Only M3 ("benchmarked") and M4 ("bot load test") mention measurement at all. The governor (K-PERF-5), the arbiter (K-PERF-1) and the hitch gate have no milestone at which they must be proven.
- Evidence: If performance is not gated from the walking skeleton on, it is retrofitted late. The brief and §6 both reject that pattern, and autonomous agents optimize for the exit criteria they are given. Continuous per-commit perf lanes from the first milestone are practice at studios such as Frostbite, Ubisoft Snowdrop and Epic (Horde/Gauntlet perf tests).
- Proposed change: Add to each exit: M0 = "trace capture + C-BENCH runner on the skeleton; C-BUDGET v0 for indie-2d tiers; perf lane in CI (frame time, startup, memory)". M1 = "indie-2d reference game within budget on min-spec PC and mobile tier; hitch gate active". M2 = "std3d and lite3d budgets per tier on PC, console and mobile; PSO first-encounter hitch gate; governor closed-loop test". M3 = "arbiter under synthetic pressure without oscillation or starvation (A14); scale-content stress worlds within asymptotic declarations". M4 = "bandwidth/player and server density budgets met under load test". Make `C-BUDGET` and `C-BENCH` "frozen" entries of M0 and M2 respectively, or add a milestone field for process contracts.

### K-PERF-14 · minor · omission
- Target: RES.PKG.format, RES.PKG.install-layout, package-formats-vfs
- Finding: Nothing owns ordering package data by access pattern. There is no capability for "play-trace-driven chunk/file ordering and co-location of assets loaded together". That ordering sets request count, read amplification and decompression batch efficiency. It also sets load time on HDD, optical, eMMC/UFS and web delivery, and still matters for NVMe request overhead.
- Proposed change: Add `RES.PKG.ordering`: "Access-order package layout from load/stream traces (co-location, request coalescing), validated by PRF.LOAD.load-time". Owner package-formats-vfs, contributors loading-streaming-performance and content-pipeline-architect.
