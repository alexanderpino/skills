# K-TOOLS — Tools & Editor Critic, G1 round 2

### K-TOOLS-1 · blocker · omission
- Target: ED.ARCH (area), C-EDCMD, editor-architect, seed-map.json `"undo/redo"`, `"command systems"`
- Finding: No capability owns transactions, undo/redo or the command system. ED.ARCH has process, separation, selection, extension, pie, remote, headless, scale, recovery, pie-net, agent-api and discipline-workflows, but nothing for the transaction/command model. `editor-architect.purpose` and the `C-EDCMD` summary ("Transactions, undo/redo, selection, tool registration") both promise it. seed-map.json maps the brief terms "undo/redo" and "command systems" to `ED.ARCH.selection`, which is a different capability, so the brief-term check passes on a wrong mapping. About 30 skills depend on this service through `C-EDCMD` (every `*.TOOL` owner, world-editor-viewport, graph-editor-framework, collaboration-version-control). ED.ARCH.recovery ("transaction journal") and ED.COLLAB.multiuser both assume it exists. Nothing defines the command granularity, how commands serialize for multi-user sessions and the recovery journal, how transactions cross the in/out-of-process boundary (B16), or undo scoping across the world, asset editors and PIE. Without that, every domain editor will build its own undo.
- Evidence: Transaction and undo design is the core of an editor. UE's FTransaction buffer serializes whole objects, which is costly and a known scaling limit. Unity's Undo system and the command/diff-based undo used in newer editors (O3DE prefab undo, Godot UndoRedo) show that the choice decides whether multi-user replication and crash journals are possible (UE Concert replicates transactions). The K-TOOLS check "undo/transactions universal" cannot be met without an owned capability.
- Proposed change: Add `ED.ARCH.transactions` ("Command/transaction model: serializable, diff-based commands, undo/redo scopes (world, asset editor, PIE-exclusion), transaction batching, cross-process transactions, journal feed for recovery and multi-user", owner `editor-architect`, E, contributors `collaboration-version-control`, `serialization-schema`). Remap seed-map "undo/redo" and "command systems" to it. Add `C-SER` and `C-IPC` to `C-EDCMD.requires` for journal and out-of-process forms.

### K-TOOLS-2 · major · missing-contract
- Target: world-editor-viewport, ED.WORLD.modes, ED.WORLD.viewport/gizmos/placement/splines, C-EDHOST, terrain, vegetation-foliage, water-ocean, atmosphere-weather, procedural-generation, global-illumination, render-2d-vector, navigation-pathfinding
- Finding: world-editor-viewport owns viewport, gizmos, placement, splines, preview scenes and "environment tool-mode hosting" but provides no contract. The environment tool owners (terrain sculpt, foliage paint, water bodies, lighting probe placement, tilemap painting, nav links, PCG volumes) consume only `C-EDCMD` and `C-EDHOST`. `C-EDHOST` belongs to editor-ui-framework yet claims "tool-mode registration", while the capability that hosts tool modes (`ED.WORLD.modes`) belongs to world-editor-viewport. The contract owner and the capability owner therefore differ. `terrain.non_responsibilities` routes "Viewport hosting" to world-editor-viewport, but terrain has no contract edge to it. Brushes, cursor raycasts against the world, gizmo/manipulator extension, spline component editing and viewport overlays have no declared interface.
- Evidence: Every production editor exposes a viewport/tool-mode API separate from panel hosting: UE `FEdMode`/`UInteractiveTool` + `InteractiveToolsFramework`, Unity `EditorTool`/`Handles`, O3DE ComponentMode/manipulators. Terrain, foliage and spline tools are the heaviest users.
- Proposed change: Add contract `C-EDVIEW` (L5, owner world-editor-viewport, requires `C-EDCMD`, `C-VIEW`, `C-RSCENE?`, `C-DRAW2D?`): "Viewport tool modes, brush/stroke input and world raycast picking, gizmo/manipulator extension, viewport overlays and 2D/ortho mode". Remove "tool-mode registration" from `C-EDHOST`. Add `C-EDVIEW` to the tool_consumes of every WLD.TOOL/RND.TOOL.lighting/RND.TOOL.tilemap-sprite/GAM.TOOL.nav/PHY.TOOL owner. Extend check.py's tool-logic rule so owners of world-placed tool caps must reach `C-EDVIEW`.

### K-TOOLS-3 · major · missing-contract
- Target: collaboration-version-control, ED.COLLAB.*, ED.GRAPH.diff, ED.UI.asset-browser, CNT.VAL.submit-gate, WLD.MODEL.file-per-object, BLD.CI.binary-distribution
- Finding: Source control has an owner but no contract (`collaboration-version-control.provides = []`). Checkout-on-edit and lock status belong in the transaction path, and the asset browser needs status overlays. Submit gates, file-per-object worlds, graph diff/merge and prebuilt-binary sync all need a VCS abstraction. ED.COLLAB.merge ("merge tooling for scene & asset data") needs domain-supplied semantic diff/merge for materials, data tables, prefabs, animation and dialogue, but no contract lets a domain register a differ or merger. Each consumer will therefore bind to Perforce or Git directly, and each domain will invent its own diff.
- Evidence: UE `ISourceControlProvider` plus per-asset diff tools, Unity VersionControl API and Smart Merge (UnityYAMLMerge), and Git/Perforce abstraction layers in Frostbite/Snowdrop-class editors. Merge of binary or semantic assets is the main collaboration pain point at 100+ people.
- Proposed change: Add contract `C-VCS` (L5, owner collaboration-version-control, requires `C-ASSET`, `C-SER`): "Workspace/changelist model, status/lock queries, checkout-on-write hook, semantic diff/merge provider registration, sparse-sync payload requests". Add it to tool_consumes of editor-architect, editor-ui-framework, graph-editor-framework, world-data-model, gameplay-data and ci-cd-automation. Record in `C-EDHOST` or `C-VCS` that every asset editor must register a diff provider.

### K-TOOLS-4 · major · dependency-error
- Target: milestones.json M1/M2/M5, C-EDCMD, C-EDHOST, C-GRAPH, C-COOK, indie-2d-tools, collaboration-version-control, ai-assisted-authoring
- Finding: (a) No milestone freezes or even drafts `C-EDCMD`, `C-EDHOST`, `C-GRAPH` or `C-COOK`, even though about 30 domain skills build tool logic against them from M1. (b) M1's exit claims "indie-2d-tools configuration builds", but milestone closure is proven only for indie-2d-client. `collaboration-version-control` (profile all, member of indie-2d-tools) joins at M2 and `ai-assisted-authoring` (member of indie-2d-tools) joins at M5. The M1 editor ships with no source control, and the claimed configuration is not closed. (c) No milestone uses a tools configuration or has a tooling exit criterion (multi-user, distributed cook, world build, on-device iteration), so tooling is never gated like runtime.
- Evidence: Output of `model.members('indie-2d-tools')` compared with the M1 skill list. Contract freezing is what makes parallel domain-editor work safe. Tool contracts churn the most.
- Proposed change: Add `C-EDCMD`, `C-EDHOST`, `C-GRAPH`, `C-COOK` (and the new `C-EDVIEW`/`C-VCS`) to M1 `contracts_draft`, and freeze them at M2. Move collaboration-version-control to M1. Make ai-assisted-authoring profile-gated (e.g. an `aaa` or new `genai` add-on) or move it earlier. Add a `tools_configuration` to each milestone (M1 indie-2d-tools, M2 standard-3d-tools, M3/M5 aaa-open-world-online-tools) and prove its closure in check.py. Add exit criteria for iteration latency (XC.ITER.metrics) and team-large pipeline features at M3/M5.

### K-TOOLS-5 · major · scale-down
- Target: procedural-generation (profiles `["openworld"]`), WLD.PCG.*, WLD.TOOL.pcg, WLD.ENV.foliage-placement, voxel-worlds
- Finding: procedural-generation is gated to `openworld` only, so PCG does not exist in indie-2d (roguelike and WFC dungeon generation), standard-3d-tools (PCG scatter for any 3D level), rts, racing or sandbox. voxel-worlds (sandbox) has no world generator. `WLD.PCG.grammars` (WFC class) is useful mainly in small 2D games, yet is unavailable there. vegetation-foliage (lite3d/std3d) lists procedural-generation as a contributor to `WLD.ENV.foliage-placement`, but PCG is missing from every lite3d/std3d configuration without openworld.
- Evidence: Printed configuration membership: PCG appears only in open-world-client and the three aaa-* configurations. Precedents include Spelunky/Dead Cells-class 2D generation, Townscaper WFC, Minecraft worldgen, and UE PCG used in linear games.
- Proposed change: Set procedural-generation profiles to `["min2d","lite3d","std3d"]`. Gate the heavy parts with capability-level tags (`WLD.PCG.runtime`, large-scale partition-aware generation → `openworld`). Add a worldgen capability for the sandbox profile (e.g. `WLD.VOX.generation`, owner voxel-worlds, contributor procedural-generation).

### K-TOOLS-6 · major · scale-down
- Target: tool-side capabilities in indie-2d-tools: ED.ARCH.pie-net, ED.WORLD.partitioned, PHY.TOOL.physics-asset, PHY.TOOL.tuning, CNT.IMP.usd/scans/splats/geospatial/caches/procedural/materialx, CNT.COOK.ml-assisted, ED.AI.*; configurations
- Finding: Capability-level profile gating was applied to runtime (VSM, clusters = std3d) but almost never to tools. The indie-2d-tools configuration therefore requires multiplayer PIE (no `online` profile), partition-aware world editing (no `openworld`), ragdoll/physics-asset and vehicle tuning editors, OpenUSD/MaterialX/photogrammetry/splat (X)/geospatial importers, and every emerging ED.AI capability. So tool scale-down is asserted, not proven. There is also no `minimal-tools`, `lite-3d-tools` or `online-*-tools` configuration, so the tools a card/narrative game needs, the mobile 3D editor path, and multiplayer PIE on its own are never proven closed.
- Evidence: The printed capability set of indie-2d-tools (714 capabilities). The brief requires tooling to scale down as well as runtime.
- Proposed change: Tag `ED.ARCH.pie-net` → `online`. Tag `ED.WORLD.partitioned` → `openworld`. Tag `PHY.TOOL.physics-asset` → `lite3d,std3d` and `PHY.TOOL.tuning` → `vehicles,lite3d,std3d`. Tag `CNT.IMP.scans/caches/usd/materialx/procedural` → `lite3d,std3d`, `CNT.IMP.splats` → `aaa`, `CNT.IMP.geospatial` → `openworld`. Gate `ED.AI.*` / `CNT.COOK.ml-assisted` behind an add-on. Add configurations `minimal-tools`, `lite-3d-mobile-tools` and `online-3d-tools`.

### K-TOOLS-7 · major · scale-down
- Target: ED.COLLAB.locking (profiles `["team-large"]`)
- Finding: File locking and checkout are tagged `team-large`, so no indie or standard tools configuration has them. Exclusive locks on unmergeable binary assets (textures, audio, FBX, packed levels) are the first collaboration need of a 3-person team on Git LFS or Perforce. Multi-user editing and farms are rightly team-large; locking is not. 00-design-principles §5 lists only multi-user, distributed cook and farms as team-large.
- Evidence: Git LFS file locking and Perforce exclusive checkout (`+l`) are standard in small studios. Unity Version Control and UE source control integrations enable locking by default for binary assets.
- Proposed change: Remove the `team-large` tag from `ED.COLLAB.locking`. Keep lock-contention analytics and ownership dashboards as a team-large sub-capability if desired.

### K-TOOLS-8 · major · missing-contract
- Target: C-EDCMD/C-EDHOST/C-GRAPH (L5, tool-only), modding-ugc, XC.EXT.mod-sdk, XC.EXT.ugc, GAM.SYS.building, RND.SHADER.untrusted
- Finding: All edit, undo and graph authoring infrastructure is L5 tool-only, and check.py forbids runtime code from consuming it. In-game creation tools (UGC level editors of the Roblox/Dreams/Mario Maker/Fortnite Creative class, player construction, photo-mode editing, in-client graph authoring for the UGC shaders `RND.SHADER.untrusted` already anticipates) must ship in client builds. They have no owner for runtime-side edit transactions, undo or selection, and no runtime graph-compile path. separately, `modding-ugc` has `tool_consumes: []`. `XC.EXT.mod-sdk` ("Mod SDK & tooling") escapes check.py's tool-logic rule because it is not named `.TOOL`. No capability covers producing a redistributable modder editor (stripping NDA console backends, middleware SDK licences and internal plugins, per BLD.REL.engine-distribution being engine-user oriented).
- Evidence: The Creation Kit, Source SDK, UEFN and Roblox Studio all ship an editor to end users. Dreams, Mario Maker and Fortnite Creative ship authoring inside the client. The `ugc` profile exists, but its authoring path is undefined.
- Proposed change: Add `C-EDIT` (L4, owner gameplay-architect or a new owner designated by editor-architect): "Runtime edit session: serializable commands, undo, selection, permissions and budgets for in-game creation". Make `C-EDCMD` a tool-side extension of it so commands are shared. Add `XC.EXT.mod-editor` ("Redistributable modder editor/SDK build: licence/NDA stripping, sandboxed tool plugins", owner modding-ugc, contributors packaging-release-patching, platform-architect, security-engineering, profile ugc). Give modding-ugc `tool_consumes: [C-EDCMD, C-EDHOST, C-COOK]`, and extend check.py's rule to capabilities whose name denotes tooling (`mod-sdk`).

### K-TOOLS-9 · major · omission
- Target: cinematics-sequencer, ANM.CINE, ANM.TOOL
- Finding: cinematics-sequencer consumes `C-EDCMD`/`C-EDHOST` but owns no tool capability. The sequencer editor itself (track and section editing, keyframing, binding to world entities, shot/sub-sequence hierarchy, take/recording of gameplay, mocap and virtual cameras, and review/playback) has no owner. The shared widget `ED.UI.curves-timeline` is a component, not the cinematic authoring tool. For AAA narrative games and virtual production, the sequencer editor is one of the largest tools.
- Evidence: UE Sequencer + Take Recorder + Virtual Camera, Unity Timeline + Recorder, and Frostbite/Decima cinematic editors (Guerrilla GDC 2017/2018 talks on Decima cinematic pipeline). Recording gameplay into sequences is standard.
- Proposed change: Add `ANM.TOOL.sequencer-editor` ("Sequencer authoring: tracks, bindings, shots/sub-sequences, keyframing, preview & scrub", owner cinematics-sequencer, contributor editor-ui-framework) and `ANM.TOOL.take-recorder` ("Recording gameplay, live-link mocap and virtual cameras into sequences", owner cinematics-sequencer, contributors asset-import-interchange, determinism-replay).

### K-TOOLS-10 · major · omission
- Target: spatial-audio-acoustics, cloth-deformables, character-rendering, crowd-simulation, voxel-worlds, localization-i18n, input-system, post-color-hdr, fluid-simulation, AUD.TOOL, UI.TOOL
- Finding: The principle "every user-facing runtime domain owns its `<DOMAIN>.TOOL`" is not applied to these domains. None of them has a tool capability or a `tool_consumes` path:
  - Acoustics: reverb-zone and occlusion authoring and precomputed-propagation baking. `AUD.SPAT.propagation` "precomputed wave" needs a cook step, but spatial-audio-acoustics consumes no `C-COOK`.
  - Cloth: weight/constraint painting and cloth asset setup.
  - Grooms: import and hair-card generation.
  - Crowds and traffic: zone and lane graph authoring, spawners.
  - Voxels: voxel/brush editing and pre-generated structures.
  - Localization: string-table editor, localization dashboard, in-context preview with pseudo-loc and overflow.
  - Input: action/context mapping editor and device preview.
  - Post and color: post volumes, grading/LUT authoring, HDR preview.
  - Fluids: simulation setup and cache baking.

  AUD.TOOL (1 capability) and UI.TOOL (1 generic "UI designer tool logic") are thin. There is no audio profiler/debugger (voice/bus visualization) and no UI preview across resolution, safe area, locale and input device, or data-binding debugging.
- Evidence: UE Chaos Cloth editor, Groom asset editor, MassEntity ZoneGraph editor, Localization Dashboard, Enhanced Input editors, Project Acoustics / Steam Audio baking. Wwise/FMOD profilers are standard. Unity UI Builder and UE UMG designer offer multi-resolution preview.
- Proposed change: Add owned tool capabilities `AUD.TOOL.acoustics` (spatial-audio-acoustics; add `C-COOK`, `C-EDCMD`, `C-EDHOST`/`C-EDVIEW` to tool_consumes), `AUD.TOOL.profiler` (audio-architect), `PHY.TOOL.cloth` (cloth-deformables), `RND.TOOL.groom` (character-rendering, aaa), `GAM.TOOL.crowd-lanes` (crowd-simulation), `WLD.TOOL.voxel` (voxel-worlds), `UI.TOOL.localization` (localization-i18n), `INP.TOOL.actions` (input-system), `RND.TOOL.post-grading` (post-color-hdr), `PHY.TOOL.fluids` (fluid-simulation), `UI.TOOL.preview` and `UI.TOOL.binding-debug` (ui-architect). Add a check.py rule: every runtime skill whose domain has a player-visible or designer-tuned output either owns a `.TOOL` capability or declares an explicit `no-authoring` justification.

### K-TOOLS-11 · major · overlap
- Target: ED.WORLD.preview-scenes (world-editor-viewport), ED.UI.asset-editor-host / ED.UI.thumbnails (editor-ui-framework), RND.ARCH.editor-rendering (render-architect), C-EDHOST ("preview-scene registration")
- Finding: Isolated preview scenes and thumbnails are claimed by three owners: world-editor-viewport owns "Isolated preview scenes & asset inspection viewports", editor-ui-framework owns the asset-editor host "(tabs, preview, viewers)", thumbnails and the contract clause "preview-scene registration", and render-architect owns "preview scenes & thumbnails". No ownership pattern resolves which skill creates the preview world, which renders it, and which registers it.
- Evidence: The capability names quoted above. Every asset editor (material, animation, VFX, physics asset, audio) depends on this surface, so three agents would write the same subsystem.
- Proposed change: Apply the "policy vs implementation" split explicitly. world-editor-viewport owns preview-world creation and lifetime (ED.WORLD.preview-scenes, exposed through `C-EDVIEW`). editor-ui-framework owns only the embedding of a preview panel and thumbnail caching. render-architect keeps only editor render features (picking, outlines, editor primitives). Rename RND.ARCH.editor-rendering to drop "preview scenes & thumbnails", and remove "preview-scene registration" from `C-EDHOST`.

### K-TOOLS-12 · major · obsolete-assumption
- Target: legacy-patterns.json (L23, L24 are the only tool-side entries)
- Finding: The anti-legacy catalogue covers runtime thoroughly but has only two tool patterns. It misses the editor legacies that phase-2 agents are most likely to copy by default:
  - Modal, blocking editor operations on the editor main thread: synchronous import, save, shader compile, lighting build and asset open.
  - Whole-object snapshot undo buffers.
  - Monolithic binary level and asset files whose only collaboration model is exclusive locks.
  - Editor state stored as runtime objects with editor-only fields compiled into the same types (the WITH_EDITORONLY_DATA pattern). L23 covers only linking into shipping builds.
  - Full re-cook or re-bake after small edits, instead of region invalidation.
  - A single editor process that crashes on a plugin or tool fault.
- Evidence: UE's blocking FScopedSlowTask and shader-compile stalls, and the one-file-per-actor retrofit (UE5 OFPA) done to fix binary-map collaboration. The editor process-model question is already open as B16.
- Proposed change: Add L28 "Modal/blocking editor operations" (justification owner editor-architect). Add L29 "Snapshot-based undo" (editor-architect). Add L30 "Monolithic binary scene/asset files" (world-data-model). Add L31 "Editor-only data fields in runtime types" (reflection-metadata / editor-architect). Add L32 "Full rebake on local edit" (content-pipeline-architect). Add detection hints for each.

### K-TOOLS-13 · minor · maturity-error
- Target: ED.COLLAB.multiuser (E), docs/06-gap-analysis A2
- Finding: "Multi-user concurrent editing" is labeled established, while gap A2 states that editor architecture for 100+ concurrent editors is "few talks; most knowledge is proprietary and folklore". Session-based multi-user editing (UE Concert, used in virtual production at around 10 users) is established. Conflict-free concurrent editing of a shared world at 100–1000 people (CRDT/OT, as listed in the skill's expertise) is emerging at best. So the non-established part escapes the radar.
- Evidence: UE Multi-User Editing documentation limits it to small sessions. CRDT editing of scene data is published mostly outside games (Figma multiplayer, Autodesk/Omniverse Nucleus live layers).
- Proposed change: Split into `ED.COLLAB.multiuser` (session-based, E, team-large) and `ED.COLLAB.concurrent-world` (conflict-free concurrent world editing at studio scale, M, team-large, radar entry with fallback "cell/actor-granular locks + one-file-per-object").

### K-TOOLS-14 · minor · wrong-boundary
- Target: physics-tools, PHY.TOOL.*, PHY.TOOL.fracture
- Finding: physics-tools is a separate tool-kind skill that owns six physics tool capabilities. This contradicts the principle stated in §4 ("domain editor = domain tool logic + editor host", with the domain skill owning `<DOMAIN>.TOOL`), and it applies the principle inconsistently even within physics: fracture authoring stays with destruction-fracture. `PHY.TOOL.tuning` (vehicle/controller tuning) and `PHY.TOOL.2d-shapes` require vehicle-physics and physics-2d literature. §4 and §8 record no justification for the exception.
- Evidence: The capability owners and the 00-design-principles §4 wording.
- Proposed change: Either move `PHY.TOOL.tuning` to vehicle-physics/character-physics and `PHY.TOOL.2d-shapes` to physics-2d, keeping physics-tools for cross-cutting physics tooling (visual debugger/recorder, simulate-in-editor, collision authoring, physics-asset), or record the exception in §8 with its reason (shared PVD-class recorder and editor expertise).
