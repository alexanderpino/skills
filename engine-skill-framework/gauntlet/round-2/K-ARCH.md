# K-ARCH — Engine Architecture Critic, round 2 (blind)

Scope: architectural completeness and subsystem boundaries. `check.py` is green (0 errors, 0 warnings). Every finding below is something the gate cannot see.

### K-ARCH-1 · blocker · omission
- Target: RES.MGMT (missing `RES.MGMT.arbitration`), resource-streaming-architect, RND.MEM.residency, C-RES, C-GPUMEM, texture-streaming-vt, virtualized-geometry-lod, ray-tracing-infrastructure, audio-dsp-mixing
- Finding: The cross-pool memory arbiter has no capability and so no owner. `RND.MEM.residency` says "Residency mechanism & budget reporting (policy in RES.MGMT.arbitration)", but `RES.MGMT.arbitration` does not exist. The RES.MGMT area holds only `handles, requests, dependencies, streaming, fallbacks, no-stall, reload, gpu-requests, pipeline`. The rationale relies on this arbiter in three places: 00 §4 ("Residency policy belongs to the cross-pool arbiter in resource-streaming-architect"), the stance table in 00 §6 ("cross-pool arbitration under one physical budget") and 06 gap A14. The M3 exit criterion is also measured "within the arbitration budget". As the data stands, every pool owner (texture/VT, cluster pages, shadow VSM pages, BVH/AS, audio streaming, animation) runs its own eviction against its own budget. That is exactly the "independent streaming pools that compete" pattern the stance forbids.
- Evidence: On UMA consoles and portables, texture, geometry, BVH and audio share one physical pool. UE5 shipped titles still show VT/Nanite/VSM pool contention, and Frostbite and Decima streaming talks describe central budget arbitration as the fix. The check proves only that each capability has one owner. It cannot notice a capability that the text points to but the data does not contain.
- Proposed change: Add `RES.MGMT.arbitration` "Cross-pool residency arbiter: one physical budget (CPU+GPU+UMA) split across registered pools by priority/deadline, pressure signals, shrink-by-deadline requests, per-tier policy", owner `resource-streaming-architect`, contributors `gpu-memory-resources, texture-streaming-vt, virtualized-geometry-lod, ray-tracing-infrastructure, audio-dsp-mixing, memory-performance, performance-architect`. Make `C-GPUMEM` residency obey `C-RES` pressure requests: add a `gpu-memory-resources` consume of `C-RES` at the residency module, or invert it through a registration hook in C-RES. Add a gate rule: any capability ID mentioned in a capability name must exist.

### K-ARCH-2 · blocker · wrong-boundary
- Target: platform-console (platforms), check.py implementer closure, C-RHI, configurations with `console`
- Finding: `platform-console` is tagged `platforms: ["pc"]`. It therefore joins every pc build, including the pc-only tools, `xr-pc-client` and `rts-3d-massim-client`. At the same time, no configuration that lists `console` has any skill scoped to console. Console builds have no `PLAT.CON.rhi-backends` implementer of C-RHI and no console suspend, user-model or OS-memory integration. The gate stays green because the implementer check is config-wide (`any(cid in implements for x in members)`), not per platform. Design principles §4 claims per-platform closure ("check.py proves that every configuration contains one for each of its platforms"), and that claim is false.
- Evidence: `in_configuration` filters by platform intersection, and the `needs_implementer` test ignores which platforms each implementer covers. `rhi-d3d12` (pc), `rhi-vulkan` (pc/mobile/xr-standalone) and `rhi-metal` (pc/mobile) implement C-RHI with no console platform. `standard-3d-client`, `open-world-client` and `aaa-open-world-online-client` (pc+console) pass only because the pc backends satisfy the config-wide check. NDA access classes (`PLAT.PAL.confidential-extensions`) would also be granted to every pc build agent.
- Proposed change: Set `platform-console.platforms = ["console"]`. Change the gate so that, for each `needs_implementer` contract and each platform `p` of the configuration, there is a member implementing it with `p ∈ platforms` (or `platforms is None`). Add a selftest mutation that re-tags a console skill.

### K-ARCH-3 · major · obsolete-assumption
- Target: CORE.FRAME.pipelining, CORE.FRAME.phases, frame-orchestration, render-architect (purpose), legacy L01/L03
- Finding: The capability that defines frame pipelining is "Frame pipelining with a dedicated game thread and a dedicated render thread". That is legacy pattern L03, stated as the design and owned by the skill that justifies L01. `CORE.FRAME.phases` also reads "Tick phases, sync points & phase barriers", which is the "fixed sequence of tick groups with barriers" named as legacy in 00 §6. `render-architect`'s purpose lists "render threading" as its own concern. Meanwhile `RND.GPU.recording` (gpu-platform-architect) says "no dedicated render thread unless ... by ADR". Two owners' texts disagree, and the capability text is what the phase-2 SKILL.md is generated from.
- Evidence: 00 §6 row 2 ("No fixed game, render or RHI threads"), legacy L03, C-FRAME ("the minimal set of named global sync points ... from which ordering is derived"). Dependency-driven overlap is the approach in production: Naughty Dog's fiber job system (Gyrth, GDC 2015), Destiny's job-based renderer (Tatarchuk, GDC 2015), Unity DOTS. UE's GT/RT/RHIT split is the reference being rejected.
- Proposed change: Rename `CORE.FRAME.pipelining` to "Frame pipelining across simulation, render-extract, GPU submission and present as task-graph stages (no fixed game/render thread; dedicated threads only via thread inventory + ADR)". Rename `CORE.FRAME.phases` to "Named global sync points (minimal set) & phase declarations; barriers only by ADR". Remove "render threading" from the `render-architect` purpose, or replace it with "render work decomposition into tasks".

### K-ARCH-4 · major · obsolete-assumption
- Target: gameplay-architect (purpose), GAM.FW.control, C-GAME, legacy L06
- Finding: The `gameplay-architect` purpose reads "rules, players and possession, ...". It is the justification owner of L06 ("Possession / controller-pawn model by habit"). Its own capability `GAM.FW.control` and C-GAME ("data-oriented control binding (input source or AI → controlled entity)") reject possession. The purpose is the text a phase-2 agent reads first, so this seeds the Actor→Pawn→Controller model into the gameplay framework.
- Evidence: 00 §6 row 5, L06. Possession does not fit RTS (multi-unit selection), card, colony-sim or MMO (server-side AI and player symmetric control) games.
- Proposed change: Change the purpose to "Gameplay framework: rules and session state, control binding as data (control model per game by ADR), extension points and game-module structure, game flow and transitions, local players."

### K-ARCH-5 · major · wrong-owner
- Target: RND.RECON.motion-vectors, post-color-hdr, reconstruction-upscaling, C-TEMPORAL
- Finding: "Motion vector, jitter & history contract" is owned by `post-color-hdr`. The contract that exposes it (`C-TEMPORAL`) is owned by `reconstruction-upscaling`, whose purpose claims "the motion-vector/jitter/history contract". The contract owner does not own the capability behind it, and the post/color skill owns a contract obligation that it does not provide. Every moving-surface producer (deformation-skinning `ANM.DEF.motion-vectors`, vfx, terrain, water, UI/HUD separation for frame generation) would route its obligations to the wrong agent.
- Evidence: TAA, DLSS/FSR/XeSS and frame generation all consume the same MV/jitter/reactive-mask inputs (FSR 2/3 and DLSS integration guides). In every production engine this lives with the TAA/upscaler owner, not with tonemapping.
- Proposed change: Set the owner of `RND.RECON.motion-vectors` to `reconstruction-upscaling`, with contributors `post-color-hdr, deformation-skinning, geometry-pipeline`.

### K-ARCH-6 · major · overlap
- Target: RND.ARCH.instance-data (render-architect), RND.GEO.gpu-scene (geometry-pipeline), C-INSTANCES
- Finding: Two owners hold the same responsibility under different wording. `render-architect` owns "GPU instance data layout & delta upload". `geometry-pipeline` owns "GPU scene & instance data management" and the contract `C-INSTANCES` ("instance data layout shared with the ray-tracing instance builder ... batched add/remove/update with delta upload"). Both agents would write the persistent instance buffer layout and upload path. `ray-tracing-infrastructure` depends on that layout.
- Evidence: 00 §6 row 8 places the persistent instance scene in one place. C-INSTANCES already specifies the layout and delta upload.
- Proposed change: Delete `RND.ARCH.instance-data`, or reword it as a policy with no layout ("Render-scene → instance-scene mapping rules"). Keep layout and delta upload in `RND.GEO.gpu-scene`, and add `render-architect` and `ray-tracing-infrastructure` as contributors.

### K-ARCH-7 · major · scale-down
- Target: platform-desktop (platforms, purpose), NET.SRV.host-os (dedicated-server), configurations with target server / headless-client on `server-host`
- Finding: No platform-backend skill is a member of any `server-host` configuration (`online-3d-server`, `online-3d-bot-client`, `sandbox-online-server`, `indie-2d-online-moddable-server`, `aaa-open-world-online-server` all list `plat: []`). `platform-desktop`'s purpose claims "server host OS", but it is scoped `["pc"]`. The PAL implementation for Linux/ARM64 container hosts is owned by `dedicated-server` (`NET.SRV.host-os`), a netcode expert with no PAL backend slot, and C-PAL requires that "platform code lives only in the PAL or in a registered platform backend slot". Either server builds have no OS backend, or a netcode agent writes PAL code, which breaks the PAL boundary.
- Evidence: Server-host OS concerns are PAL concerns: io_uring, cgroups CPU quotas and CPU-topology discovery inside containers, NUMA on server SKUs, signal handling, and ARM64 Graviton-class hosts. They differ from desktop Linux and belong with the PAL expertise.
- Proposed change: Either add `server-host` to `platform-desktop.platforms` and move `NET.SRV.host-os` to `platform-desktop` (contributor `dedicated-server`), or create a small `platform-server-host` expert (platforms `["server-host"]`, targets `server, headless-client, tools`). Add a gate rule that every configuration has at least one platform-scoped member per platform.

### K-ARCH-8 · major · missing-contract
- Target: NET.SRV.zoning (dedicated-server, E), NET.ARCH.meshing (network-architect, X), WLD.PART.sim-tiers ("remote server regions", world-architect, E), WLD.PART.server, replication, C-WORLD, C-REP
- Finding: Multi-server worlds are split across three owners in three workstreams, and no contract joins them. Zoned/instanced handoff belongs to dedicated-server, seamless meshing to network-architect, and off-bubble "remote server regions" to world-architect. There is no contract for cross-server entity migration, authority transfer, region ownership maps or cross-boundary interest. C-REP and C-WORLD are both single-process. `WLD.PART.sim-tiers` is labeled E while it contains "remote server regions", which is the experimental meshing technique in disguise. For "future AAA open-world online games" this is the central large-scale boundary, and today it can be resolved only by ad hoc escalation to engine-architect.
- Evidence: SpatialOS postmortems, Star Citizen server meshing (CitizenCon 2023–2025) and New World/Dual Universe talks. Entity handoff touches replication (net-ID continuity), persistence (leases), world partition (cell ownership) and prediction (authority change mid-prediction), so it needs one contract.
- Proposed change: Add contract `C-SHARD` (L3, owner `network-architect`, requires `C-REP, C-WORLD, C-NET`): region/cell → server ownership map, entity migration protocol, authority transfer, cross-boundary relevancy. Consumers: `dedicated-server`, `replication`, `world-architect@C-SIGNIF`, `persistence-save?`. Move "remote server regions" out of `WLD.PART.sim-tiers` into `NET.ARCH.meshing` (X, radar), and make `NET.SRV.zoning` the established implementer of C-SHARD.

### K-ARCH-9 · major · missing-contract
- Target: ED.ARCH.agent-api (editor-architect, tools-only), crosscutting "agent operability", visual-debugging-tools, observability-telemetry, C-IPC
- Finding: The cross-cutting obligation "Expose debug state and controls through the agent/automation API with structured results" applies to every runtime skill, including server and headless builds. Its only owner is `editor-architect`, a tool-kind skill that ships in `targets: ["tools"]` only, and no contract carries it. Runtime skills cannot consume an L5 tool contract (the gate forbids it), so the obligation cannot be met in the builds where agents most need it: device, server, soak and bot runs. For a framework built to be operated by ~140 autonomous agents, the runtime introspection and control surface is critical infrastructure.
- Evidence: Structured automation and control protocols (UE Remote Control API and Gauntlet, Unity Test Framework remote, the Chrome DevTools Protocol pattern) always have a runtime-resident server side. `C-IPC` covers transport only, `C-DEVUI` covers the human UI only.
- Proposed change: Add contract `C-AGENTAPI` (L2 or L3, runtime, owner `visual-debugging-tools` or `observability-telemetry`, requires `C-IPC, C-REFL`): command/query registry, structured results, state snapshots, dev-only port security. Move the runtime half of `ED.ARCH.agent-api` to that owner. Keep editor bindings in `editor-architect` through `tool_consumes`. Re-own the crosscutting "agent operability" concern to the runtime owner.

### K-ARCH-10 · major · dependency-error
- Target: C-RT (requires C-RSCENE), ray-tracing-infrastructure (parent gpu-platform-architect), spatial-audio-acoustics (C-RT?), render-validation
- Finding: C-RT is placed as GPU-platform infrastructure: the lead is `gpu-platform-architect`, and 00 §8 says it serves "every renderer tier". Yet C-RT `requires C-RSCENE`, and `ray-tracing-infrastructure` consumes `C-RSCENE` and `C-INSTANCES` (render-architect subtree). The GPU-platform subtree therefore depends upward on the render-feature subtree, which contradicts the lead split justification. Any non-render ray-query consumer, such as `spatial-audio-acoustics` for GPU acoustic propagation or future AI visibility, must drag in the whole render scene. The acceleration-structure mechanism and the render-scene population of TLAS instances are two different things fused into one contract.
- Evidence: DXR and Vulkan RT make AS build/query a device-level service. Audio (Steam Audio Radeon Rays, Project Acoustics bakes) and physics/AI queries use BVHs that have nothing to do with the render scene. 00 §8 row 1 names "ray queries" under the GPU platform lead.
- Proposed change: Split C-RT into `C-RTAS` (L2/L3 under gpu-platform, requires `C-RHI, C-GPUMEM`: AS build/refit/compaction, query API, software backend) and a render-side binding owned in the render-architect subtree (TLAS population from `C-INSTANCES`/`C-RSCENE`, hit/material binding). Or keep one skill and let only the `C-RSCENE`-dependent module carry `@`-attributed deps. Retarget `spatial-audio-acoustics` to `C-RTAS?`.

### K-ARCH-11 · major · missing-contract
- Target: anti-cheat-integrity (provides nothing), NET.PRED.input-commands, NET.SRV.transactions, GAM.SYS.predicted-abilities, character-movement
- Finding: `anti-cheat-integrity` is a runtime expert that offers server-authoritative validation patterns (movement, hits, economy), rate limiting, anomaly signals and score validation to other skills, but it provides no contract. Principle §1.3 says "Anything it offers to others is a contract". Movement, abilities, hit resolution and transactions are listed as contributors in the opposite direction (anti-cheat contributes to *their* capabilities), so the validation hooks will be designed ad hoc inside each gameplay skill. Anti-cheat then reviews but cannot bind them.
- Evidence: Server-side validation needs a uniform hook surface: movement-delta validators, fire/hit rewind validation and economy idempotency checks that feed a common anomaly/telemetry sink. Valorant (Riot, "Peeking into Valorant's netcode" and anti-cheat posts) and Overwatch GDC 2017 describe centralized validation plus signal pipelines.
- Proposed change: Add `C-INTEGRITY` (L3, owner `anti-cheat-integrity`, requires `C-NET, C-ID`): validator registration per authoritative action, anomaly-signal sink, rate-limit policy, client-middleware boundary. Consumers: `character-movement?`, `gameplay-systems-toolkit?`, `dedicated-server`, `prediction-rollback?`, `platform-services?` (score submission).

### K-ARCH-12 · major · dependency-error
- Target: C-PREDICT (requires C-REP), prediction-rollback, NET.PRED.rollback, NET.PRED.lockstep
- Finding: `C-PREDICT` requires `C-REP`, and `prediction-rollback` consumes `C-REP` unconditionally. Deterministic lockstep (RTS) and P2P rollback (fighting games, GGPO-class) exchange only tick-stamped inputs over `C-NETLINK` and never replicate state. Every lockstep or rollback configuration is forced to build the full replication module: interest management, delta compression, RPCs, net IDs. This contradicts "scale down as well as up" and hides a wrong boundary: input-only netcode depends on state-replication machinery.
- Evidence: GGPO/rollback architecture (Pusch, "Rollback networking in Mortal Kombat and Injustice 2", GDC 2018) and AoE/StarCraft-class lockstep (Bettner & Terrano, "1500 Archers", GDC 2001) use no state replication. `rts-2d-massim-client` and `rts-3d-massim-client` currently pull in replication only because of this edge.
- Proposed change: Change C-PREDICT to require `C-NETLINK, C-DET, C-SNAPSHOT, C-INPUT`. Make `C-REP` optional (`C-REP?`) in `prediction-rollback.consumes`, attributed to the client-prediction/reconciliation module (`C-REP@...`) and not to the rollback/lockstep module.

### K-ARCH-13 · major · other
- Target: ARCH.ORG.adjudication, ARCH.ORG.critic-calibration, ARCH.ORG.triage (program-orchestration)
- Finding: The skill that schedules work, sequences integration and is measured on milestone throughput also owns adjudication of rejected critic findings and critic calibration (seeding and recall thresholds). This puts the "builder does not get the last word" and "independent oracles" principles (00 §6 last row, PROTOCOL adjudication, QA.AGENT.oracle-independence) inside the party with the strongest incentive to converge early. `test-architect` owns oracle independence for code, but independence for architecture findings sits with the scheduler.
- Evidence: Separation of duties is standard in safety-critical V&V (DO-178C independence, ISO 26262 confirmation reviews). The protocol itself treats adjudication as a check on the builder. With ~140 agents, program-orchestration is the de facto builder at program level.
- Proposed change: Move `ARCH.ORG.adjudication` and `ARCH.ORG.critic-calibration` to `architecture-governance`, or to `test-architect` beside `QA.AGENT.*`. Keep `program-orchestration` as the contributor for scheduling. Add "Adjudicating findings" to program-orchestration's non-responsibilities.

### K-ARCH-14 · major · wrong-boundary
- Target: non-responsibilities of network-architect, dedicated-server, network-transport, water-ocean, navigation-pathfinding; purposes of spatial-audio-acoustics, build-release-architect
- Finding: Several non-responsibility routes and purposes contradict the capability owners. Agents route work by NR, so these send change requests to the wrong skill:
  - `network-architect` sends "Matchmaking services" to `platform-services`, but `PLAT.SVC.matchmaking` is owned by `online-services-liveops`.
  - `dedicated-server` sends "Fleet operation" to `platform-services`, and `NET.SRV.orchestration` lists `platform-services` as contributor. Fleet hosting is third-party or own backend (`online-services-liveops` / `external:backend`), not first-party.
  - `network-transport` sends "Relay service operation" to `platform-services`. It should go to `online-services-liveops` or `external:backend`.
  - `water-ocean` sends "Buoyancy dynamics" to `character-physics`, but `PHY.DYN.buoyancy` is owned by `rigid-body-dynamics`. `WLD.ENV.buoyancy` (a water query service) also lists `character-physics` as contributor.
  - `navigation-pathfinding` sends "Crowd avoidance" to `crowd-simulation`, but it owns `GAM.AI.local-avoidance` (ORCA/RVO) itself, and `crowd-simulation`'s purpose also claims "crowd avoidance". This is a real overlap hidden by wording.
  - `spatial-audio-acoustics`' purpose starts "Panning and distance", but `AUD.DSP.panning` is owned by `audio-dsp-mixing`.
  - `build-release-architect`'s purpose claims "orchestration of the code → content → package pipeline", but `BLD.CI.orchestration` is owned by `ci-cd-automation`.
- Evidence: See the listed data. 00 §1 says non-responsibilities exist to "prevent overlapping agents". The gate checks only that NR targets exist, not that they own the named work.
- Proposed change: Retarget the three platform-services NRs to `online-services-liveops` or `external:backend`. Set the water-ocean NR to `rigid-body-dynamics` and the `WLD.ENV.buoyancy` contributor to `rigid-body-dynamics` (rename the cap id to `water-queries`). Remove "crowd avoidance" from crowd-simulation's purpose and state "local avoidance → navigation-pathfinding; flow-field/mass avoidance → crowd-simulation". Drop "Panning and distance" from spatial-audio's purpose. Reword build-release-architect's purpose to "pipeline architecture (execution by ci-cd-automation)". Add a gate lint: an NR target must own or contribute to at least one capability whose name shares a keyword with the NR text, flagged for review.

### K-ARCH-17 · minor · wrong-boundary
- Target: modding-ugc and plugin-system (parent api-lifecycle-migration), anti-cheat-integrity (parent security-engineering)
- Finding: Runtime experts are parented under process cross-cutting skills whose workstream differs from their own. `modding-ugc` is in workstream gameplay under the governance skill, and `anti-cheat-integrity` is in workstream online under quality. 00 §2 says intra-subtree disputes are settled by the subtree's lead. That puts VFS, scripting and packaging disputes of modding-ugc before an API-versioning policy skill, and anti-cheat versus replication disputes before a threat-model skill. Neither has the runtime coupling to decide them. `plugin-system` is coupled to C-MOD (core-runtime-architect), not to versioning.
- Proposed change: Reparent `plugin-system` to `core-runtime-architect`, `modding-ugc` to `gameplay-architect` (or `content-pipeline-architect`), and `anti-cheat-integrity` to `network-architect`. Keep api-lifecycle-migration and security-engineering as reviewing contributors.
