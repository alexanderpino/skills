# K-SIM · Physics & Simulation Critic · Round 2 findings

### K-SIM-1 · major · obsolete-assumption
- Target: CORE.FRAME.pipelining (frame-orchestration), legacy-patterns L03, C-FRAME
- Finding: The capability that defines how simulation, render and GPU work overlap is worded "Frame pipelining with a dedicated game thread and a dedicated render thread". That is the pattern the framework itself lists as legacy L03 ("Game-thread / render-thread dichotomy … render work as tasks; dedicated threads only by ADR"), and it contradicts 00-design-principles ("The frame is a task graph"). The simulation schedule (CORE.FRAME.sim-schedule, PHY.ARCH.stepping, PHY.ARCH.async) sits on top of this capability. An agent implementing frame-orchestration from this label would build a two-thread engine and put physics, animation and gameplay on "the game thread" by default.
- Evidence: Destiny's task-graph frame (Tatarchuk/Genova, GDC 2015 "Multithreading the Entire Destiny Engine"). Naughty Dog's fiber job system (Gyrich, GDC 2015 "Parallelizing the Naughty Dog Engine Using Fibers") has no dedicated game or render thread. Frostbite's frame graph (O'Donnell, GDC 2017). The framework's own L03 and the task-graph principle.
- Proposed change: Rename CORE.FRAME.pipelining to "Frame pipelining across simulation, render-build and GPU stages expressed as overlapping task-graph frames; any dedicated thread only by ADR (L03)". Add a check.py rule that no capability name matches a legacy-pattern detection string without an ADR reference.

### K-SIM-2 · major · overlap
- Target: WLD.ENV.water-interaction (water-ocean), PHY.FLUID.shallow (fluid-simulation), water-ocean.non_responsibilities, WLD.ENV.buoyancy, PHY.DYN.buoyancy
- Finding: Two owners hold the same technique. "Local interactive water surface simulation" (water-ocean) and "Shallow-water / heightfield water simulation" (fluid-simulation) are both heightfield/shallow-water solvers, and each lists the other as a contributor. water-ocean's expertise also lists "shallow-water models" while its non-responsibility says "Fluid solvers → fluid-simulation". Buoyancy has three conflicting pointers. PHY.DYN.buoyancy is owned by rigid-body-dynamics. water-ocean's non-responsibility sends "Buoyancy dynamics" to character-physics. WLD.ENV.buoyancy names character-physics as contributor. Because fluid-simulation is `aaa`-only, a std3d water agent will also build its own solver, which makes the duplicate a certainty.
- Evidence: A shallow-water interactive surface is the same solver class whether it is used for boat wakes or a flooding simulation (e.g. the "From Dust" shallow-water model; Cities: Skylines water simulation; Horizon Forbidden West local water interaction). Ownership should split on *surface query and rendering* versus *solver*, not on "local" versus "shallow".
- Proposed change: Choose one owner for the heightfield solver. Recommended: water-ocean owns PHY.FLUID.shallow merged into WLD.ENV.water-interaction (it ships in lite3d/std3d). fluid-simulation keeps volumetric and particle solvers only. Fix water-ocean's non-responsibility to "Buoyancy dynamics → rigid-body-dynamics". Rename WLD.ENV.buoyancy to "Water query service (C-ENV provider)" with contributors rigid-body-dynamics and vehicle-physics, not character-physics.

### K-SIM-3 · major · scale-down
- Target: fluid-simulation.profiles, PHY.FLUID.*, capability map (no cellular/2D fluid capability)
- Finding: Fluids are gated on `aaa`, a production-scale add-on, not a feature. As a result, no min2d, lite3d or plain std3d configuration can include any fluid solver. There is also no capability at all for the fluid and material simulation class that defines whole 2D and sandbox genres: cellular automata or falling sand, grid-based liquids and gases, and heat or pressure diffusion.
- Evidence: Noita (per-pixel falling-sand simulation, GDC 2019 "Exploring the Tech and Design of Noita"), Oxygen Not Included (gas/liquid/heat grid), Terraria liquids, Dwarf Fortress fluids. None of these are AAA; all are min2d- or sandbox-scale. The framework's own principle, "not every configuration needs every subsystem", argues for gating on features, not budget.
- Proposed change: Change fluid-simulation.profiles to ["min2d","lite3d","std3d"], included on demand (or gate it on `sandbox`/`massim` in addition to `aaa`). Add PHY.FLUID.cellular "Grid/cellular material & fluid simulation (falling-sand, liquid/gas/heat grids), 2D-capable, deterministic" (E) owned by fluid-simulation, with contributor physics-2d. Add a configuration or reference game that exercises it (e.g. extend indie-2d-client or add a 2D sandbox configuration).

### K-SIM-4 · major · scale-down
- Target: procedural-generation.profiles, voxel-worlds, configurations sandbox-online-server, rts-2d-massim-client, indie-2d-client
- Finding: procedural-generation is gated on `openworld` only. So the sandbox configuration (sandbox-online-server: std3d+sandbox+online), whose defining feature is infinite generated voxel terrain, does not contain the PCG skill. 2D roguelike and colony games (min2d, massim) have no world-generation owner either. voxel-worlds owns no generation capability and consumes no generation contract, so a voxel agent will build its own generator outside the deterministic PCG framework (WLD.PCG.framework).
- Evidence: Minecraft-class sandbox generation is server-authoritative, deterministic from a seed, and runs at chunk stream-in. That is exactly WLD.PCG.runtime and needs C-DET. Roguelike and colony generation (Spelunky, RimWorld, Dwarf Fortress) is min2d/massim scale.
- Proposed change: Set procedural-generation.profiles to ["min2d","lite3d","std3d"] (on demand) or at least add `sandbox` and `massim`. Make procedural-generation provide a contract (C-PCG: seeded, deterministic generation requests per cell/chunk, headless-capable) consumed by voxel-worlds (required under sandbox) and terrain/vegetation (optional). Add WLD.VOX.generation or make voxel-worlds an explicit contributor to WLD.PCG.runtime.

### K-SIM-5 · major · dependency-error
- Target: crowd-simulation.consumes, GAM.AI.mass, GAM.AI.traffic, configurations rts-2d-massim-client / rts-3d-massim-client
- Finding: crowd-simulation consumes only C-NAV, C-ECS and C-SPATIAL. It does not consume C-DET, even though both massim configurations are `online` RTS games whose netcode model is deterministic lockstep (NET.PRED.lockstep), so unit movement must be bit-deterministic. It does not consume C-SIGNIF, even though its core capability is "Mass-agent simulation & LOD" and C-SIGNIF is defined as the input to every domain's LOD policy. It does not consume C-PHYS (agents against physics obstacles, ragdoll hand-off) or C-SNAPSHOT/C-PREDICT (rollback of agent state). check.py passes only because none of these edges are declared.
- Evidence: RTS lockstep with thousands of units (AoE II, "1500 Archers on a 28.8", Bettner & Terrano, GDC 2001; StarCraft II; Planetary Annihilation). UE Mass uses significance/LOD processors (UE MassAI/City Sample docs). Mass-agent LOD without the shared significance signal duplicates WLD.PART.sim-lod.
- Proposed change: crowd-simulation.consumes += ["C-DET","C-SIGNIF","C-PHYS?","C-SNAPSHOT?","C-TASK"]. Add a determinism-level declaration requirement ("lockstep-grade under massim+online") to crowd-simulation's G2 obligations. Add a massim determinism conformance scene to QA.SIM.golden-traces.

### K-SIM-6 · major · omission
- Target: PHY.ARCH.*, C-PHYS, vehicle-physics, WLD.MODEL.instancing, NET.SRV.density
- Finding: There is no capability or contract surface for (a) multiple independent physics worlds in one process, or (b) moving local simulation frames. Case (a) covers many match instances per server process (NET.SRV.density), editor preview worlds (physics-asset editor, simulate-in-editor), and level instances. Case (b) covers ship or train interiors where characters and loose bodies simulate relative to a moving vehicle, and nested physics grids for space games. C-PHYS describes one world ("Bodies, shapes, queries…"). PHY.CTRL.platforms covers only a controller riding a platform, not a full rigid-body sub-space.
- Evidence: Sea of Thieves ship interiors (Rare, GDC 2019 networking and physics talks). Star Citizen "physics grids"/zones for ship interiors. Space Engineers grids. UE Chaos supports multiple solvers per world. Jolt supports multiple PhysicsSystem instances and is used that way for server density. Without an owner, vehicle-physics, character-physics and dedicated-server will each invent incompatible approaches.
- Proposed change: Add PHY.ARCH.multi-world "Multiple physics worlds per process (per-instance, preview, server-density), handle scoping, per-world budgets" (E) owned by physics-architect, with contributors dedicated-server and world-data-model. Add PHY.ARCH.local-frames "Moving local simulation spaces (physics grids), transitions of bodies and controllers between frames, LWC interplay" (M) owned by physics-architect, with contributors vehicle-physics, character-physics, spatial-transforms, prediction-rollback. Extend C-PHYS summary with "world instances and local simulation spaces". Add a radar entry for local-frames.

### K-SIM-7 · major · missing-contract
- Target: vehicle-physics.provides, GAM.MOVE.transitions, GAM.AI.traffic, AUD (engine audio), INP.DEV haptics, character-physics.expertise
- Finding: vehicle-physics provides no contract, but several skills must drive it or read it. character-movement's "Mount & vehicle transitions" needs a seat/control API. Traffic LOD (GAM.AI.traffic, "physics vehicle → kinematic → abstract flow") needs drive commands and a state hand-off. Engine and tire audio needs telemetry (RPM, load, slip). Force feedback needs a steering-torque source. AI drivers need a control input. Characters have C-MOVE; vehicles have only raw C-PHYS bodies. Each consumer will therefore reach into vehicle internals or define an ad-hoc component layout. character-physics.expertise also still lists "vehicle dynamics" and "tire models", which blurs the character/vehicle split.
- Evidence: Production vehicle stacks expose a control and telemetry interface separate from the solver (e.g. UE Chaos Vehicles movement component inputs and outputs; the Forza/Assetto-style telemetry feeding audio and FFB). Engine audio (granular/RPM-driven) always consumes vehicle telemetry.
- Proposed change: Add contract C-VEHICLE (layer 3, owner vehicle-physics): "control inputs (throttle/brake/steer/collective…), seat and occupant attachment points, telemetry stream (RPM, load, slip, contact), FFB torque source, sim-tier hand-off (physics ↔ kinematic ↔ abstract)". It requires C-PHYS. Consumers: character-movement (C-VEHICLE?), crowd-simulation (C-VEHICLE?), audio-content-runtime (C-VEHICLE?), input-devices-haptics (C-VEHICLE?), ai-behavior-perception (C-VEHICLE?). Remove "vehicle dynamics" and "tire models" from character-physics.expertise.

### K-SIM-8 · major · omission
- Target: capability map (no projectile/ballistics capability), GAM.SYS.hit-detection, PHY.COL.queries, NET.PRED
- Finding: Projectiles and ballistics have no owner. That covers simulated projectiles with drag and gravity, many-projectile batching, CCD or sweep for fast projectiles, penetration and ricochet driven by physics materials, and server-side rewind validation of projectile hits. GAM.SYS.hit-detection covers hit/hurtbox authoring and resolution. PHY.COL.queries covers the query primitive. NET.PRED covers lag compensation in general. The projectile system, which is the most common physics-to-gameplay-to-netcode junction in shooters, falls between gameplay-systems-toolkit, collision-detection and prediction-rollback.
- Evidence: Battlefield-class ballistics (bullet drop, per-material penetration), "I Shot You First" (Halo: Reach, GDC 2011) on projectile vs hitscan networking, and the Overwatch GDC 2017 netcode talk on predicted projectiles. UE ships a dedicated ProjectileMovementComponent separate from character movement. Batched sweep queries are a known physics-throughput hotspot.
- Proposed change: Add GAM.SYS.projectiles "Projectile & ballistics simulation (batched sweeps, drag/gravity, penetration/ricochet by physics material, predicted projectiles, server-side rewind validation)" (E), owned by gameplay-systems-toolkit, with contributors collision-detection, prediction-rollback, physics-architect (materials) and anti-cheat-integrity. Add a non-responsibility on collision-detection pointing projectile logic to gameplay-systems-toolkit.

### K-SIM-9 · major · omission
- Target: profile `massim`, seed-map "large-scale simulation", GAM.*, CORE.FRAME.time
- Finding: The `massim` add-on ("RTS, colony, city, crowds") gates exactly one skill, crowd-simulation, and the brief term "large-scale simulation" maps only to WLD.PART.sim-lod and GAM.AI.mass. That leaves several simulation substrates of colony, city and factory games without an owner. The first is spatial field simulation: influence, heat, pollution, land-value and fire-spread grids. The second is network/flow simulation: power, water, logistics and conveyor graphs. The third is time acceleration with multi-tick catch-up under budget (CORE.FRAME.time covers dilation, not ×N fast-forward with guaranteed-deterministic sub-ticking). The fourth is snapshotting and saving very large simulation state. As things stand these become ad-hoc gameplay code in every game.
- Evidence: Factorio (deterministic lockstep, belt/fluid/electric network optimizations, FFF dev blogs). Cities: Skylines (traffic/utility/pollution grids). RimWorld and Dwarf Fortress (field and temperature simulation). Paradox titles (time acceleration). All are massim-class, and none are covered by crowd agents.
- Proposed change: Add an expert skill `systems-simulation` (parent gameplay-architect, profiles ["massim","sandbox"], workstream gameplay) owning: GAM.SIM.fields "Grid/field simulation substrates (diffusion, influence, cellular spread), SIMD/GPU-capable, deterministic" (E); GAM.SIM.networks "Flow networks (power, fluid, logistics, conveyors) with incremental solve" (E); GAM.SIM.time-accel "Time acceleration with budgeted multi-tick catch-up" (E, contributor frame-orchestration); GAM.SIM.scale-save "Large simulation-state snapshot/save" (E, contributor persistence-save). It consumes C-DET, C-ECS, C-TASK, C-SIGNIF? and C-SNAPSHOT?. Map "large-scale simulation" in seed-map to these capabilities too.

### K-SIM-10 · major · missing-contract
- Target: WLD.PART.sim-tiers, C-SIGNIF, vehicle-physics, rigid-body-dynamics, character-physics, crowd-simulation
- Finding: world-architect owns "Off-bubble simulation tiers (abstract/statistical sim, promotion/demotion, remote server regions)". But C-SIGNIF only publishes a tier and budget per entity. It defines no promotion/demotion protocol, meaning the state hand-off when an abstract entity becomes a full physics or animation participant and back. That hand-off includes placing a promoted vehicle on its lane at the correct velocity, resolving interpenetration on spawn-in, settling sleeping bodies, and collapsing a physics vehicle back to an abstract flow. Only physics-architect (optional), animation-architect, audio, AI and replication consume C-SIGNIF. vehicle-physics, character-physics, crowd-simulation and cloth do not. Tier transitions are where the visible bugs of open-world simulation live (pop, launches, cars falling through the road).
- Evidence: GTA/Watch Dogs-class traffic promotion. UE Mass LOD "representation" switching (actor ↔ ISM ↔ none) with explicit hydration/dehydration. X4 in-sector versus out-of-sector simulation. Every one of these needs a per-domain state-transfer protocol, not just a tier number.
- Proposed change: Extend C-SIGNIF with "tier-transition protocol: per-domain promote/demote handlers, state hand-off records, spawn-in validity (depenetration, grounding), hysteresis". Add PHY.ARCH.tier-transitions "Physics participation in simulation-tier promotion/demotion" (E) owned by physics-architect, with contributors vehicle-physics, character-physics and crowd-simulation. Add C-SIGNIF? to vehicle-physics, character-physics and crowd-simulation consumes.

### K-SIM-11 · major · omission
- Target: PHY.COL.cook, PHY.COL.*, voxel-worlds, WLD.ENV.terrain-deform, destruction-fracture, modding-ugc
- Finding: Collision building exists only as a cook-time step (PHY.COL.cook, "Collision data cooking", contributor asset-cook-processors). Nobody owns runtime or incremental collision generation for geometry that changes during play. That includes voxel edits (sandbox), runtime terrain deformation, destruction debris and damaged meshes, player-built structures, and UGC loaded without a cook. The shipping runtime of sandbox-online-server must rebuild chunk collision within a frame budget, and the owner is ambiguous between voxel-worlds (C-PHYS optional), terrain and collision-detection.
- Evidence: Teardown's voxel physics, and Minecraft/Valheim-class runtime chunk collision. Jolt and PhysX both provide runtime mesh and heightfield cooking APIs exactly for this case, with a cost profile (BVH build time) that needs budgeting and async placement.
- Proposed change: Add PHY.COL.runtime-build "Runtime/incremental collision generation for edited geometry (voxel chunks, deformed heightfields, debris, UGC), async and budgeted" (E) owned by collision-detection, with contributors voxel-worlds, terrain, destruction-fracture and modding-ugc. Make C-PHYS required (not optional) for voxel-worlds under `sandbox`.

### K-SIM-12 · minor · wrong-boundary
- Target: GAM.SYS.building, voxel-worlds.non_responsibilities, destruction-fracture.profiles, PHY.DEST.*
- Finding: The "structural integrity" of player constructions is placed in gameplay-systems-toolkit (GAM.SYS.building), and voxel-worlds points to it. Stress propagation and collapse is a simulation that produces fracture and debris, so it belongs with destruction. Meanwhile destruction-fracture is gated on std3d only, so the lite3d and sandbox configurations that most need collapse have no destruction owner.
- Evidence: Valheim, 7 Days to Die and Teardown use a structural stability simulation feeding physical collapse. Red Faction: Guerrilla (GDC 2010) handles structural stress inside the destruction system.
- Proposed change: Add PHY.DEST.structural "Structural integrity / load-path evaluation and collapse" (E) owned by destruction-fracture, with contributor gameplay-systems-toolkit. GAM.SYS.building keeps snapping and sockets. Set destruction-fracture.profiles to ["lite3d","std3d"] (on demand; pre-fractured tier on lite3d).

### K-SIM-13 · minor · omission
- Target: PHY.ARCH.*, PHY.CTRL.character, GAM.MOVE.modes, WLD.MODEL.planetary
- Finding: Nothing owns gravity and force fields: gravity volumes, non-uniform or radial gravity, explosion radial impulses and physics fields. Planetary worlds are on the map (WLD.MODEL.planetary, M), and they require arbitrary-up character controllers and non-uniform gravity on bodies, but neither character-physics nor rigid-body-dynamics declares it.
- Evidence: UE Chaos Fields (radial force, falloff, strain fields). Super Mario Galaxy-style gravity volumes. Planetary games (Outer Wilds, Starfield, KSP) need per-body gravity sources and arbitrary controller up-vectors.
- Proposed change: Add PHY.ARCH.fields "Gravity & force fields (volumes, radial/non-uniform gravity, impulse/explosion fields) applied to bodies, controllers and cloth" (E) owned by physics-architect, with contributors character-physics and vehicle-physics. Add "arbitrary up-vector / non-uniform gravity" to the PHY.CTRL.character name.

### K-SIM-14 · minor · missing-contract
- Target: C-PHYS.requires
- Finding: C-PHYS claims "snapshot/restore/resimulate participation" and determinism-dependent behavior, yet it requires only C-SPATIAL, C-FRAME and C-ID. The conformance suite for C-PHYS therefore has no declared dependency on the C-SNAPSHOT protocol or the C-DET rules it must satisfy, and an integrated middleware backend could be accepted as conformant without rewind support.
- Evidence: Layering permits it: C-DET is L1, C-SNAPSHOT is L2, C-PHYS is L3. PHY.ARCH.build-integrate lists "rewind" as decision evidence, and the contract should enforce it.
- Proposed change: C-PHYS.requires += ["C-SNAPSHOT","C-DET"]. Add a C-PHYS conformance item: "restore + resimulate N ticks reproduces state hash at the declared determinism level".

### K-SIM-15 · minor · other
- Target: legacy-patterns.json
- Finding: The anti-legacy catalogue has no simulation-specific entries, so G2 critics have no detector for the most common physics legacy. The first is simulation stepped by variable render delta. The second is per-body transform write-back callbacks, meaning an O(bodies) sync each frame instead of active-set or change-set output. The third is gameplay mutating the physics world or running synchronous scene queries in the middle of a step instead of through batched queries and deferred command buffers.
- Evidence: Gaffer on Games "Fix Your Timestep!" (author of record). Jolt's body-interface locking and batched APIs. PhysX 5 and Jolt active-body lists. The framework's own WLD.SPACE.change-sets and C-PHYS "handle-addressed, batched" queries define the modern stance, but nothing flags the old one.
- Proposed change: Add L28 "Frame-coupled variable-timestep simulation" (stance: fixed/declared step with interpolation per C-FRAME; owner physics-architect). Add L29 "Per-body sync callbacks and mid-step world mutation/queries" (stance: active-set/change-set output, batched queries, deferred commands; owner physics-architect).

### K-SIM-16 · minor · wrong-boundary
- Target: CORE.FRAME.sim-schedule contributors
- Finding: The canonical simulation phase order names physics-architect, animation-architect and network-architect as contributors, but not character-movement. character-movement's own purpose defines it as "the junction of input, physics, animation and netcode", and it owns the root-motion authority and resimulatable move API that the schedule must place (pre-physics move → physics → post-physics animation). gameplay-architect (GAM.FW.execution) is also missing.
- Evidence: The ordering of movement, root motion and physics is the canonical source of one-frame lag and jitter bugs (UE CharacterMovement / Mover 2.0 tick-ordering documentation).
- Proposed change: CORE.FRAME.sim-schedule contributors += ["character-movement","gameplay-architect"].

### K-SIM-17 · minor · maturity-error
- Target: PHY.FLUID.grid, radar "Particle & GPU fluids"
- Finding: "Grid-based smoke & fire" is labelled E and used as the radar fallback for M fluids, yet the radar's own evidence for real-time fluids is "Niagara Fluids (beta)". Gameplay-interactive, real-time grid smoke or fire in shipped titles is rare. Production use is mostly offline-baked flipbooks or VDB playback, and the established technique is VFX-grade baked volumes.
- Evidence: Shipped real-time use is limited to a few titles (e.g. PhysX Flow/Turbulence in select titles). Niagara Fluids and EmberGen are used predominantly for baking.
- Proposed change: Split PHY.FLUID.grid into "Baked/volume-cache smoke & fire playback" (E, owner vfx-particles via RND.VFX.volumes) and "Real-time interactive grid smoke & fire" (M, owner fluid-simulation, on the radar). Change the radar fallback to the baked variant.

### K-SIM-18 · minor · omission
- Target: QA.SIM.*, simulation-validation
- Finding: QA.SIM covers rigid-body stability, golden traces, netsim, animation and audio. It has no validation suites for vehicle dynamics (reference manoeuvres and tire-model correlation), cloth and soft-body stability, crowd and mass-agent throughput and determinism, or character-controller edge cases (step, slope, ledge, moving platforms). These are the systems where agent-produced changes regress silently.
- Evidence: Vehicle dynamics are validated against standard manoeuvres (ISO 3888 lane change, ISO 4138 steady-state circular). Controller conformance suites are standard practice (e.g. Jolt CharacterVirtual test scenes).
- Proposed change: Add QA.SIM.vehicles (contributor vehicle-physics), QA.SIM.deformables (cloth-deformables), QA.SIM.mass-agents (crowd-simulation, determinism-replay) and QA.SIM.controllers (character-physics, character-movement), each owned by simulation-validation, with oracles defined by the domain owner.
