# K-LEGACY · Round 2 findings (Anti-Legacy Critic, blind)

### K-LEGACY-1 · blocker · obsolete-assumption
- Target: CORE.FRAME.pipelining (frame-orchestration), render-architect (purpose "render threading"), RND.GPU.recording, L03, docs/00 §6 row 2
- Finding: `CORE.FRAME.pipelining` reads "Frame pipelining with a dedicated game thread and a dedicated render thread" and is labelled E. That is the L03 game-thread/render-thread split, stated as an owned, established capability. It contradicts §6 ("No fixed game, render or RHI threads"), `RND.GPU.recording` ("no dedicated render thread unless an API mandates affinity, by ADR") and L03. Three skills are involved, and their written territory disagrees on who decides thread existence. `frame-orchestration` owns the dedicated-thread capability. `render-architect` lists "render threading" in its purpose. `gpu-platform-architect` routes "frames in flight / thread existence" to frame-orchestration, but L03 names `gpu-platform-architect` as its justification owner. A phase-2 frame-orchestration agent would build the fixed-thread topology in good faith, with no ADR, and every downstream skill (render extraction, physics hand-off, audio) would adapt to it. check.py cannot catch this because it does not read the wording.
- Evidence: A fixed thread split caps parallelism at the number of threads and forces a hand-off copy every frame (the §6 rationale itself). Task-based frames with no render thread have shipped: Naughty Dog's fiber-based frame-centric jobs (Gyrling, "Parallelizing the Naughty Dog Engine Using Fibers", GDC 2015) and Destiny's job-based renderer (Tatarchuk et al., GDC 2015). UE's own RHI-thread and render-thread design is the legacy that §6 names as the thing it replaces.
- Proposed change: Reword `CORE.FRAME.pipelining` to "Frame pipelining depth (sim N+1 ∥ extract/record N ∥ GPU N−1) expressed as overlapping task-graph frames; no dedicated game/render/RHI threads (dedicated threads only by ADR via CORE.JOBS.thread-model)". Remove "render threading" from `render-architect.purpose` and add a non-responsibility "Thread existence / frame pipelining → frame-orchestration". Set L03 `justification_owner` to `frame-orchestration`, with `job-system-task-graph` for the thread inventory, so that the owner of the capability and the owner of the justification are the same skill.

### K-LEGACY-2 · major · obsolete-assumption
- Target: CORE.FRAME.phases, CORE.FRAME.sim-schedule, C-FRAME (name "Frame, tick phases & time"), frame-orchestration purpose
- Finding: `CORE.FRAME.phases` is "Tick phases, sync points & phase barriers", and `CORE.FRAME.sim-schedule` is a "Canonical simulation phase order (pre/post-physics, substeps, net snapshot, render extract)". Together they are UE tick groups (TG_PrePhysics/TG_DuringPhysics/TG_PostPhysics) with barriers between them, renamed. §6 explicitly claims to replace "a fixed sequence of tick groups with barriers". `C-FRAME` promises "the minimal set of named global sync points", but the owned capability makes phase barriers a first-class feature, and nothing defines phases as non-barrier ordering labels. The legacy is therefore silently present.
- Evidence: Bevy (schedules and system sets with ambiguity detection) and Unity Entities (SystemGroups lowered to a job dependency graph) show that named phases can be pure ordering constraints derived from access, with no full-frame barrier. Barriers between phases serialize the frame's tail and head: each phase waits for its slowest system. Rollback and resimulation need a fixed *order*, not a barrier.
- Proposed change: Reword `CORE.FRAME.phases` to "Named phases as ordering constraints over declared access (non-barrier by default); global sync points enumerated, each needing an ADR". Reword `CORE.FRAME.sim-schedule` to "Canonical simulation dependency order (partial order; total order only where C-DET requires it)". Rename C-FRAME to "Frame schedule, phases & time". Add a fitness function (`ARCH.GOV`) that counts global sync points against the ADR list.

### K-LEGACY-3 · major · obsolete-assumption
- Target: gameplay-architect (purpose), GAM.FW.control, L06, B25
- Finding: The `gameplay-architect` purpose says "Gameplay framework: rules, players and **possession**…". The owned capability `GAM.FW.control` says control binding is data and the model is chosen per game by ADR, and L06 lists possession-by-habit as legacy. Phase 2 generates the SKILL.md mainly from `purpose`, so the lead agent's charter hard-codes the Actor→Pawn→Controller possession model before ADR B25 has been decided.
- Evidence: Possession does not fit RTS, card, colony, simulation or MMO games that control many entities (§6 rationale). This is a charter/territory mismatch of the kind check.py cannot see.
- Proposed change: Replace "players and possession" with "players and data-oriented control binding (model per game by ADR B25)" in `gameplay-architect.purpose`. In `gameplay-systems-toolkit.purpose`, replace "spawning and pooling" with "batched deferred spawning (pooling only where measured)" to match `GAM.SYS.spawning`.

### K-LEGACY-4 · major · obsolete-assumption
- Target: UI.FW.logic, UI.FW.architecture, C-UI (requires C-REFL), CORE.REFL.static-default, L20
- Finding: `UI.FW.logic` is "UI logic hosting via **reflection-invoked handlers**". C-UI's only binding substrate is C-REFL, whose summary is "dynamic invocation". This is stringly-typed runtime binding: property paths and function names resolved and invoked through reflection on the UI update path. It is exactly L20, and `CORE.REFL.static-default` (string lookup only at tool/script/serialization boundaries) lists `ui-architect` as a contributor but is not reflected in the UI capabilities. The contract says nothing about change notification, so the default becomes polling-based binding.
- Evidence: UMG function and property bindings are evaluated every frame, and Epic's own guidance discourages them. UE 5.1+ replaced them with the MVVM plugin (field-notify, compiled bindings). Noesis and WPF compiled bindings, and Unity UI Toolkit's runtime binding with resolved paths, follow the same direction.
- Proposed change: Reword `UI.FW.logic` to "UI logic hosting: handlers resolved at load/compile time (script or visual script via C-SCRIPT); reflection only for authoring". Reword `UI.FW.architecture` to "retained UI with change-notified view models and compiled/resolved bindings (no per-frame polling)". Add to the C-UI summary: "bindings resolved at load time, driven by change notification". Make `ui-architect` a named co-signer of L20.

### K-LEGACY-5 · major · obsolete-assumption
- Target: GAM.SCR.level-scripting, GAM.SYS.volumes ("level-scoped logic wiring"), world-data-model, L18
- Finding: `GAM.SCR.level-scripting` ("Level-bound script/event wiring") and `GAM.SYS.volumes` ("level-scoped logic wiring") keep the Level-Blueprint model, in which logic is bound to a level file and holds references to objects in that level. That model assumes the whole level is resident: level-as-a-file (L18). It breaks under cell streaming, because referenced objects may be unloaded, and it has no defined lifetime under data layers or level instances.
- Evidence: UE5 World Partition does not let the persistent Level Blueprint safely reference actors in streamed cells. Epic steers logic toward actor-, data-layer- or world-subsystem-scoped wiring for that reason. This is a production case of level-bound scripting failing against streaming.
- Proposed change: Reword to "World-, cell-, data-layer- or instance-scoped script wiring with streaming-safe references (soft IDs, activation/deactivation events via C-WORLD)". Add obligation text: a scripted reference to a streamed object must be a soft handle resolved on activation. `world-architect` becomes a contributor.

### K-LEGACY-6 · major · maturity-error
- Target: RND.GRAPH.work-graphs (E), RND.RHI.gpu-work (E), radar entry "Work graphs & mesh nodes" (X), docs/00 §7
- Finding: The radar classes work graphs as X ("no shipped titles"), but the capability `RND.GRAPH.work-graphs` is labelled **E**. `RND.RHI.gpu-work` (E) also bundles "work-graph programs" into an established capability. §7 says work graphs are an optional part of C-RG and never a required dependency of an established capability, yet here they sit inside two E capabilities of the RHI and the render graph. This is the "GPU-driven everywhere" new dogma (L27): an agent implementing the E capability would treat work graphs as baseline. check.py only verifies that non-E capabilities appear on the radar, not that a capability listed on the radar has the same class.
- Evidence: D3D12 Work Graphs 1.0 shipped in 2024. Vulkan has only a vendor extension (VK_AMDX_shader_enqueue), there is no Metal or WebGPU equivalent, and no public console support. That meets the framework's own X definition.
- Proposed change: Split `RND.GRAPH.work-graphs` into `RND.GRAPH.gpu-generated-work` (E: indirect/DGC scheduling, barriers and memory) and `RND.GRAPH.work-graphs` (X). Remove "work-graph programs" from `RND.RHI.gpu-work` and add `RND.RHI.work-graphs` (X). Add a check.py rule: every capability listed on the radar has maturity equal to the radar class.

### K-LEGACY-7 · major · wrong-boundary
- Target: CORE.ECS.baking (ecs-runtime), WLD.PART.cook, WLD.PART.hlod (world-architect), RND.ARCH.editor-rendering (render-architect), L23, check.py tool-side rule
- Finding: Four cook-side or editor-side capabilities are owned by runtime skills whose `tool_consumes` is empty. The cook steps never consume C-COOK, and editor rendering never reaches C-EDHOST. So nothing places that code in a tools-only module, and it defaults into the skill's runtime module. That module ships in the client and server targets, which is the L23 editor-in-runtime monolith, and it also contradicts the "format owner vs pipeline host through C-COOK" pattern in §4. The check.py guarantee ("tool-logic owners reach the editor through contracts") covers only `*.TOOL.*` capability ids, so cook and editor-rendering territory escapes it.
- Evidence: `ecs-runtime`, `world-architect` and `render-architect` all have `tool_consumes = []`, and `render-architect` targets `client` and `tools`. UE's historic WITH_EDITOR/WITH_EDITORONLY_DATA sprawl is the production example of editor code bleeding into runtime modules when module placement is not enforced.
- Proposed change: Add `tool_consumes: ["C-COOK"]` to `ecs-runtime` and `world-architect`, and `["C-EDHOST"]` to `render-architect`. Add a per-capability `side: runtime|tool` attribute, or derive it from the id pattern (cook, bake, build, editor, TOOL). Extend check.py so that every tool-side capability's owner consumes a tool contract, and so that tool-side modules never appear in the client or server closure.

### K-LEGACY-8 · major · omission
- Target: CORE.OBJ.*, WLD.MODEL.*, ED.ARCH.pie, C-ECS, C-WORLD
- Finding: No capability states that the engine supports multiple independent world instances per process, and none forbids a process-global "current world". Several features need it: in-process client+server (listen server, multiplayer PIE per `ED.ARCH.pie-net`), editor preview scenes and thumbnails (C-EDHOST), background or off-bubble simulation, parallel tests, and rollback's "resimulate on a copy". `ED.ARCH.pie` ("simulation isolation") treats this as an editor feature rather than a core invariant. It is the most common piece of hidden-global legacy (UE `GWorld`), and it is absent from L08 and from the catalogue.
- Evidence: UE's GWorld and world-context workarounds for PIE and multiplayer PIE show the cost of retrofitting. Unity Entities (multiple `World`s) and Bevy (`World` as a value, sub-apps) show the alternative has shipped.
- Proposed change: Add `CORE.OBJ.world-instances` ("Multiple isolated world instances per process; all world-scoped state reachable only through a world handle; no current-world global"), owned by `entity-object-model` with contributors `ecs-runtime`, `world-architect` and `editor-architect`. Add legacy pattern "Process-global current world" (detection: static world accessor), with justification owner `entity-object-model`.

### K-LEGACY-9 · major · obsolete-assumption
- Target: NET.REP.state, NET.REP.priority, C-REP, replication, legacy-patterns.json
- Finding: Replication is described as "Entity & property replication" with no stance on how changes are detected. The legacy default, and the historically shipped one, is per-connection, per-object property polling: comparing shadow state for every replicated object for each connection every net tick, at cost O(objects × connections). The framework's own scalability obligation ("spatial replicas update in O(changes)") is not applied to replication, and no L-pattern covers it.
- Evidence: UE's generic replication needed ReplicationGraph for Fortnite scale, and was then replaced by Iris (UE 5.1+), which uses push-model dirty tracking and serializes once for all connections. Change-tracked replication consuming ECS change detection is the demonstrated best practice.
- Proposed change: Reword `NET.REP.state` to "Entity & property replication with push/dirty-tracked change detection (consuming C-ECS change versions and C-SPATIAL change sets), serialize-once-per-object shared across connections". Add legacy pattern "Per-connection per-object property polling" with justification owner `replication`.

### K-LEGACY-10 · major · obsolete-assumption
- Target: C-ENV (multiple implementers), C-SPATIAL, C-NAV, ARCH.STRUCT.binding, L10
- Finding: C-ENV is implemented by four providers (terrain, water, atmosphere, voxel) and serves per-point queries such as ground height, water height/velocity and wind. Its summary never says the queries are batched, or how a provider is bound. The natural implementation is a virtual `QueryWaterHeight(point)` call per buoyancy point, per particle or per foot IK sample, dispatched across providers: L10 on one of the hottest query paths in an open world. C-SPATIAL ("generic spatial queries") and C-NAV ("path requests") also omit batch granularity. C-PHYS is the only query contract that states it ("handle-addressed, batched").
- Evidence: Buoyancy, foliage wind and foot placement generate thousands of point queries per frame. Batched query streams, as in Jolt/PhysX batch queries and UE's async trace batches, are the established form. `ARCH.STRUCT.binding` states the rule, but the contracts do not.
- Proposed change: Amend the C-ENV summary: "queries submitted as batched streams per phase; provider bound per region/cell at activation time (no per-query dispatch across providers)". Add "batched query API" to C-SPATIAL and C-NAV. Add a C-ARCH conformance item: each query contract declares its batch granularity.

### K-LEGACY-11 · major · scale-down
- Target: job-system-task-graph (CORE.JOBS.test-modes), PLAT.WEB.runtime, platform-web, L25, docs/00 §6
- Finding: "Parallel by default" has no *shipping* single-threaded execution mode. The only serial mode is `CORE.JOBS.test-modes` (tests). Web builds without cross-origin isolation (COOP/COEP) have no SharedArrayBuffer and so no threads. That is the case for most embed portals and many hosting setups. `platform-web` ships in minimal, min2d and lite3d. The browser main thread also cannot block (Atomics.wait is disallowed) and has to yield to the event loop every frame. With no explicit inline, cooperative task-graph mode, agents will either assume threads everywhere (breaking web and minimal targets) or build a separate single-threaded loop, which reintroduces L01 through the back door.
- Evidence: Emscripten pthreads require COOP/COEP headers. Unity's and Godot's web exports have long shipped single-threaded because of this. Anti-legacy should mean "task graph first, executable on N ≥ 1 workers", not "threads assumed".
- Proposed change: Add `CORE.JOBS.inline-mode` ("Shipping single-worker/inline execution of the same task graph, cooperative yielding to a host event loop, no blocking waits on the host thread"), owned by `job-system-task-graph` with contributors `platform-web` and `frame-orchestration`. Amend PLAT.WEB.runtime to cover the no-threads fallback. Restate L25's stance as "parallel by construction, correct on one worker".

### K-LEGACY-12 · major · scale-down
- Target: WLD.PART.grid, WLD.PART.sources, WLD.PART.activation, WLD.PART.hlod, WLD.PART.sim-tiers, WLD.PART.server (no profile tags); world-architect (profiles: all); L18
- Finding: Every WLD.PART capability is untagged, so cell streaming, HLOD orchestration, off-bubble simulation tiers and server-side world streaming are all in the `minimal` (card/UI game) and `min2d` closures. L18's stance ("cell streaming with budgeted activation") is written as universal. That is new dogma (L27): for a 2D platformer or a card game, one asynchronously loaded, non-blocking world unit is the correct design, and the legacy part of level-as-a-file is *blocking* the load, not having one file.
- Evidence: The capability-level profile tags exist precisely for this (for example VSM and cluster LOD are `std3d`), but they are not applied to world partitioning. Many shipped 2D and indie games use per-scene async loads well.
- Proposed change: Tag WLD.PART.grid, sources, hlod, sim-tiers and server as `openworld` (keep `lite3d`/`std3d` where useful). Add `WLD.MODEL.unit-load` ("async non-blocking whole-unit load with loading-screen hand-off"), E, for minimal and min2d. Reword L18 to "Blocking whole-level load before play; default: async non-blocking loading; cell streaming for openworld".

### K-LEGACY-13 · major · omission
- Target: data/legacy-patterns.json, docs/00 §6
- Finding: The catalogue is missing several load-bearing legacy patterns, and it has no machine link from each pattern to the capability that embodies its default stance. That missing link is why K-LEGACY-1 to -5 could exist without being detected. Missing patterns:
  - (a) runtime shader/PSO compilation on first use (stutter);
  - (b) frame-rate-coupled simulation or variable-dt physics;
  - (c) hard-reference transitive load graphs (loading one asset pulls half the game);
  - (d) process-global current world (see K-LEGACY-8);
  - (e) per-connection property polling (see K-LEGACY-9);
  - (f) a global shared RNG consumed from parallel tasks (`CORE.MATH.random` states no per-stream/counter-based policy);
  - (g) stringly-typed or polling UI binding (see K-LEGACY-4).

  §6 also gives no default stance for L18–L24, even though it claims to be the set of defaults that phase 2 inherits.
- Evidence: PSO stutter is the most visible PC-era regression of the last five years (UE 5.2+ PSO precaching was added as a retrofit). Hard-reference load chains are a routine UE production pain point, which is why soft references and asset managers exist. Counter-based RNGs (Philox, Salmon et al., SC 2011) are the standard way to get parallel-deterministic randomness.
- Proposed change: Add L28–L34 for (a)–(g) with owners `shader-system`, `frame-orchestration`, `content-pipeline-architect`, `entity-object-model`, `replication`, `math-simd-numerics` and `ui-architect`. Add a `stance_capabilities: [cap ids]` field to every pattern (for example L03 → CORE.FRAME.pipelining and RND.GPU.recording; L18 → WLD.PART.activation and RES.MGMT.no-stall). Extend check.py so that every pattern has at least one stance capability, each stance capability exists, and its owner is the justification owner or one of its contributors. Extend the §6 table to cover L18–L24 or state that it is a subset.

### K-LEGACY-14 · minor · wrong-owner
- Target: L11, L15, C-LIFETIME, RND.GRAPH.barriers
- Finding: The justification owner does not match the capability owner. L15 (frame-tied lifetimes) names `resource-streaming-architect`, but the retirement service keyed to completion tokens is `C-LIFETIME` / `CORE.LIFE.ownership-model`, owned by `core-runtime-architect`, and `RND.MEM.lifetime` belongs to `gpu-memory-resources`. L11 bundles "global renderer sync" under `concurrency-primitives`, but renderer synchronization is owned by `render-graph-scheduling`. L03 has the same problem (see K-LEGACY-1). An ADR request would be routed to a skill that cannot change the code involved.
- Evidence: See the owner fields of the capabilities named above.
- Proposed change: L15 → `core-runtime-architect` (with `gpu-memory-resources` for GPU resources). Split L11 into "coarse locks" (`concurrency-primitives`) and "global renderer sync / flush" (`render-graph-scheduling`).

### K-LEGACY-15 · minor · overlap
- Target: RND.ARCH.instance-data (render-architect), RND.GEO.gpu-scene and C-INSTANCES (geometry-pipeline), RND.ARCH.scene-sync
- Finding: Two skills own the persistent GPU instance scene: "GPU instance data layout & delta upload" (render-architect) and "GPU scene & instance data management" plus the C-INSTANCES contract (geometry-pipeline). Two owners of the render-side mirror is how per-feature proxy mirrors (L14) come back: each owner keeps its own copy.
- Evidence: See the owners of the two capabilities and the C-INSTANCES contract.
- Proposed change: Fold `RND.ARCH.instance-data` into `RND.GEO.gpu-scene` (owner geometry-pipeline) and keep `render-architect` as a contributor. Add to the C-RSCENE obligations: "one persistent instance scene; features consume it, never mirror it".

### K-LEGACY-16 · minor · other
- Target: C-SCRIPT, GAM.SCR.concurrency, L22
- Finding: The L22 stance (per-worker VMs or isolates, deferred world mutation) lives only in the capability `GAM.SCR.concurrency`. The contract that consumers bind to, C-SCRIPT ("Binding generation, sandbox limits, script lifecycle"), says nothing about threading or mutation rules, and the `scripting-runtime` purpose lists "GC policy" but not concurrency. Gameplay, UI and AI consumers designing against C-SCRIPT would therefore assume a single global VM.
- Evidence: Phase-2 contracts are drafted from the contract summaries (08-phase-2-plan, "Contracts first").
- Proposed change: Add to the C-SCRIPT summary: "execution on task-graph workers via per-worker VMs/isolates; world mutation only through deferred command buffers; weak handles to engine objects". Add "VM concurrency model" to `scripting-runtime.purpose`.

### K-LEGACY-17 · minor · other
- Target: RES.MGMT.no-stall, PLAT.PAL.thread-affinity
- Finding: `RES.MGMT.no-stall` says "no **main-thread** waits". That presumes a main thread which the rest of the framework says does not exist, and it leaves waits on worker tasks on the critical path unaddressed.
- Evidence: Under a task-graph frame, a blocking wait in any critical-path task stalls the frame just as a main-thread wait does.
- Proposed change: Reword to "No blocking waits on frame-critical tasks or host/OS-bound threads; completions via C-TASK tokens".

### K-LEGACY-18 · minor · omission
- Target: radar "WebGPU backend & web 3D" (fallback "WebGL-class 2D only"), ARCH.REQ.non-goals, lite-3d-mobile configurations
- Finding: The radar names a WebGL-class fallback, and no skill owns a GLES or WebGL backend. The framework has removed the OpenGL-era APIs, which is correct as an architecture, but it never records the removal as a non-goal with its scale-down cost: low-end Android devices without usable Vulkan, and browsers or embeds without WebGPU. As written, the fallback is an unowned OpenGL-era path that an agent could add ad hoc.
- Evidence: The radar fallback entry and the absence of any GLES/WebGL owner in `C-RHI` implementers.
- Proposed change: Add a radar `non_goal` entry "GLES/WebGL backends", recording the device-share evidence and a revisit trigger. Alternatively, if the fallback is real, give it an owner as a C-RHI implementer limited to the `min2d` tier.
