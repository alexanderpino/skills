# K-TOOLS — Tools & Editor Critic, round 3

### K-TOOLS-1 · blocker · dependency-error
- **Target:** milestones M0, M1, M2; build-system-toolchains, ci-cd-automation, asset-import-interchange, packaging-release-patching; C-BUILD, C-PKG
- **Finding:** The M0 exit says the skeleton "passes CI with sanitizer, fuzz and determinism smoke lanes" and "loads one cooked and signed asset from a package". M0 also gates XC.DET.conformance, which is a CI gate. M1 requires hot reload, and C++ live coding reaches the build through `tool_consumes: C-BUILD`. Yet `build-system-toolchains` (C-BUILD), `ci-cd-automation`, `packaging-release-patching` and `asset-import-interchange` all arrive only at M2, and C-BUILD is only drafted at M2. So for two milestones every compiled module, every CI lane and every source asset (PNG sprites, fonts, audio: CNT.IMP.textures and CNT.IMP.audio) has no owning agent. The ledger cannot give out the build description, CI pipeline definitions or import code, so either agents write unowned files or M0/M1 cannot exit. check.py cannot see this because C-BUILD is tool-side and client configurations do not close over it.
- **Evidence:** The walking-skeleton practice (Cockburn; Freeman & Pryce, *GOOS*) puts build, deploy and test automation in the first slice. Engine teams bring up build + CI + import→cook→load first: data pipelines are the long pole (Naughty Dog's and Insomniac's GDC pipeline talks; Our Machinery's "tools-first" posts). The framework's own principle "instrumentation, tests, budgets ... exist before features (milestone gates from M0)" requires CI at M0.
- **Proposed change:** In `milestones.json`, move `build-system-toolchains`, `ci-cd-automation` and `asset-import-interchange` (at least the texture, font and audio importers) to M0. Move `packaging-release-patching` to M1 (M1 claims shippable indie-2d@pc). Draft C-BUILD at M0 and freeze it at M1. Add a check.py rule: every skill named as a contributor of a gate capability, or reached through `tool_consumes` by a milestone's skills, must have arrived by that milestone.

### K-TOOLS-2 · major · obsolete-assumption
- **Target:** CNT.COOK.ddc (content-pipeline-architect); C-COOK; legacy-patterns.json
- **Finding:** The capability defines the derived-data cache as "keyed by source path & file modification time". That is the legacy timestamp-make model. It contradicts the owner's purpose ("content-addressed store"), CNT.ID.identity (GUID + content hash), C-COOK's "cache keys, determinism class", CNT.COOK.shared-cache and CNT.COOK.incremental-equivalence. Mtime keys are machine-local, so a shared or cloud DDC cannot key on them. A VCS sync, branch switch or checkout rewrites mtimes, which gives mass false invalidation. Copy tools or clock skew give stale hits. Mtime keys also ignore processor version, platform, parameters and transitive dependencies, so incremental cooks cannot be proven equal to a clean cook. No legacy pattern catches this.
- **Evidence:** UE DDC keys hash the inputs plus the builder version GUID and settings, and Zen/Cloud DDC are content-addressed. Unity Asset Database v2 (2019.3) moved from timestamps to content hashes of the import dependencies, which enabled the Accelerator cache. Bazel, Buck2 and Pants action caches key on input digests plus the action/tool digest. Timestamp `make` is the textbook counterexample (Mokhov, Mitchell & Peyton Jones, "Build Systems à la Carte", 2018).
- **Proposed change:** Rename CNT.COOK.ddc to "Content-addressed derived-data cache keyed by hash of (source content, transitive dependency hashes, processor/version id, platform & quality variant, parameters); mtime only as a local change-detection hint". Add to C-COOK summary: "cache key = digest of all declared inputs + processor version; undeclared inputs are a conformance failure". Add legacy pattern "Timestamp/path-keyed build caches" (detection: mtime or path in a cache key; stance CNT.COOK.ddc, CNT.COOK.incremental-equivalence; justification owner content-pipeline-architect).

### K-TOOLS-3 · major · wrong-boundary
- **Target:** ED.ARCH.transactions, C-EDCMD (layer 5, editor-architect), C-EDIT (layer 4, modding-ugc), XC.EXT.player-creation, ED.COLLAB.multiuser
- **Finding:** There are two command/undo systems. C-EDIT's summary says its "serializable commands (schema shared with C-EDCMD per ED.ARCH.transactions)". But C-EDCMD is layer 5 and tool-side only, and editor-architect ships only in the tools target, so runtime code cannot consume it. The shared command schema, apply/invert, journal and merge core has no owner at a layer both sides can reach. In practice modding-ugc will build a second transaction system in the client, editor-architect a third concern in the editor, and collaboration-version-control's multi-user merge (journal feed) will run against only one of them. It gets worse over time: C-EDCMD is frozen at M3 and C-EDIT is drafted only at M4, so the "shared" schema is frozen before its second user exists.
- **Evidence:** The brief's editor direction ("editor is the game" runtime editing: Roblox Studio vs in-experience building, UEFN/Fortnite Creative, Dreams, Bevy's editor-in-runtime work) needs one command model usable in both tool and client builds. Diff-based command journals are the basis of Omniverse live layers and CRDT/OT editing (ED.COLLAB.concurrent-world), and they must be the same data in both places.
- **Proposed change:** Add capability `CORE.SER.commands` ("Serializable diff-based command & transaction core: command schema, apply/invert, journal, compaction, merge hooks") owned by `serialization-schema` (contributors editor-architect, modding-ugc, collaboration-version-control). Add contract `C-CMD` (layer 2, requires C-SER, C-REFL, C-ID) and make both C-EDCMD and C-EDIT `require` it. Keep ED.ARCH.transactions as editor policy (scopes, PIE exclusion, UI). In milestones, freeze C-CMD before C-EDCMD, and freeze C-EDCMD no earlier than C-EDIT's draft.

### K-TOOLS-4 · major · dependency-error
- **Target:** milestones.json freezes of C-ASSET, C-COOK and C-TARGETPLAT (M1); C-EDCMD (M3)
- **Finding:** Tool-side contracts are frozen before their principal producers and consumers exist:
  - C-ASSET and C-COOK are frozen at M1. The importer (the main producer of registry entries, source tracking and redirects), the editor, VCS (C-VCS requires C-ASSET) and every 3D cook builder (virtualized-geometry-lod, global-illumination, terrain, world-architect's WLD.PART.cook, the CNT.COOK.world-build region graph, destruction and motion-synthesis) arrive at M2–M3.
  - C-TARGETPLAT, which covers per-target cook variants, the shader backend hook, the packager and deploy/launch/debug on device, is frozen at M1 while its only implementer is platform-desktop. platform-console, platform-mobile and platform-web arrive at M2 and platform-server-host at M4, and packaging-release-patching (a consumer) arrives at M2.
  
  The first real on-device iteration and console cook implementers therefore meet a frozen, desktop-shaped interface. The "frozen after owner and a consumer" rule is met formally but not in substance.
- **Evidence:** On-demand cooking and cook-server streaming to devices (CNT.COOK.on-demand; UE Zen/ODSC) and devkit deploy/launch have constraints (file-serving over devlink, console package formats, per-platform shader compilers) that desktop never exercises. Freezing an interface with a single implementer is the standard way to get an abstraction that leaks.
- **Proposed change:** Move the C-ASSET and C-COOK freezes to M3, after asset-import-interchange, the editor, VCS and at least one world-scope builder have arrived. Move the C-TARGETPLAT freeze to M3, after console, mobile and web implementers and packaging exist; its exit already requires "on-device iteration to console and mobile". Extend the check: a `needs_implementer` contract may freeze only after at least two implementers of different platform classes, and a layer-5 contract only after a tool-side consumer has arrived.

### K-TOOLS-5 · major · other
- **Target:** oracle_author of C-ASSET (ai-assisted-authoring), C-SER (collaboration-version-control), C-TEXT (editor-ui-framework), C-REPLAY (physics-tools); systemic
- **Finding:** Acceptance suites (tests/acceptance/<contract>/, owned by the oracle author) cannot exist when the contract freezes, because the oracle author has not arrived yet:
  - C-ASSET is frozen at M1, but its oracle `ai-assisted-authoring` arrives at M6. It is also in the `aaa` profile only and is an M-maturity evaluation skill, so it is the wrong party to write the asset-identity oracle for every configuration.
  - C-SER is frozen at M1, and its oracle collaboration-version-control arrives at M2.
  - C-TEXT is frozen at M1, and its oracle editor-ui-framework arrives at M2.
  - C-REPLAY is frozen at M1, and its oracle physics-tools arrives at M2.
  
  The same inversion affects about 29 frozen contracts (for example C-SIGN→modding-ugc at M4, C-SPATIAL→crowd-simulation at M4, C-WORLD→dedicated-server at M4, C-SCRIPT→modding-ugc at M4). The framework's anti-gaming rule (implementers never grade themselves; oracle-first) is therefore not in force for most of the foundation.
- **Evidence:** C-TEST/C-ORCH define oracle-owned read-only acceptance suites as a freeze precondition in spirit ("a provider change merges only when the contract's conformance suite ... passes"). An oracle that arrives five milestones late means the contract was frozen untested.
- **Proposed change:** Reassign C-ASSET's oracle to `asset-import-interchange` (moved to M0 per K-TOOLS-1) or `package-formats-vfs`. Reassign C-TEXT's oracle to `ui-architect` (M1) and C-REPLAY's oracle to `physics-architect` (M1) or `functional-automation-soak`. Keep C-SER→collaboration-version-control only if that skill arrives by M1. Add a check.py rule: `oracle_author` must be a process skill or must arrive no later than the contract's draft milestone.

### K-TOOLS-6 · major · missing-contract
- **Target:** C-RELOAD consumers; XC.ITER.coordination; ED.ARCH.discipline-workflows
- **Finding:** Only 4 runtime skills consume C-RELOAD: ecs-runtime, world-data-model, shader-system and scripting-runtime. The skill's own non-responsibility says "each system's own reload implementation (via C-RELOAD)" is the owning skill's job. Yet the domains whose edit→see loop matters most declare no reload dependency: material-system (material instances and parameters), gameplay-data (tuning tables), ui-architect (widget trees, styles), localization-i18n (string tables), audio-content-runtime (events, mix), vfx-particles (emitters), animation-runtime and animation-graphs (clips, graph instances), navigation-pathfinding (navmesh tiles), text-fonts, input-system (action maps) and gameplay-camera (rigs). Generic handle swapping in RES.MGMT.reload does not rebuild the derived runtime state (graph instances, voice parameters, particle pools, bound widgets). So no agent is obliged to implement it, and the M3 iteration-latency gate cannot be met by construction.
- **Evidence:** Production iteration loops in Unity's Domain Reload-less Enter Play Mode, UE live tuning of material and data assets, and Frostbite/Insomniac live asset editing need per-domain state migration. Insomniac's GDC talks on the "live-editing everything" pipeline credit per-system reload handlers.
- **Proposed change:** Add `C-RELOAD?` to `consumes` of material-system, gameplay-data, ui-architect, localization-i18n, audio-content-runtime, vfx-particles, animation-runtime, animation-graphs, navigation-pathfinding, text-fonts, input-system, gameplay-camera and cinematics-sequencer. Add a check: any runtime skill that owns a *.TOOL capability and loads C-ASSET data must consume C-RELOAD, or record an `iteration` note saying why not.

### K-TOOLS-7 · major · scale-down
- **Target:** ED.WORLD.partitioned (profiles: openworld); WLD.PART.grid and WLD.PART.hlod (lite3d, std3d)
- **Finding:** standard-3d-tools, lite-3d-mobile-tools and online-3d-tools contain world partition cells, streaming sources and HLOD generation (WLD.PART.grid and WLD.PART.hlod carry lite3d/std3d). They do not contain partition-aware editing: region load/unload, cell visualization, HLOD preview, and editing a subset without loading the world. Those configurations cook worlds their editor cannot edit partition-aware. Designers either load the whole world or edit blind to cell assignment, and a std3d level with streaming then needs rework when openworld is enabled.
- **Evidence:** UE5 World Partition editing (region loading, data layers, HLOD preview) applies to any partitioned map, not only open worlds. Unity's scene-streaming workflows are likewise independent of world size.
- **Proposed change:** Set the profiles of ED.WORLD.partitioned to `["lite3d","std3d"]`, matching WLD.PART.grid. If a large-world-only part exists (for example multi-kilometre region management), split it out as `ED.WORLD.large-world-regions` [openworld].

### K-TOOLS-8 · major · scale-down
- **Target:** team-large profile; CNT.COOK.shared-cache, ED.COLLAB.multiuser, ED.ARCH.telemetry, CNT.COOK.distributed; configurations
- **Finding:** The brief asks for collaboration from 3 to 1000 people. The framework has one binary `team-large` add-on, and it appears only in aaa-open-world-online-tools. Every other tools configuration (indie-2d, standard-3d, lite-3d-mobile, online-3d) has no shared DDC, no multi-user session, no tool telemetry and no distributed cook. So the 10–150-person tier (most std3d/online studios) is neither designed for nor proven. A shared or cloud derived-data cache is the single largest iteration win for teams as small as 3–5: without one, every artist re-derives shaders and textures after every sync. It is cheap (a network share or a single cache server). It should not sit behind the AAA flag.
- **Evidence:** UE documentation recommends a shared DDC for any multi-person team. Unity Accelerator and Unity Cache Server target small teams. Godot and Bevy communities use shared import caches via VCS/CI artifacts. Multi-user editing (UE Multi-User/Concert) is used by virtual-production teams of 3–10 people.
- **Proposed change:** Remove `team-large` from CNT.COOK.shared-cache. Keep "cloud/multi-site deployment & health" as a separate `CNT.COOK.cache-fleet` [team-large]. Add a `team-mid` add-on (shared DDC, tool crash/usage telemetry, small-session multi-user, partial sync) and a configuration `standard-3d-team-tools` {std3d, online, team-mid} claimed at M4. Re-tag ED.COLLAB.multiuser to `["team-mid","team-large"]`.

### K-TOOLS-9 · major · missing-contract
- **Target:** ED.ARCH.pie-net (profiles online, online-lockstep, online-rollback); editor-architect consumes (`C-NET?`, `C-REP?`)
- **Finding:** Multiplayer play-in-editor has to create sessions in each hosting mode (listen, dedicated, P2P), launch and attach dedicated-server processes, and apply the link conditioner for network emulation. Those capabilities live in C-NETSESSION (NET.SESS.host-mode), C-SERVER (host lifecycle) and C-NETLINK (NET.TRANS.simulation). editor-architect consumes none of them. For the lockstep and rollback families it reaches only C-REP?, which those configurations do not even link, and not C-PREDICT. So PIE-net for fighting and RTS projects has no contract path, and the owner would have to reach into netcode internals.
- **Evidence:** UE PIE multi-client/dedicated-server mode runs through the session/NetDriver layer plus network emulation settings. GGPO-class rollback test modes need a local two-peer session with synthetic latency and a sync test.
- **Proposed change:** Add `C-NETSESSION?`, `C-NETLINK?`, `C-PREDICT?` to editor-architect `consumes`, and add `C-SERVER?` to its `tool_consumes` for spawning server processes. Add `net-session` and `prediction-rollback` as contributors to ED.ARCH.pie-net.

### K-TOOLS-10 · major · missing-contract
- **Target:** ED.COLLAB.multiuser, ED.COLLAB.concurrent-world, collaboration-version-control (consumes C-EDCMD, C-SER, C-ASSET, C-RELEASE); untrusted input `collab-session`
- **Finding:** Multi-user session editing and conflict-free concurrent world editing need a network transport, a session server (host, auth, persistence and replay of the session journal, late join) and presence/lock broadcasting. collaboration-version-control consumes no network or IPC contract. No capability owns the multi-user session server: its deployment, authentication, persistence or scaling. The M6 gate ED.COLLAB.multiuser therefore has no dependency path. C-IPC is local dev-only, and C-NETLINK is the game transport, which is never declared for tools use here.
- **Evidence:** UE Multi-User Editing runs a dedicated Concert server with session persistence. Omniverse uses the Nucleus server with live layers. Figma-class CRDT editing uses a server-authoritative relay. In all of them the server is a separately owned, deployable component.
- **Proposed change:** Add capability `ED.COLLAB.session-server` ("Multi-user session server: transport, auth via XC.SEC.dev-trust access classes, journal persistence, late join, presence & lock broadcast") owned by collaboration-version-control [team-mid/team-large], with contributors network-transport and security-engineering. Add `C-NETLINK?` (or `C-IPC` plus a PAL HTTP/TLS client) to collaboration-version-control's `consumes`. Add editor-architect's C-EDCMD journal feed as the payload.

### K-TOOLS-11 · major · omission
- **Target:** xr-runtime, input-devices-haptics; check.py AUTHORING_WORKSTREAMS
- **Finding:** xr-runtime is a user-facing runtime domain that owns and contributes no authoring or preview capability. There is no VR/XR preview from the editor (play-in-headset), no XR device simulator for developers without a headset, no in-headset or spatial editing, and no passthrough/anchor/scene-mesh preview. Separately, INP.DEV.haptic-assets defines authored haptic and trigger-effect assets but no one owns the haptics editor or on-controller preview. check.py's authoring rule skips both because it covers only the world, simulation, audio, ui and gameplay workstreams, and platform is excluded.
- **Evidence:** UE's "VR Preview" PIE mode and VR editing mode; Unity XR Device Simulator; Meta XR Simulator; Apple's visionOS simulator and Reality Composer Pro; Meta Haptics Studio; the Sony DualSense haptics authoring workflow (audio-to-haptics plus trigger-effect design); Apple Core Haptics AHAP authoring.
- **Proposed change:** Add `PLAT.XR.editor-preview` ("Play-in-headset, XR device simulation, passthrough/anchor/scene-mesh preview from the editor") owned by xr-runtime, with contributors editor-architect and world-editor-viewport, and with xr-runtime `tool_consumes: C-EDCMD, C-EDVIEW`. Add `INP.TOOL.haptics` ("Haptic & trigger-effect editor with live on-device preview") owned by input-devices-haptics, with contributor audio-content-runtime. Add "platform" to AUTHORING_WORKSTREAMS, with `authoring` notes for skills that have no user-facing content.

### K-TOOLS-12 · minor · dependency-error
- **Target:** C-AUTOMATION (consumed only by editor-architect)
- **Finding:** docs/00 justifies making C-AUTOMATION runtime-owned because "agents drive device, server and soak builds, not only the editor". Yet no test, performance or CI skill declares it: functional-automation-soak, perf-benchmarking, ci-cd-automation, test-runtime-harness and render-validation. Consumer-driven conformance cases and freeze reviews for the protocol therefore come only from the editor. QA.FUNC.automation, BLD.CI.device-lanes and replay-driven C-BENCH runs will end up with private control channels.
- **Evidence:** The framework's own C-TEST rule ("conformance suites ... with consumer-driven additions") needs declared consumers. The protocol's stated users are the device, server and soak builds.
- **Proposed change:** Add `C-AUTOMATION` to `consumes` of functional-automation-soak, perf-benchmarking and render-validation, and to `tool_consumes` of ci-cd-automation.

### K-TOOLS-13 · minor · omission
- **Target:** untrusted-inputs.json; ED.ARCH.extension, XC.SEC.dev-trust
- **Finding:** Opening a project can execute editor-side code: tool scripts in the ED.ARCH.extension scripting (Python-class) language, startup scripts, project descriptors, and custom importer or processor code shipped in the project. Nothing in the registry covers this. `scripts` is validated by scripting-runtime with VM time and memory limits, which do not apply to unsandboxed editor tool scripting. `editor-plugins` covers binaries only.
- **Evidence:** UE `init_unreal.py` auto-runs on editor start. Unity Editor scripts run on project open. VS Code "Workspace Trust" exists for exactly this vector. Malicious game projects have been used as malware carriers (Check Point's 2024 "GodLoader" report on Godot).
- **Proposed change:** Add input `project-tool-code` ("editor tool scripts, startup scripts, project descriptors, in-project importers/processors"): validating_owner editor-architect, parser_owners [plugin-system], trust hostile-local, mode redteam+harness, limits "workspace trust: no execution before trust grant; per-command permission classes (ED.ARCH.automation-security)". Add editor-architect to its untrusted_inputs.

### K-TOOLS-14 · minor · wrong-boundary
- **Target:** legacy pattern L37; ED.ARCH.process; ED.UI
- **Finding:** L37 ("modal, blocking editor operations" replaced by "asynchronous, cancellable editor jobs with progress") names ED.ARCH.process (in- vs out-of-process runtime) as its stance capability. No capability owns the editor background-job model: async import, save, compile and bake jobs scheduled on C-TASK with progress, cancellation, UI-thread-free completion and conflict with open transactions. Relatedly, no capability owns the world outliner or scene hierarchy at scale (virtualized lists over 10⁶ objects, filtering by data layer and cell), which is the most-used panel after the viewport and a known large-project bottleneck.
- **Evidence:** UE's Scene Outliner and asynchronous compilation (async shader/texture/static-mesh compile manager) were each reworked for UE5 large worlds. A2 in docs/06 names 10⁶-object editor performance as a research gap without an owning capability.
- **Proposed change:** Add `ED.ARCH.async-jobs` (owner editor-architect) and point L37's stance_capabilities at it. Add `ED.UI.outliner` ("Scene hierarchy/outliner virtualized for 10⁶ objects, filtering by data layer/cell/partition") owned by editor-ui-framework, with contributor world-data-model.
