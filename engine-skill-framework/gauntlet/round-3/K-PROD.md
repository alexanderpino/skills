# K-PROD · Production Critic · Round 3

### K-PROD-1 · blocker · other
- **Target:** ARCH.ORG.independence, ARCH.ORG.staffing, crosscutting.json `independence`, contracts `oracle_author` (41 code contracts), security-engineering, security-runtime, test-architect, test-runtime-harness
- **Finding:** The framework says independence is enforced because each never-same-agent pair sits in a different workstream, and the workstream is the co-hosting unit (00 §2, 04 "Independence matrix"). The data breaks that promise in two places. (a) In 41 of the code contracts, the `oracle_author` is in the same workstream as the contract owner or an implementer. Examples: C-RHI (oracle gpu-memory-resources; rhi-core and all backends are in rendering), C-REP (prediction-rollback / replication, online), C-PREDICT (anti-cheat-integrity / prediction-rollback, online), C-SAVE, C-SCRIPT, C-NAV, C-MEM, C-ID, C-BUILD, C-PKG, C-SERVER, C-SHARD, C-AUTOMATION and C-TESTHOST (test-architect / test-runtime-harness, quality). (b) security-engineering is the "security reviewer vs reviewed code" party, yet it shares the quality workstream with security-runtime (the crypto, signing and anti-rollback code it must gate under ARCH.ORG.sensitive-paths), privacy-data-protection, robustness-fuzzing and test-runtime-harness. check.py skips every `owning-skill` pair and never compares oracle_author with implementers by workstream. Under the documented staffing rule, a small organization therefore puts the implementer and its oracle author in one agent, which is exactly the self-grading that L56 and QA.AGENT.* exist to prevent.
- **Evidence:** Computed from contracts.json × skills.json (owner + `implements` vs `oracle_author` workstream). Precedent: benchmark gaming when the author of the code controls its tests is the documented failure mode that QA.AGENT.oracle-independence cites (A13 in 06).
- **Proposed change:** Reassign `oracle_author` for the 41 contracts to a skill in a different workstream (for example C-RHI → render-validation (quality), C-REP/C-PREDICT → simulation-validation, C-TESTHOST → robustness-fuzzing if moved to assurance). Move security-engineering (and robustness-fuzzing) into the `assurance` workstream. Extend check.py so that `oracle_author` workstream ≠ owner/implementer workstream for every code contract, and security-engineering workstream ≠ every skill whose write set is in ARCH.ORG.sensitive-paths. Otherwise, redefine staffing as explicit agent groups (see K-PROD-11) and check the pairs per agent.

### K-PROD-2 · major · obsolete-assumption
- **Target:** BLD.REL.staged-rollout, milestones M4 gate, legacy-patterns.json
- **Finding:** The capability named "staged rollout" is defined as "Simultaneous global rollout to all players with post-release kill switches". That is the big-bang release the name contradicts, and M4 uses it as a gate ("patch + DLC + staged rollout + rollback executed"). It exposes 100% of players to a bad client or server build before any health signal exists. The only safeguard left is a kill switch, which does not help against crashes on boot, save corruption or a patch that breaks the kill-switch path. No legacy pattern flags big-bang releases.
- **Evidence:** Google Play staged rollouts (percentage with halt), App Store phased release (7-day ramp), Steam beta branches, console "soft launch" regions, and server canary/blue-green deploys (Google SRE Workbook, "Canarying Releases"). Live incidents caused by global simultaneous pushes (e.g. CrowdStrike July 2024 channel-file push) are the industry reference for why exposure is ramped.
- **Proposed change:** Rename and redefine it as `BLD.REL.staged-rollout`: "Percentage/ring/region-staged client, content and server rollout with health-gated promotion (crash-free sessions, error budgets from PLAT.LIVE.operations), automatic halt, and kill switches", with contributors online-services-liveops, crash-diagnostics and dedicated-server. Add legacy pattern L58 "Big-bang simultaneous release to all players" with stance capabilities [BLD.REL.staged-rollout, NET.SRV.lifecycle].

### K-PROD-3 · major · wrong-boundary
- **Target:** milestones.json gates (M1–M7); ARCH.ORG.independence ("milestone owner vs gate owner")
- **Finding:** Milestone gates name *feature* capabilities, whose owner is the implementer of the feature being gated. Examples: NET.PRED.rollback (prediction-rollback), CORE.SCALE.governor (runtime-scalability), RND.SHADER.pso-lists (shader-system), BLD.REL.staged-rollout/rollback (packaging-release-patching), NET.SRV.cross-server (server-scaleout-persistence), ED.COLLAB.vcs/multiuser (collaboration-version-control), RES.MGMT.arbitration (resource-streaming-architect), GAM.FW.local-players (gameplay-architect). A milestone exit therefore rests on the implementer's own claim. The M7 gates ARCH.PROD.customer-corpus and XC.EXT.lts belong to the governance workstream, the same workstream as program-orchestration, which owns the milestones. That breaks the declared "milestone owner vs gate owner" pair, because only the program-orchestration ↔ reference-games pair is encoded.
- **Evidence:** Output of the gate-owner/workstream join over milestones.json. Stage-gate practice (e.g. certification/TRC readiness reviews, and "definition of done verified by a party other than the implementer") requires an independent verifier.
- **Proposed change:** Give every gate a `validator` field that names a validation capability owned outside the gated feature's workstream and outside governance. Examples: NET.PRED.rollback → QA.SIM.netsim; CORE.SCALE.governor → PRF.* governor test; RND.SHADER.pso-lists → PRF.LOAD.hitch-gate; BLD.REL.staged-rollout → a QA.FUNC release-rehearsal capability; ARCH.PROD.customer-corpus → QA.REF.upkeep. Add a check.py rule: validator owner ≠ gated capability owner, and validator workstream ≠ program-orchestration's workstream.

### K-PROD-4 · major · omission
- **Target:** ARCH.ORG.human-gates, PLAT.LIVE.support-tools, NET.SRV.admin, PLAT.SVC.remote-config, BLD.REL.staged-rollout, BLD.REL.end-of-service
- **Finding:** The human-gate register covers the build side (contracts, spend, NDA, signing, submissions). It does not cover irreversible live-production actions that agents can reach through owned capabilities:
  - restoring or editing player data (PLAT.LIVE.support-tools)
  - GM/admin commands on shipping servers (NET.SRV.admin)
  - mass bans and ban waves (anti-cheat)
  - promoting a rollout past canary, and activating a kill switch or remote-config change for all players
  - economy or currency grants (NET.SRV.transactions)
  - end-of-service shutdown and data deletion

  These actions touch real players' money, data and access. The framework therefore lets an autonomous agent take them without a human.
- **Evidence:** Live-service practice (two-person rule for economy grants and ban waves, change-advisory review for production config) and GDPR Art. 22 (automated decisions with significant effects, e.g. bans) require human involvement or review.
- **Proposed change:** Extend ARCH.ORG.human-gates with a "live-production actions" class that lists the items above. Add online-services-liveops, anti-cheat-integrity and dedicated-server as contributors. Require C-LIVE and the NET.SRV.admin surface to carry a human-approval token for those command classes.

### K-PROD-5 · major · omission
- **Target:** ARCH.ORG.ownership-ledger, C-ORCH, ARCH.ORG.critic-calibration
- **Finding:** The ledger has "territory locks" but no lock leases or expiry, no stale-lock reclamation, and no task checkpoint or hand-off record for an agent that crashes, runs out of context or is replaced mid-task. With 100+ autonomous agents, abandoned locks and lost partial work are routine and will deadlock territories. There is also no trigger for a change of the underlying model or agent version. A model swap changes implementer and critic behaviour, but calibration (ARCH.ORG.critic-calibration) and SKILL.md evals (ARCH.ORG.skill-lifecycle) are only re-run at milestone exits.
- **Evidence:** Distributed lock services use leases and fencing tokens for exactly this reason (Chubby, Kleppmann's "How to do distributed locking"). Critic recall/precision in PROTOCOL.md is model-dependent, which is why the protocol already demands model-family diversity.
- **Proposed change:** Add `ARCH.ORG.agent-continuity` (program-orchestration): lock leases with heartbeats and fencing tokens, stale-lock reclamation, a mandatory task hand-off record (state, open CRs, branch, evidence bundle) and re-brief on agent replacement. Add to C-ORCH. Add `ARCH.ORG.model-change` (architecture-governance, contributor program-orchestration): a change of model or agent version triggers critic re-calibration and skill evals before the new agent counts as a gate.

### K-PROD-6 · major · wrong-boundary
- **Target:** ARCH.ORG.decomposition, program-orchestration, domain leads
- **Finding:** One orchestrator skill decomposes every milestone into tasks for all 153 skills ("Milestone → task decomposition by skill territory"). Leads settle disputes but have no planning territory. For an agent this is a context-window and throughput bottleneck, and a single point of failure. It also contradicts "few orchestrators, many focused experts": in effect the orchestrator must understand every domain in enough depth to cut tasks.
- **Evidence:** Large engine programs plan hierarchically (engine director → domain leads → strike teams), and multi-agent planning literature shows the same: hierarchical task networks and manager/worker delegation scale better than flat planners.
- **Proposed change:** Split ARCH.ORG.decomposition. program-orchestration decomposes milestones into per-lead work packages and cross-workstream integration tasks. Add `<DOMAIN>.ARCH.work-planning`, or one capability with all 15 leads as contributors, for intra-subtree task decomposition. Define the work-package format in C-ORCH.

### K-PROD-7 · major · obsolete-assumption
- **Target:** UI.LOC.strings (localization-i18n)
- **Finding:** "String tables keyed by English source text" is the gettext-era key model. It contradicts the framework's own localizability obligation ("use stable string IDs"), GAM.NARR.lines ("stable IDs") and C-LOC ("String IDs"). Keying by source text orphans every translation when the source wording changes, merges homographs that need different translations, and breaks VO line linkage and patch-stable data layout (the "live changeability" obligation).
- **Evidence:** Production loc pipelines (Unreal text namespaces/keys, Unity Localization table keys, XLIFF `id` + source with change tracking) key by stable ID and keep the source text only as a change-detection field.
- **Proposed change:** Redefine UI.LOC.strings as "String tables keyed by stable IDs (namespace + key); source text and its hash tracked for change detection and re-translation flags". Add a legacy pattern "Source-text-keyed localization" with stance [UI.LOC.strings, UI.LOC.gather].

### K-PROD-8 · major · omission
- **Target:** QA.FUNC, OBS.CRASH, ED.COLLAB.production-tracking
- **Finding:** Nothing owns bug capture: an in-game and in-editor bug report that bundles build ID, a replay/snapshot (C-REPLAY/C-SNAPSHOT), screenshot or video, logs, world position and config, deduplicates against crash buckets and files into the tracker. Testers, playtesters, beta players and content creators file most defects this way. ARCH.PROD.intake covers game-team reports to the engine, not this capture tool.
- **Evidence:** In-house tools such as Frostbite's bug-sentry class, Unity's Bug Reporter for engine defects and studio "Ctrl+B" reporters are standard AAA and indie infrastructure. Without state capture, triage (ARCH.ORG.triage) cannot reproduce content bugs.
- **Proposed change:** Add `QA.FUNC.bug-capture` (functional-automation-soak) with contributors determinism-replay, crash-diagnostics, visual-debugging-tools and collaboration-version-control (tracker link). Register a `bug-reports` untrusted input for player or beta submissions.

### K-PROD-9 · major · omission
- **Target:** ARCH.PROD.field-feedback, ARCH.PROD.licensing-model, engine-product-management (consumes [])
- **Finding:** field-feedback pulls cross-title crash, performance and developer-experience metrics from licensee titles and editors into the vendor's roadmap. No capability owns the legal and privacy basis for that flow: the controller/processor role versus the licensee, licensee opt-in, a data processing agreement, what editor and runtime telemetry the vendor may collect, and never using it for billing without consent. engine-product-management also consumes no contract at all, so the data path from crash-diagnostics and observability is undeclared.
- **Evidence:** Unity's 2023 Runtime Fee, based on install counts from engine telemetry, caused a customer revolt and was withdrawn in 2024. That is direct precedent that vendor telemetry and licensing terms are a product-existential risk. GDPR Art. 28 (processor agreements) also applies.
- **Proposed change:** Add `ARCH.PROD.vendor-telemetry` (privacy-data-protection, contributors engine-product-management, observability-telemetry, crash-diagnostics and certification-compliance): licensee-controlled opt-in, a DPA template, data classes and a ban on silent billing telemetry. Make engine-product-management consume C-CRASH/C-INSTR-derived reports through a declared process contract. Add "licensing-model changes" to ARCH.ORG.human-gates.

### K-PROD-10 · major · omission
- **Target:** ML.RT.training-boundary, CNT.ID.rights, QA.CERT.genai, motion-synthesis, facial-animation, GAM.NARR.vo-script
- **Finding:** Rights tracking covers assets in general (CNT.ID.rights) and disclosure of generated content (QA.CERT.genai). No capability owns the provenance of shipped ML models and their training data: the model licence, dataset licence, and performer consent for digital replicas of voice, face and motion (TTS VO, learned motion matching, facial solvers, voice conversion). No capability owns the regulatory transparency duties for AI-generated content either. These models are shipped runtime artifacts in several M/X capabilities.
- **Evidence:** SAG-AFTRA Interactive Media Agreement (2025) requires consent and disclosure for digital replicas. EU AI Act Art. 50 transparency obligations apply from Aug 2026. Store policies (Steam AI-content disclosure) require disclosure.
- **Proposed change:** Add `QA.CERT.ml-provenance` (certification-compliance, contributors ml-inference-runtime, content-pipeline-architect, motion-synthesis, facial-animation and narrative-dialogue): a model/dataset licence register, a performer-consent register linked to CNT.ID.rights, and an EU AI Act transparency mapping. Make ML.RT.training-boundary emit the lineage record into the rights manifest.

### K-PROD-11 · major · scale-down
- **Target:** ARCH.ORG.staffing, ARCH.GOV.process-tiers, ARCH.ORG.independence
- **Finding:** The data proves engine scale-down (34 configurations). Organizational scale-down is only asserted. No data defines organization tiers (e.g. one human + a few agents, a small studio, a AAA program), which agents host which skills, or the minimum agent count that still satisfies the independence pairs. "Co-hosting unit = workstream" yields at least 16 agents plus separate reviewers, which does not scale down to an indie effort. Tier names are also defined twice (ARCH.ORG.staffing and ARCH.GOV.process-tiers), which breaks the "one definition of tier names" principle the framework applies to hardware tiers.
- **Evidence:** The framework's own principle 5 is "scaling down is proven, not asserted". Indie teams of 1–5 people ship on commercial engines; the agent organization must be able to shrink the same way.
- **Proposed change:** Add `data/organizations.json` with named org tiers. Each tier maps agents to skill groups (groups may span workstreams) and lists the process-tier governance stages. Make ARCH.ORG.staffing the only owner of tier names, with ARCH.GOV.process-tiers consuming them. Extend check.py so that for every org tier, independence pairs, oracle_author vs implementers and security-engineering vs sensitive-path owners land on different agents, and every skill is hosted.

### K-PROD-12 · minor · dependency-error
- **Target:** milestones M4/M7, PLAT.LIVE.operations
- **Finding:** M4 claims all online configurations and executes live patch, DLC, rollout and rollback. Live-title SLOs, alerting, incident runbooks and the launch-readiness review (PLAT.LIVE.operations) are gated only at M7. Online titles would be declared ready without operational readiness.
- **Evidence:** Launch-readiness reviews (Google SRE "Production Readiness Review") come before first live exposure, not at the product's 1.0.
- **Proposed change:** Move the PLAT.LIVE.operations gate to M4. Keep an end-of-service rehearsal (BLD.REL.end-of-service) at M7.

### K-PROD-13 · minor · wrong-boundary
- **Target:** BLD.REL.rollback
- **Finding:** "Release rollback" is stated without regard to channel. Store-distributed clients on console, iOS/Android and most PC stores cannot be rolled back after install. Those channels need roll-forward hotfixes plus server-side and content-side rollback under the compatibility window (NET.ARCH.versioning). As written, agents will design and gate (M4) a mechanism that cannot exist on those channels.
- **Evidence:** Platform holders offer no user-side downgrade. Store practice is to halt the staged rollout and ship a new build.
- **Proposed change:** Redefine BLD.REL.rollback as "Per-channel recovery: server and content rollback, client roll-forward hotfix path, rollout halt; compatibility-window constraints", with contributors network-architect and online-services-liveops.
