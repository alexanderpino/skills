# K-RENDER · Rendering Critic · round 3

### K-RENDER-1 · major · obsolete-assumption
- **Target:** RND.POST.effects, post-color-hdr, C-TRANSLUCENT, C-TEMPORAL
- **Finding:** RND.POST.effects says the post chain (bloom, depth of field, motion blur, lens) is "applied after tonemapping on display-referred output". That is the LDR-era order. Bloom, DOF, motion blur and lens effects are energy-based convolutions of scene radiance. They must run on scene-referred linear HDR before the output transform, and DOF and motion blur usually run before or around the upscaler. The row also contradicts C-TRANSLUCENT, which composes translucency "before/after DOF and upscale", and C-TEMPORAL's upscalers, which take pre-tonemap HDR input. An agent writing post-color-hdr's SKILL.md from this row would build a display-referred post chain. Highlights would clip and bloom would stop following exposure, and the result would not survive HDR output, where one scene feeds several output transforms.
- **Evidence:** Jimenez, "Next-Generation Post-Processing in Call of Duty: AW" (SIGGRAPH 2014 Advances): bloom, DOF and motion blur operate in HDR. The UE and Frostbite post pipelines both run bloom, DOF and motion blur before the tonemapper and output transform. ACES/OCIO: the output transform (RRT/ODT, or ACES 2.0 OT) is the last scene→display step. DLSS/FSR/XeSS integration guides require pre-tonemap HDR color input.
- **Proposed change:** Rename RND.POST.effects to "Post chain (bloom, depth of field, motion blur, lens) on scene-referred linear HDR before the output transform; ordering relative to upscaling published in C-SCENETEX phases". Add RND.POST.display-referred: "Display-referred stage after the output transform (grain, UI-safe sharpening, dithering)". Add to the C-COLOR summary: "scene-referred/display-referred boundary and the passes allowed on each side".

### K-RENDER-2 · major · scale-down
- **Target:** RND.LIGHT.*, direct-lighting-shadows, configurations lite-3d-mobile-client / lite-3d-mobile-online-client / xr-standalone-client
- **Finding:** The only shadow-map capability is RND.LIGHT.vsm, which is tagged `std3d`. RND.LIGHT.rt-shadows is also `std3d`, and RND.LIGHT.contact is screen-space only. No capability row exists for cascaded shadow maps, for local-light (spot/point) shadow atlases, or for static/dynamic shadow caching. Every lite3d configuration therefore closes with no directional or local shadow-map technique. Cascades appear only in the skill's purpose text and as an option in gap-analysis B4, and that ADR can only choose among owned capabilities. check.py proves lite3d closure, but it proves it over an empty shadowing tier.
- **Evidence:** CSM (Engel, ShaderX5; Zhang PSSM), scrolling/cached cascades, and shadow atlases with per-light caching are what ships on mobile, Switch-class hardware, standalone XR and every non-VSM PC tier. Arm/Qualcomm best-practice guides describe CSM with few cascades on TBDR. UE keeps CSM as the non-Nanite/mobile path next to VSM.
- **Proposed change:** Add RND.LIGHT.csm "Cascaded/scrolling directional shadow maps with stabilization and caching" (E, no profile). Add RND.LIGHT.local-shadows "Local-light shadow atlas, cube/tetrahedral maps, static/dynamic caching & per-light budget" (E). Add RND.LIGHT.shadow-filtering "PCF/PCSS/EVSM-class filtering tiers" (E). All three are owned by direct-lighting-shadows. Add a C-LIGHT summary clause: "shadow technique per tier (CSM/atlas, VSM, RT) behind one lookup API".

### K-RENDER-3 · major · missing-contract
- **Target:** vfx-particles, C-ABILITY, C-SEQ, C-ANIM, destruction-fracture, deformation-skinning
- **Finding:** vfx-particles provides no contract. Nothing gives gameplay cues (C-ABILITY effects and hit results), animation notifies (C-ANIM events), destruction, cinematics tracks (C-SEQ), weather or UI a way to spawn, attach, parameterize, pool or stop an effect instance. Nothing gives VFX a declared way to read data sources either: skinned-mesh surface sampling, physics contact events, C-ENV fields. Audio has C-AUDIO "emitters & events" for the same job, and VFX has no counterpart. Each consumer will either reach into VFX internals or invent its own spawn API, and there is no place to record replication and cosmetic-vs-simulated rules or significance culling of effect requests.
- **Evidence:** Niagara exposes a component/parameter API and Data Interfaces (skeletal mesh, collision, grid). Unity VFX Graph exposes event attributes, property binders and the GameplayCue → Niagara pattern in GAS. Frostbite and Decima VFX talks (GDC 2016–2019) describe an effect-request interface with budgets and significance.
- **Proposed change:** Add contract C-VFX (layer 3, owner vfx-particles, requires C-RSCENE, conformance, oracle_author gameplay-systems-toolkit): "Effect instance requests (spawn/attach/stop, pooled handles, batched), user parameters, event payloads, data-source bindings (skinned surfaces via C-RSCENE deformation streams, C-PHYS contacts, C-ENV fields), significance and budget class, determinism class (cosmetic by default)". Add C-VFX? to the consumes of gameplay-systems-toolkit, cinematics-sequencer, destruction-fracture, animation-runtime, atmosphere-weather and ui-architect. Also add C-ANIM? and C-PHYS? event sources to vfx-particles.

### K-RENDER-4 · major · dependency-error
- **Target:** C-VT, texture-streaming-vt, material-system, geometry-pipeline, RND.TEX.mip-streaming
- **Finding:** C-VT is consumed only by terrain and render-2d-vector. material-system is the skill that generates the shader code sampling VT page tables and writing sampler/VT feedback, and it does not consume C-VT. Neither does geometry-pipeline (visibility-buffer material resolve), translucency-decals or vfx-particles. texture-streaming-vt consumes C-RES, C-GPUMEM and C-RG but no scene or view contract (C-RSCENE, C-INSTANCES, C-VIEW). CPU-computed mip priorities (screen size × texel density per instance per view), the established path on lite3d/mobile where RND.TEX.feedback is `std3d`, therefore have no data path. Either materials cannot sample streamed or virtual textures, or the streamer cannot know what to stream.
- **Evidence:** UE texture streaming computes per-primitive texel factors from the render scene and views. Id Tech's MegaTexture/virtual texturing and UE RVT/SVT inject VT sampling and feedback into generated material code. Sampler feedback (D3D12) also needs shader-side writes emitted by the material compiler.
- **Proposed change:** Add C-VT to material-system consumes, attributed to shader codegen. Add C-VT? to geometry-pipeline, translucency-decals and vfx-particles. Add C-RSCENE, C-INSTANCES? and C-VIEW to texture-streaming-vt consumes. Extend the C-VT summary: "shader-side VT sampling/feedback interface consumed by material codegen; per-instance texel-density registration for CPU-priority mip streaming".

### K-RENDER-5 · major · dependency-error
- **Target:** C-RTAS (layer 2), ray-tracing-infrastructure (C-RG@C-RT only), RND.GRAPH.external-work, L28
- **Finding:** RND.GRAPH.external-work says acceleration-structure builds are registered producers that the render graph schedules, with barriers, queue placement and budgets. But C-RTAS (AS build/refit/compaction and ray queries) is layer 2, below C-RG (layer 3), and the C-RTAS module does not consume C-RG. The layering therefore forbids the AS-build module from registering with the graph, so it must record its own barriers and submissions. That reintroduces renderer sync outside the graph (L28) for BLAS/TLAS builds, and for the non-render consumer spatial-audio-acoustics as well.
- **Evidence:** AS builds need UAV/AS barriers against the passes that trace, and they compete for async-compute time and scratch memory with other graph work. Production engines (UE RDG ray-tracing scene builds; Frostbite FrameGraph) schedule BLAS/TLAS builds as graph passes. C-MLGPU already follows the correct pattern: layer 3, requires C-RG.
- **Proposed change:** Move C-RTAS to layer 3 with requires [C-RG, C-GPUMEM], and make ray-tracing-infrastructure consume C-RG unattributed. Alternatively, extract an L2 contract "C-GPUWORK: external GPU work registration (producer, queue class, deadline, budget, resource import/export)" owned by render-graph-scheduling, required by C-RTAS, C-IO GPU decompression and C-GPUMEM uploads, and implemented by the graph.

### K-RENDER-6 · major · missing-contract
- **Target:** path-tracing, RND.PT.reference, QA.RENDER.reference, ANM.CINE.movie-render, render-validation, cinematics-sequencer
- **Finding:** The reference path tracer is the ground-truth oracle for all raster features, yet it provides no contract. render-validation and cinematics-sequencer (movie render) reach it through nothing, so there is no declared interface for converged reference renders (spp or convergence target, seeds, AOVs, determinism tolerance). The oracle also consumes C-LIGHT (the light-sampling API of direct-lighting-shadows, one of the skills it judges) and C-TEMPORAL (the upscaler/denoiser). A units or IES-falloff bug in C-LIGHT, or a denoiser bias, therefore appears identically in the raster output and in the reference, and the golden comparison passes. The oracle's code is not independent of the implementation it grades. path-tracing and the features it checks also share the render-architect lead and the rendering workstream.
- **Evidence:** PBRT-4/Mitsuba-style references evaluate lights and BSDFs from scene definitions, not from the real-time sampling structures. NVIDIA Falcor and UE's reference path tracer are kept separate from the real-time light grid. Test-oracle independence is the framework's own rule (L56, QA.AGENT.oracle-independence).
- **Proposed change:** Add contract C-PTREF (layer 3, owner path-tracing, requires C-RSCENE, C-MATIF; conformance; oracle_author render-validation): "reference render request (scene snapshot, view, convergence criterion, seed, AOVs), converged unbiased output without denoising, variance estimate". Attribute C-LIGHT and C-TEMPORAL to the real-time module only (C-LIGHT@C-PTRT, C-TEMPORAL@C-PTRT). The reference module evaluates light definitions from C-RSCENE. render-validation and cinematics-sequencer consume C-PTREF?. Add an independence row [path-tracing, direct-lighting-shadows / global-illumination, "reference oracle vs judged feature: no shared sampling code"].

### K-RENDER-7 · major · maturity-error
- **Target:** RND.GEO.splat-relight (E, std3d), RND.GEO.splats (M), radar "Gaussian splatting & radiance fields"
- **Finding:** Relightable and dynamic splats with hybrid raster/RT composition are labelled Established and enabled in every std3d shipping configuration. Base static splats in the same skill are only M. The radar's own promotion trigger for splats is "standard format + relighting + shipped game use", and docs/07 calls splatting "experimental for games". Because the capability is E, it skips the radar and fallback check and becomes a silent dependency of shipping std3d builds.
- **Evidence:** Relightable Gaussian splats (e.g. GS³, Relightable 3D Gaussians 2024), 3DGRT/3DGUT (2024–25) and dynamic/4D GS remain research. No shipped game relies on relit, dynamic splats.
- **Proposed change:** Set RND.GEO.splat-relight maturity to X and profile to ['experimental']. Add it to the splat radar entry (or a new X entry) with fallback "static unlit splats composited over raster, or photogrammetry meshes".

### K-RENDER-8 · minor · maturity-error
- **Target:** RND.RECON.denoise (M), radar "ML denoising & ray reconstruction"
- **Finding:** One M row merges established spatiotemporal denoisers (SVGF/ReBLUR/ReLAX, shipped widely) with emerging ML ray reconstruction. The radar fallback, "spatiotemporal denoisers", is part of the M capability itself, so the fallback is circular. The established path every RT tier needs therefore sits behind an emerging label.
- **Evidence:** NRD ReBLUR/ReLAX ship in many titles. SVGF (Schied 2017). DLSS RR is vendor-specific and M.
- **Proposed change:** Split the row: RND.RECON.denoise "Spatiotemporal denoising (SVGF/ReBLUR class)" E, and RND.RECON.ml-denoise "ML denoising / joint ray reconstruction" M. Point the radar entry at ml-denoise only, with fallback RND.RECON.denoise.

### K-RENDER-9 · minor · maturity-error
- **Target:** radar entries for RND.SHADER.neural and RND.SHADER.autodiff
- **Finding:** (a) RND.SHADER.autodiff shares a radar entry with in-shader neural evaluation. Its fallback, "Standalone inference dispatch", does not apply to a compile-time differentiation feature used for tooling and training. (b) The evidence, "SM 6.9 cooperative vectors (preview)", is stale. Cooperative vectors did not ship in retail SM 6.9 and were redirected to a broader DXIL linear-algebra/matrix feature. Vulkan's cooperative-vector extension is NV-only, while cooperative-matrix is KHR. If the revisit trigger stays keyed to "cooperative vectors", the capability may never be promoted.
- **Evidence:** DirectX Developer Blog SM 6.9 release notes and the linear-algebra roadmap (2025); Khronos registry VK_NV_cooperative_vector and VK_KHR_cooperative_matrix.
- **Proposed change:** Give RND.SHADER.autodiff its own radar entry (M, fallback "hand-derived gradients / offline finite differences in tool code"). Reword the neural entry's evidence and trigger to "API-neutral matrix/tensor intrinsics (DXIL linear algebra, VK cooperative matrix/vector, Metal tensor ops) on ≥2 vendors".

### K-RENDER-10 · minor · omission
- **Target:** legacy-patterns.json (L29 and missing rendering patterns)
- **Finding:** The anti-legacy catalogue has no pattern for the display-referred/LDR pipeline (gamma-space lighting, post after tonemap, hard-coded SDR tonemapper). K-RENDER-1 shows that pattern has already crept into the data. The catalogue also lacks geometry-shader / fixed-function tessellation / stream-out pipelines as a default on capable tiers. L29's stance_capabilities omit the capabilities that actually carry the stance: RND.SHADER.precache and RND.RHI.pso (async creation with fallbacks).
- **Evidence:** Vendor guidance (AMD RDNA and NVIDIA Ada performance guides) discourages geometry shaders and HW tessellation in favour of mesh/compute. HDR output requires a scene-referred pipeline. Epic's PSO precaching (UE 5.2+) is the load-time half of the PSO-stutter stance.
- **Proposed change:** Add L58 "Display-referred/LDR rendering pipeline" (stance: scene-referred linear HDR end-to-end with a single output transform; owner post-color-hdr; stance_capabilities RND.POST.color, RND.POST.effects). Add L59 "Geometry-shader/HW-tessellation/stream-out pipelines on capable tiers" (stance: mesh/compute or cluster displacement; owner geometry-pipeline; stance_capabilities RND.GEO.mesh-shaders, RND.LOD.displacement). Add RND.SHADER.precache and RND.RHI.pso to L29.

### K-RENDER-11 · minor · scale-down
- **Target:** RND.TEX.formats, texture-streaming-vt, platform-web, rhi-webgpu
- **Finding:** No capability covers runtime transcoding from a supercompressed universal format (KTX2 + Basis/UASTC) to the format the device supports. On the web, WebGPU exposes BC, ASTC or ETC2 depending on browser and device, so one download cannot carry one native format. Android fragmentation has the same issue. Transcoding appears only as an NTC fallback phrase in the radar.
- **Evidence:** Khronos KTX 2.0 and glTF KHR_texture_basisu. Basis Universal is used by three.js, Babylon and Unity web builds for exactly this reason.
- **Proposed change:** Add RND.TEX.transcode "Load-time transcoding from supercompressed universal formats (KTX2/UASTC/ETC1S) per device capability" (E), owned by texture-streaming-vt with contributors platform-web and asset-cook-processors, and register "texture-transcoder input" under the existing user-images/assets untrusted-input entries.

### K-RENDER-12 · minor · other
- **Target:** critics.json K-RENDER scope
- **Finding:** K-RENDER's scope leaves out three skills that own rendering code. world-editor-viewport and visual-debugging-tools (debug draw, GPU-side overlays, frame-capture integration) are the rendering tooling surface in the brief. text-fonts owns the glyph atlas/curve rendering data behind C-DRAW2D. Rendering-tooling currency and the correctness of text rendering (Slug/MSDF-class) therefore get no rendering review.
- **Evidence:** RND.ARCH.editor-rendering, RND.TOOL.frame-debugger and RND.SHADER.gpu-debug-draw all list these skills as contributors, but no rendering critic reviews them.
- **Proposed change:** Add world-editor-viewport, visual-debugging-tools and text-fonts to K-RENDER scope, with stages S1–S3.
