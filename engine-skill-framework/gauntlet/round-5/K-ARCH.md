# K-ARCH · Engine Architecture Critic · Round 5

Method: mechanical sweep of all 134 contracts (owner, requires, oracle_author, summary vs the owner's purpose and consumes), all 1,708 capabilities with contributors (owner vs expertise, and contributor to owner contract edges), the 88 legacy patterns and their stance capabilities, skill purposes and non-responsibilities, and organizations.json. check.py is green and none of the findings below is something it proves.

### K-ARCH-1 · major · obsolete-assumption
- Target: RND.ARCH.scene-sync (stance capability of L14), C-RSCENE, C-INSTANCES, RND.GEO.gpu-scene
- Finding: the capability that is supposed to carry the "change-tracked delta extraction, O(changes)" stance is worded as its opposite: "per-frame mirrored copy of every scene object handed to the render side, versioned per frame (CPU cost O(scene objects))". That is exactly the per-object render-proxy mirror that L14 flags as legacy, and it contradicts C-RSCENE ("no per-object proxy mirror; CPU cost O(changes)") and C-INSTANCES ("delta upload, cost O(changes)").
- Evidence: L14 in legacy-patterns.json; 00-design-principles section 6 ("Simulation-to-render extraction is change-tracked, with delta upload into a persistent instance scene"); production precedent is UE5 GPU Scene with dirty-primitive tracking and Unity's BatchRendererGroup persistent GPU instance data. A SKILL.md generated for render-architect from the capability list would implement the mirror.
- Proposed change: rename to "Simulation→render extraction: change-tracked deltas into the persistent instance scene (C-INSTANCES); no per-object proxy mirror; CPU cost O(changes)". Add "mirror", "every scene object" and "O(scene objects)" to L14 contradiction_terms.

### K-ARCH-2 · major · obsolete-assumption
- Target: UI.FW.architecture (stance capability of L35), C-UI, ui-architect purpose
- Finding: UI.FW.architecture reads "retained UI with view models refreshed by per-frame property polling through string-keyed bindings". This is the stringly-typed polling binding that L35 flags. C-UI and the ui-architect purpose say the opposite ("bindings resolved at load time and driven by change notification").
- Evidence: L35 and L20; UI.FW.logic and CORE.REFL.static-default in the same catalogue require resolved IDs on runtime paths; UI.FW.performance (invalidation) cannot be met by polling. Precedent: Unreal UMG property bindings polled per frame are the documented performance trap, and the current stance is Slate attributes, Unity UI Toolkit runtime binding or Coherent-style change notification.
- Proposed change: "Game UI architecture: retained UI with change-notified view models and load-time-resolved bindings (no per-frame polling, no string-keyed lookup on runtime paths)". Add "polling" and "string-keyed" to L35 contradiction_terms.

### K-ARCH-3 · major · obsolete-assumption
- Target: ED.ARCH.transactions (stance capability of L38), C-EDCMD, C-CMD
- Finding: ED.ARCH.transactions says "each undo step stores a full copy of the affected scene or asset state". That is snapshot-based undo (L38), and it contradicts C-EDCMD and C-CMD ("serializable diff-based commands, apply/invert").
- Evidence: L38; ED.ARCH.transaction-invariants (do→undo→redo equivalence) and ED.COLLAB.merge require invertible deltas; full copies are impossible at the 10^6-object worlds of ED.UI.outliner and break merge and journal replay. Precedent: Unreal transactions serialize property deltas, and Unity Undo records diffs.
- Proposed change: "Command / transaction / undo-redo system over C-CMD diff-based commands; editor scopes (world, asset editor, PIE exclusion), selection and journal feed; no whole-state snapshots per step".

### K-ARCH-4 · major · obsolete-assumption
- Target: C-PHYS summary, PHY.ARCH.events (L36), NET.REP.physics-bodies
- Finding: the C-PHYS contract ends with "contact events are delivered per body through step-time callbacks so gameplay can react and modify bodies during the step, with optional batching". That is L36 (per-body sync callbacks and mid-step world mutation). It contradicts PHY.ARCH.events ("batched change sets, queries batched, mutations deferred") and the C-SCRIPT/C-GAME rule that world mutation goes through deferred command buffers. It also breaks C-PHYS's own conformance line (restore + resimulate reproduces the state hash), because mid-step mutation from callbacks is not reproducible.
- Evidence: L36; Jolt and PhysX 5 use contact-modification callbacks only in narrowly scoped, thread-safe form, with a batched contact-event buffer as the default; Rapier and Havok use event queues.
- Proposed change: replace the clause with "contact events delivered as a per-step batched buffer at a declared C-FRAME phase; mutations only through deferred commands; a step-time contact-modification hook exists only as an optional, allocation-free, read-mostly extension declared by ADR".

### K-ARCH-5 · major · obsolete-assumption
- Target: QA.STRAT.flaky (stance capability of L69), test-architect, ARCH.ORG.critic-calibration
- Finding: the capability defines flake handling as "automatic quarantine after repeated failures and rerun-based clearing, quarantined tests excluded from gate results". That is "retry until green" (L69, whose stance is flake classification and root-cause policy). For autonomous agents it is worse than for humans: an implementer can make a red test disappear from the gate by making it flaky. It also conflicts with QA.AGENT.test-integrity, which treats skipped and deleted cases as gate failures.
- Evidence: L69; Google's flaky-test practice and the Meta 2020s flaky-test work both separate detection (rerun) from clearing, which requires a root-cause label and an expiry. Quarantined tests must still count against release criteria (QA.STRAT.release-criteria).
- Proposed change: "Flake classification and root-cause policy: reruns only classify; quarantine carries an owner, expiry and root-cause label; quarantined tests remain counted in release gates; holdout, conformance and determinism lanes can never be quarantined".

### K-ARCH-6 · major · obsolete-assumption
- Target: CORE.JOBS.degenerate (stance capability of L25), RES.MGMT.no-stall, CORE.FRAME.host-loop, PLAT.WEB.runtime
- Finding: CORE.JOBS.degenerate allows "blocking waits on the host thread for IO completion". RES.MGMT.no-stall forbids "blocking waits on frame-critical tasks or host/OS-bound threads", and CORE.FRAME.host-loop requires a "non-blocking cooperative frame step". On the web target this is not implementable: a browser main thread cannot block on IO (no Atomics.wait on the main thread, and OPFS sync handles exist only in workers), and mobile display-link and Choreographer loops must not block. This is the one stance capability that reintroduces synchronous IO on the inline path.
- Evidence: L16, L25; the HTML spec forbids Atomics.wait on the window main thread.
- Proposed change: "blocking waits are forbidden on the host thread; the inline mode completes IO through cooperative polling of C-TASK completion tokens between frames". State the dedicated-worker exception, if any, in CORE.JOBS.blocking.

### K-ARCH-7 · minor · obsolete-assumption
- Target: PRF.METH.budgets (stance capability of L70), C-BUDGET
- Finding: PRF.METH.budgets lists "average frame-time" as a budget line. L70's stance is per-tier frame-time budgets with percentiles, and C-BUDGET says p50/p99/p99.9, max hitch length and hitches per hour. The capability name would seed an agent that budgets on averages.
- Evidence: L70; frame-pacing practice (percentile frame time, hitch counts).
- Proposed change: replace "average frame-time" with "p50/p99/p99.9 frame time, hitch length and hitches per hour".

### K-ARCH-8 · major · other
- Target: RND.SHADER.neural, C-SHADER, C-MLGPU, radar entry "In-shader neural evaluation"
- Finding: three artefacts disagree on the fallback. The capability says "single-vendor cooperative-vector tier; no standalone-dispatch fallback". C-SHADER says "optional tier with a mandatory standalone-dispatch fallback through C-MLGPU". The radar entry says "fallback: Standalone inference dispatch" and cites DXIL linear algebra, Vulkan cooperative matrix and Metal tensor operations (three vendors, not one). Owners are shader-system for the capability and ml-inference-runtime for C-MLGPU, so this is not a placement choice; the framework contradicts itself. check.py cannot see it because the radar entry fallback is non-empty.
- Evidence: DirectX cooperative vectors (SM 6.9 preview), VK_KHR_cooperative_matrix and NV cooperative_vector, Metal 4 tensors are multi-vendor; a mandatory fallback is what keeps C-SHADER's non-RT/non-ML builds buildable (00-design-principles section 7).
- Proposed change: "In-shader small-network evaluation (matrix/tensor intrinsics tier, multi-backend; mandatory standalone-dispatch fallback via C-MLGPU)". Add a conformance case to C-SHADER: fused and standalone outputs agree within the ML.RT.validation tolerance table.

### K-ARCH-9 · major · overlap
- Target: CORE.SER.commands / C-CMD (serialization-schema), ED.ARCH.transactions / C-EDCMD (editor-architect), XC.EXT.player-creation / C-EDIT (modding-ugc), GAM.FW.turns (gameplay-architect)
- Finding: four skills each own an "apply/invert, undo/history, journal" substrate. C-CMD and C-EDCMD both list "serializable diff-based commands, transactions, journal and merge hooks", and C-EDCMD requires C-CMD, so its summary should be reduced to the editor delta. C-EDIT adds its own undo and selection. GAM.FW.turns adds "ordered commands, undo/history, deterministic replay, clonable-state API" with no edge to C-CMD (contributors: determinism-replay, ai-behavior-perception, persistence-save, liveops). The overlap is hidden by naming (command, transaction, turn substrate, creation session). C-CMD is also owned by a format skill, although apply/invert and merge semantics are behavior, not encoding.
- Evidence: the ownership pattern "contract owner vs implementer" and the check that every capability has one owner. Two capabilities with the same nouns and different owners will yield two journals and two undo semantics; a UGC creation session then cannot be merged by ED.COLLAB.merge.
- Proposed change: (a) C-CMD is the only command/transaction core; move its owner to core-runtime-architect or entity-object-model (schema stays with serialization-schema). (b) Reduce C-EDCMD to undo scopes, selection, tool registration and cross-process transactions. (c) Add C-CMD to gameplay-architect consumes and state whether GAM.FW.turns is a client of C-CMD or a justified separate log (search AI needs cheap clone, not invert). (d) Reword the C-EDIT summary to "sessions, permissions, budgets, publish; commands via C-CMD".

### K-ARCH-10 · major · wrong-owner
- Target: oracle_author of C-IO, C-VFS, C-ASSET, C-RES, C-COOK, C-BUILD, C-PKG, C-EDCMD, C-GRAPH, C-CMD, C-STATECLASS, C-VFX, C-CAMERA, C-ABILITY, C-GAME and others (functional-automation-soak, 34 contracts); simulation-validation (28); render-validation (24); robustness-fuzzing (19)
- Finding: oracle authorship is concentrated in four generalist skills that do not hold the expertise of the contracts they judge. functional-automation-soak is described as "scripted and bot playthroughs, smoke, soak, HW/OS matrix, server load tests", yet it authors the conformance suites for the IO stack, the build system, the packager, editor command undo/redo invertibility, the graph compile contract, the state-class registry and VFX. The purpose of robustness-fuzzing is fuzzing, fault injection and schedule perturbation, yet it authors the semantic conformance of C-PAL, C-MOD, C-ID, C-REFL, C-SER, C-FRAME, C-FLOW and C-PRESENT. Meanwhile foundation-conformance ("conformance suites for foundation contracts") authors only 7 contracts. This contradicts "many focused experts", and 34 suites in one agent is a throughput bottleneck for the oracle-independence rule that the whole agent-validation design depends on.
- Evidence: contracts.json oracle_author counts (functional-automation-soak 34, simulation-validation 28, render-validation 24, robustness-fuzzing 19, foundation-conformance 7, ui-text-conformance 4); seL4, Chromium and Linux-kernel-style conformance ownership is per subsystem, not by test technique.
- Proposed change: (a) Move L0-L2 foundation contracts (C-PAL, C-MOD, C-SYNC, C-TASK, C-LIFETIME, C-ID, C-REFL, C-SER, C-FRAME, C-FLOW, C-PRESENT, C-IPC, C-SNAPSHOT-adjacent) to foundation-conformance; keep robustness-fuzzing as a co-signer of the harness only. (b) Add two experts under test-architect: `tools-pipeline-conformance` (C-COOK, C-BUILD, C-PKG, C-EDCMD, C-GRAPH, C-CMD, C-IMPORT, C-VCS, C-EDVIEW, C-EDHOST, C-EDPREVIEW, C-TARGETPLAT) and `content-runtime-conformance` (C-IO, C-VFS, C-ASSET, C-RES, C-SAVE, C-GAMEDATA, C-STATECLASS). (c) Keep functional-automation-soak for C-GAME-level and online contracts. Add a check that no oracle author owns more than about 20 contracts.

### K-ARCH-11 · major · overlap
- Target: QA.CONF.memory-model, QA.CONF.foundation (foundation-conformance) vs C-SYNC, C-LIFETIME, C-TASK oracle_author (robustness-fuzzing), CORE.CONC.correctness
- Finding: QA.CONF.memory-model ("memory-model litmus and model-checking lanes for foundation contracts") is owned by foundation-conformance. CORE.CONC.correctness says litmus and linearizability suite authorship "belongs to the contract's oracle_author", which for C-SYNC, C-LIFETIME and C-TASK is robustness-fuzzing. Two skills therefore own the same suites, and robustness-fuzzing's own non-responsibility list ("concurrency test campaigns" belongs to it) and foundation-conformance's ("fuzz campaigns → robustness-fuzzing") do not resolve which one authors litmus tests.
- Evidence: memory-model verification is model checking (CDSChecker, Relacy, loom, herd7 litmus), a different technique from schedule-perturbation stress (QA.ROBUST.concurrency).
- Proposed change: set oracle_author of C-SYNC and C-LIFETIME to foundation-conformance (litmus and model checking); keep QA.ROBUST.concurrency (stress and perturbation) with robustness-fuzzing; state the split in both purposes.

### K-ARCH-12 · major · missing-contract
- Target: C-EDIT, XC.EXT.runtime-graphs, C-GRAPH, RND.SHADER.untrusted
- Finding: XC.EXT.runtime-graphs compiles UGC graphs "in client targets" and states "C-GRAPH node/pin model as shared schema"; C-EDIT (layer 4, runtime) says its node/pin schema is "shared with C-GRAPH". C-GRAPH is layer 5 and tool-only, and check.py forbids runtime modules consuming L5. The text bypasses the rule, because C-EDIT does not formally require C-GRAPH. Client builds either drag the editor graph framework in or duplicate the schema.
- Evidence: the layering rule "tool contracts (L5) may only be consumed from tool_consumes"; check.py sees only listed consumes and requires, not prose.
- Proposed change: add a runtime-side contract (for example C-GRAPHRT, layer 2 or 3, owned by graph-editor-framework or scripting-runtime) for the node/pin schema, validation and restricted node-set profile; C-GRAPH consumes it on the tool side, C-EDIT requires it. Remove the prose sharing.

### K-ARCH-13 · major · missing-contract
- Target: GAM.DATA.surface-types, C-GAMEDATA, C-ENV, C-PHYS, C-AUDIO, C-VFX, C-MATIF, physics-architect, terrain, audio-content-runtime, vfx-particles, material-system
- Finding: the surface-type taxonomy is "shared by physics, terrain, audio, VFX, decals, projectiles and haptics", and C-GAMEDATA says surface-type IDs are "referenced by C-ENV, audio, VFX and materials". None of physics-architect, terrain, audio-content-runtime, vfx-particles or material-system consumes C-GAMEDATA, and C-ENV, C-PHYS, C-AUDIO and C-VFX do not require it. The most widely shared identifier space in the engine is owned by a gameplay-layer skill (data tables, tuning), with no dependency edge. physics-2d in the min2d profile therefore needs friction and restitution materials keyed by IDs from a skill it does not depend on.
- Evidence: PHY.ARCH.materials ("physics parameters bound to shared surface types"); Unreal physical materials and surface types, Unity PhysicsMaterial plus FMOD/Wwise surface switches all use one registry that sits below gameplay.
- Proposed change: create a small L2 contract for surface/material taxonomy IDs (owner entity-object-model or content-pipeline-architect, format via C-ASSET), or move the capability into C-ASSET. Add consumes edges from the five skills, and make C-GAMEDATA a client of it instead of the owner.

### K-ARCH-14 · major · scale-down
- Target: organizations.json tiers, ARCH.ORG.staffing, ARCH.ORG.delegated-planning, radar entry "Coordination of ~150 autonomous agents"
- Finding: the framework's stated program is ~150 agents (radar entry, 156 skills), but the largest staffing tier is 16 agents, each hosting an entire workstream (rendering hosts 26 skills, foundation 20, simulation 18). No tier exists at skill or lead-subtree granularity, so ledger locks, per-skill write sets and the independence proofs are never exercised at the intended agent count. The workstream is also the independence unit, so two skills in one workstream (for example rendering) can never be independence-checked against each other, and the single "quality" agent in the large tier authors every oracle (see K-ARCH-10).
- Evidence: check.py proves independence only per workstream grouping; organizations.json.
- Proposed change: add tier "xl" (one agent per skill, or per lead subtree for leads with more than 10 children) to organizations.json, with a check that every independence pair and every oracle_author vs owner/implementer pair still separates. Add a co-hosting cap (capabilities and contracts per agent) as ARCH.ORG.independence already promises but the data does not encode.

### K-ARCH-16 · minor · other

- Finding: purposes omit contracts the skill provides, which is a boundary inconsistency between purposes and contracts. modding-ugc provides only C-EDIT, but its purpose has no in-game creation, runtime graphs or distribution integrity, roughly half its capabilities. spatial-transforms owns C-VIEW (the view registry used by audio, streaming, XR, camera and editor) without mentioning views. visual-debugging-tools owns C-AUTOMATION, the protocol test skills and the editor depend on, without mentioning it. Also missing: C-CMD (serialization-schema), C-STATECLASS (reflection-metadata), C-IPC (core-runtime-architect), C-BASE and C-TARGETPLAT (platform-architect), C-HOSTAUTH quotas and overload (net-session), C-CHARCTRL (physics-architect) and C-ENV (world-architect).

### K-ARCH-17 · minor · dependency-error
- Target: C-GPUMEM→C-RES, C-RSCENE→C-INSTANCES, C-SEQ→C-FLOW, C-AI/C-AIAGENT→C-REPLAY, C-SNAPSHOT→C-STATECLASS, C-SRVDATA→C-STATECLASS, C-EDIT→C-SER/C-ID/C-FRAME, C-INTEGRITY→C-ID/C-FRAME, C-ASSET/C-PHYS/C-ANIM/C-AUDIO→C-ID
- Finding: contract summaries or requires name a dependency that the owner skill's consumes list lacks, so the closure proof, which runs on consumes, never sees it. C-GPUMEM says residency obeys the arbiter through the C-RES pool hook, but gpu-memory-resources consumes only C-RHI, C-GPUTIER and C-LIFETIME. C-RSCENE names "one persistent instance scene (C-INSTANCES)" but neither requires nor consumes it. C-AIAGENT says outputs enter simulation as C-REPLAY external inputs, but ai-behavior-perception does not consume C-REPLAY. Similar mismatches exist for the other pairs listed.
- Evidence: comparison of contracts.json requires and summary references with skills.json consumes for each owner.
- Proposed change: add the edges to requires and consumes (optional where gated). Add a check.py rule: every C-X named in a contract summary is in requires or in an explicit "informs" list, and every owner consumes the contracts its provided contracts require.

### K-ARCH-18 · minor · wrong-boundary
- Target: input-system, xr-runtime, online-services-liveops (parent platform-architect); C-SERVER vs C-HOSTAUTH
- Finding: (a) input-system (action mapping, rebinding, UI routing, accessibility input) has its real coupling to gameplay-architect (GAM.FW.control) and ui-architect (UI.FW.focus, INP.ACT.ui-routing), yet its parent is platform-architect and its workstream is platform, so its disputes always reach engine-architect. xr-runtime is mostly render-side (C-XRVIEW consumed only by render-architect). online-services-liveops has 4 of 5 consumers in the online workstream (anti-cheat, dedicated-server, net-session, ai) but sits under platform-architect. (b) C-SERVER's summary repeats "per-connection budgets, overload state and kick/ban primitives are enforced by the server host", which C-HOSTAUTH owns ("quotas and budgets, overload state, kick/ban primitives"), and the name C-HOSTAUTH suggests authentication, which is NET.SESS.auth.
- Evidence: consumers and contributors lists; ARCH.ORG.escalation rule (cross-workstream disputes go to the root).
- Proposed change: re-parent input-system under ui-architect or gameplay-architect (keep C-DEVICE with platform), online-services-liveops under network-architect (keep first-party C-SVC with platform), and xr-runtime under render-architect or gpu-platform-architect. Rename C-HOSTAUTH to C-HOSTCTL and drop the duplicate clause from C-SERVER (keep admin surface and lifecycle only).

### K-ARCH-19 · minor · maturity-error
- Target: RND.GI.restir (E), RND.LIGHT.stochastic (M), RND.PT.realtime (M), NET.TRANS.web (E) vs NET.TRANS.quic (M)
- Finding: RND.GI.restir ("ReSTIR GI & path-traced GI") is labelled E while ReSTIR DI (RND.LIGHT.stochastic) and real-time path tracing (RND.PT.realtime, whose radar tech name is the same "ReSTIR GI & path-traced GI") are M. It ships in a few titles on one vendor's hardware path, which is emerging. NET.TRANS.web (E) prefers WebTransport datagrams while NET.TRANS.quic (M) treats QUIC/WebTransport as emerging.
- Evidence: Ouyang et al. 2021 (ReSTIR GI), Lin et al. 2022 (ReSTIR PT); WebTransport is still not in every browser engine.
- Proposed change: RND.GI.restir → M (radar entry M with revisit trigger, fallback RND.GI.hybrid); NET.TRANS.web → "WebRTC unreliable channels (E) preferred, WebTransport (M via NET.TRANS.quic) when available".
